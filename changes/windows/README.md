# Change tooling for the gaming PC

This directory holds the only code in the repository that changes the PC. Each script makes one change, either one step of the undo order in the latency change timeline report or one researched change such as the network tuning, and `kbd-crash-dump.ps1` adds the keyboard initiated crash dump. Each is run by hand at the PC on the captain's own Yes for that change, and can put back exactly what it changed. Everything else in the repository (the collectors, the scenario runner, the SSH front door) is read only and never refers to this directory; `tests/test_changes_area.py` enforces that.

## Rules for every change script

- **Separate area.** Change scripts live here, outside `collectors/`, one self contained script per change, with a library beside it when it needs one. No collector, no part of the scenario runner and nothing in `remote-access/` may call, list or name anything here, and nothing the dispatcher, the runner or a collector does may start a change script. Collectors keep their own read only rules and forbidden command list.
- **Verbs.** `-Plan` is the default and reads only: it prints the current state, exactly what would change and every precondition, and refuses with the reason when one fails. `-Apply` saves the before-state, checks, writes and reads back. `-Undo` restores the saved before-state. `-Readback` reads only and prints PASS or FAIL per value. Only `-Apply` and `-Undo` change anything; each must be named, one verb per run, and no script ever prompts.
- **Save before change, refuse without it.** `-Apply` writes every affected key to a timestamped evidence folder first (a values CSV, `reg export` files and a SHA-256 list written last) and refuses if any part of that fails. `-Undo` restores exactly what was saved: a value that was absent is deleted again, and nothing else is touched. Every Apply and Undo ends with a readback that prints PASS or FAIL per value.
- **Stop on the unexpected.** The precheck refuses when a live value is not the one the plan expects, and prints what is there instead.
- **Nothing else.** No installs, downloads, network calls, scheduled tasks (the one exception is `session-bracket-task.ps1`, whose change is exactly one per user logon task with the standard token), services, restarts, game handles, injection or overlays, and nothing runs while the game or its launcher runs. Nothing gives itself lasting elevation: a script that needs administrator rights says so and the operator starts an elevated Windows PowerShell by hand.
- **Privacy.** Output uses fixed labels (`display-adapter-1`, `ethernet-1`) and `<profile>`; it never prints a user name, profile path, command line, device instance path, or hardware or network address. Evidence folders stay on the PC.
- **Windows PowerShell 5.1, plain ASCII,** and no `ConvertTo-Json`. Every Windows fact is cited to Microsoft Learn or the tool's own documentation next to the code, and anything not yet seen on the PC is on the list at the end of this page.

The scripts are tested only against a synthetic backend: `tests/` replaces every adapter that touches Windows, and the Pester suite runs every Apply, Undo and Readback path, including the failure paths (export fails, precheck fails, write fails, readback mismatch, undo after a partial apply). Nothing is ever tested on a real registry or adapter.

```
pwsh -NoProfile -File changes/windows/tests/Invoke-Checks.ps1 -ModulePath tools/psmodules
pytest tests/test_changes_area.py tests/test_change_gpu_affinity_1a.py tests/test_change_network_tuning.py tests/test_change_kbd_crash_dump.py tests/test_changes_pwsh.py
```

## `gpu-affinity-1a.ps1`: step 1a, display adapter interrupt affinity

What it changes: the two values Stutter Guard's affinity tweak wrote on 12 November under the display adapter's `Device Parameters\Interrupt Management\Affinity Policy` key, `DevicePolicy` and `AssignmentSetOverride`, which a later tool rewrote on 17 November (CPU 6). It puts each back to the state recorded in the single matching `Originals` row of Stutter Guard's journal: Existed false deletes the value, Existed true writes the recorded type and data. It never touches `DevicePriority` (no journal row covers it; it is read and saved for the record), the MSI properties (step 1b) or anything else. The operator page with the sequence, the play log and the advance criteria is [docs/changes/step-1a-gpu-affinity.md](../../docs/changes/step-1a-gpu-affinity.md).

```
gpu-affinity-1a.ps1 [-Plan] | -Apply | -Undo [-EvidenceFolder <yyyyMMddTHHmmssZ>] | -Readback
                    [-StutterGuardDataDirectory <dir>] [-EvidenceRoot <dir>]
```

Defaults: the Stutter Guard data folder is `%ProgramData%\Stutter Guard` (the pinned `Paths.cs` also knows an older `DPC Latency Tweaker` folder; pass it with `-StutterGuardDataDirectory` if that is where `journal.json` is), the evidence root `%ProgramData%\win-forensics\changes\gpu-affinity-1a`. Exit codes: 0 done (Plan: every precondition holds; Readback: every value PASS), 1 a write or a readback failed, 2 refused or cannot tell, with nothing changed. Plan and Readback run unelevated; Apply and Undo refuse unless the console is elevated.

### What Plan checks

| Check | Passes when |
| --- | --- |
| `device` | exactly one present PCI device of the Display setup class, with an instance path of the PCI shape (`Get-PnpDevice -Class Display -PresentOnly`) |
| `game` | neither the game nor its launcher is running |
| `live` | `DevicePolicy` is REG_DWORD 4 and `AssignmentSetOverride` holds a mask with only CPU 6 (REG_BINARY, REG_DWORD or REG_QWORD); otherwise it prints what is there |
| `journal` | `journal.json` reads as the pinned format; one malformed row makes it unreadable |
| `row-DevicePolicy`, `row-AssignmentSetOverride` | exactly one `Originals` row with Kind `reg` and the value's Target, belonging to tweak `irq.<instance>`, recorded on 12 November |
| `session-reg` | the reg export Stutter Guard made of the device's `Interrupt Management` key in the session that recorded the rows (the latest `Backups\yyyyMMdd-HHmmss` of that day created no later than the row), parsed as text and never imported, shows the same before-state for both values |
| `bitsum-backup` | Bitsum's `HKLM\SOFTWARE\Bitsum\InterruptAffinityBackup` has exactly one entry for the adapter's vendor and device, and what it recorded agrees with the rows (no mask recorded when the row says there was no mask, the same mask or policy when one was) |
| `nothing-to-do` | the live values are not already the rows' values |
| `reapply` | no scheduled task, service or running program that could put the values back (below) |

### Sources

- **The values and their types.** `DevicePolicy` is a REG_DWORD (`IrqPolicySpecifiedProcessors` is 4) and `AssignmentSetOverride` a KAFFINITY mask stored as REG_BINARY (little endian, at most the platform's KAFFINITY size), REG_DWORD or REG_QWORD, under the device's `Interrupt Management\Affinity Policy` key; Microsoft recommends the default policy where it applies: [Interrupt affinity and priority](https://learn.microsoft.com/windows-hardware/drivers/kernel/interrupt-affinity-and-priority).
- **Restart.** The values reach the driver through `IRP_MN_FILTER_RESOURCE_REQUIREMENTS`, which the PnP manager sends before it allocates the device's resources during initial device configuration and may send during rebalancing: [IRP_MN_FILTER_RESOURCE_REQUIREMENTS](https://learn.microsoft.com/windows-hardware/drivers/kernel/irp-mn-filter-resource-requirements). So a restart is needed before the change takes effect. That the display adapter takes them at the next restart is an inference; Bitsum documents the same for display adapters ([Interrupt Affinity Policy](https://bitsum.com/apps/process-lasso/docs/tools/interrupt-affinity-policy/), [IRQControl](https://bitsum.com/irqcontrol/)). The script never restarts anything and says so in Plan, Apply and Readback; Readback compares the last boot time ([Win32_OperatingSystem](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-operatingsystem)) with the Apply time.
- **The key.** The script opens `HKLM\SYSTEM\CurrentControlSet\Enum\<instance>\Device Parameters\...` in the 64 bit view with `Microsoft.Win32.RegistryKey` ([OpenBaseKey](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey.openbasekey), [GetValue](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey.getvalue), [SetValue](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey.setvalue), [DeleteValue](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey.deletevalue)). This departs from Learn, which says a device's hardware key must not be opened directly and names `SetupDiOpenDevRegKey` or `CM_Open_DevNode_Key` instead ([Opening a device's hardware key](https://learn.microsoft.com/windows-hardware/drivers/install/opening-a-device-s-hardware-key)). The Enum path is the one Stutter Guard's journal names, the one `reg export` takes, and the one the other tools wrote through; using it keeps the change free of native interop. Item 1a.2 below checks that it is the same key.
- **Saving.** `reg export <key> <file> /y` returns 0 on success and 1 on failure: [reg export](https://learn.microsoft.com/windows-server/administration/windows-commands/reg-export). The evidence folder holds `before-values.csv` (role, value, existence, kind, data, the target state and a SHA-256 of the device's instance path, never the path), `evidence.txt` (journal and session export hashes, the row numbers, the pinned source commit), `affinity-policy.reg`, `msi-properties.reg`, `bitsum-backup.reg` and `SHA256SUMS`, written last; a folder without `SHA256SUMS` is incomplete and Undo never uses it. The reg exports carry the instance path, so the folder stays on the PC.
- **Stutter Guard's records,** read from its public source at commit `8c783a478f4b511c273b3235bf745b5d64550f49`, never by running anything it ships: `Journal.cs` (the row fields, first record wins, System.Text.Json with nulls omitted), `RegistryOps.cs` (how a value is written into Data), `JournalRestorer.cs` (Existed with a kind and data writes, otherwise deletes), `BackupSet.cs` (the session folders and the export file names), `Paths.cs` (the data folder) and `Interrupts.cs` (the tweak exports the `Interrupt Management` key, then writes `DevicePolicy` 4 and `AssignmentSetOverride`). The reader is `_stutter-guard-journal.ps1`; later steps (1b, 4a) call `Read-WfSgJournal` and `Select-WfSgOriginalRow` with their own targets.
- **Unsafe undo sources,** never used: Stutter Guard's `undo-all.ps1` and per session `undo.ps1` (they revert every session), whole key `.reg` imports (they overwrite every value), and Bitsum's Restore All, Reset Configuration or uninstall (every changed device).

### Re-application

Plan refuses while anything that could put the values back is present, and names it:

- **Stutter Guard.** At the pinned commit it registers two tasks under `\Stutter Guard\` (`BootTasks.cs`, `TaskSched.cs`): "Device power saving off" runs `StutterGuard.exe --agent device-power` at boot, which changes device power settings only (`Agent.cs`, `DevicePower.ApplyNow`), and "Timer resolution" starts the timer helper at logon. `--agent drift-check` only reads. Re-applying a drifted interrupt affinity ("heal") happens only from the app's window on a click (`Pages.cs`). Plan accepts exactly these task actions as known, refuses any other action in those folders or any task or service that runs `StutterGuard.exe`, `IRQControl.exe`, `LatencyTest.exe` or `DpcTimerRes.exe` with an action it has not reviewed, and refuses while `StutterGuard`, `IRQControl` or `LatencyTest` is running.
- **Bitsum.** The Interrupt Affinity Policy tool is its own program (IRQControl) that writes the policy Windows reads when it starts a device; the Process Governor applies process rules ([How it works](https://bitsum.com/apps/process-lasso/docs/getting-started/how-it-works/), [Auto-start](https://bitsum.com/apps/process-lasso/docs/deployment/auto-start/)). Neither page describes re-applying an interrupt policy at boot or on a timer. Silence is not proof, so the Governor is reported, not refused, and Readback after the restart is the check: a value put back reads FAIL.

## `network-tuning.ps1`: the wired adapter's network settings

What it changes: advanced properties of the one wired Realtek adapter on the Realtek NetAdapterCx driver (`rt25cx21x64`) installed on 19 November, in two groups:

- **The default set,** the settings the research gave an include verdict. Today that is one setting, `idle-restriction`: `*IdleRestriction` from 0 ("No restriction", the value the install set) back to 1 ("Only idle when user isn't present", the value before the install).
- **Opt in experiments,** the properties the research rates measure first (no cited latency case either way): `green-ethernet`, `power-saving-mode`, `gigabit-lite` (found by their display names, since the PC's transcription did not record their keywords), `ltr-obff` (keyword `LTROBFF`) and `flow-control` (`*FlowControl`). They are never in the default set, run only when named alone with `-Only`, and get the same save, Undo and Readback. Each proposes the driver's own off value: the one valid value whose display text is "Disabled", read live. Plan labels each "measure first, no cited latency case" and refuses when the driver shows no such value (today `LTROBFF` is hidden, so `ltr-obff` is refused).

 It never touches the TCP/IP stack, QoS, DNS, IPv6, the MTU, interrupt affinity or MSI (step 4a), device power management or USB (step 4b), or ExitLag (step 7). Why each other setting is left alone, with sources, is in [docs/changes/network-tuning-research.md](../../docs/changes/network-tuning-research.md); the operator page with the sequence and what to record is [docs/changes/network-tuning.md](../../docs/changes/network-tuning.md).

```
network-tuning.ps1 [-Plan] | -Apply | -Undo [-EvidenceFolder <yyyyMMddTHHmmssZ>] | -Readback
                   [-Only <name>[,<name>...]] [-EvidenceRoot <dir>]
```

`-Only` takes setting names (one comma separated string or several) and goes with Plan, Apply and Readback; without it the default set runs. An unknown name is refused with the list of known ones, and an opt in name together with any other name is refused (one experiment at a time). Undo takes no `-Only`: one Apply run is one evidence folder, and Undo puts back everything that folder saved. The evidence root defaults to `%ProgramData%\win-forensics\changes\network-tuning`. Exit codes: 0 done (Plan: ready to apply; Readback: every value PASS), 1 a write or a readback failed, 2 refused, nothing to do, or stopped on an unexpected error, with nothing changed. Plan and Readback run unelevated; Apply and Undo refuse unless the console is elevated.

### What Plan checks

| Check | Passes when |
| --- | --- |
| `game` | neither `Overwatch` nor `Battle.net` is running |
| `adapter` | exactly one physical adapter with the 802.3 medium (`NdisPhysicalMediumType` 14) is Up (`Get-NetAdapter -Physical`) |
| `realtek` | its description names Realtek and its driver file is `rt25cx21x64.sys` (a rollback to another driver is refused, since `*IdleRestriction` is a NetAdapterCx keyword) |
| `name` | its name has no wildcard characters, so the NetAdapter cmdlets take it literally |
| `driver-key` | its driver key name (`DEVPKEY_Device_Driver`) has the network class shape `{4d36e972-e325-11ce-bfc1-08002be10318}\nnnn`, so Apply can export it |
| per setting `exposed` | the driver lists the keyword, or for a setting matched by name the display name, exactly once (`Get-NetAdapterAdvancedProperty -AllProperties`), and the live keyword is a plain name; every write uses that live keyword |
| per setting `displayed` | it has a display name (a hidden property is refused) |
| per setting `type` | its registry type is REG_SZ (1), as for every displayed property |
| per setting `value` | the live value is one decimal number |
| per setting `off-value` | opt in entries only: exactly one valid value is shown as "Disabled"; it becomes the proposed value |
| per setting `valid` | the driver's valid values include both the live and the proposed value |

When every selected setting already holds its proposed value, Plan says NOTHING TO DO and Apply refuses. Plan also lists every other displayed property of the adapter (never one whose keyword or name mentions an address) and the "allow the computer to turn off this device" state, read only, so the before-and-after record has them.

### Saving, the write, Undo and Readback

- **The evidence folder** `<root>\<yyyyMMddTHHmmssZ>` holds `before-values.csv` (setting, keyword, display name, the live value and its display text, the proposed value, the valid values, a SHA-256 of the device instance path, never the path, the driver file and version), `adapter-driver-key.reg` (`reg export` of `HKLM\SYSTEM\CurrentControlSet\Control\Class\<driver key>`, where the driver keeps its advanced properties) and `SHA256SUMS`, written last. Apply refuses if the folder exists, the export exits non zero or writes nothing, or the CSV does not read back. A folder without `SHA256SUMS` is incomplete and Undo never uses it. The `.reg` export can hold the adapter's addresses, so the folder stays on the PC.
- **The write** is `Set-NetAdapterAdvancedProperty -Name <adapter> -RegistryKeyword <keyword> -RegistryValue <value> -NoRestart`, one setting at a time, in the table's order, after a precheck that every live value still equals the saved one. A failed write stops the run; the readback that follows names what changed, and the output says to run `-Undo -EvidenceFolder <stamp>`.
- **Undo** uses the newest complete folder, or the one named with `-EvidenceFolder`. It checks every file against `SHA256SUMS` and the device hash against the adapter. The hashes sit in the same folder, so they only detect accidental damage; what bounds Undo to the table's settings is the row checks: each row names a setting from the table once, its keyword is that setting's own (exactly, for a setting with a keyword; a plain name saved with the setting's display name, for one matched by display name), its driver file is rt25cx21x64, and on the live adapter that keyword is exposed exactly once, still under the setting's display name when matched by it, with both the saved and the applied value among its valid values. Any row that fails refuses the whole Undo before a write. Then for each saved row: a live value equal to the saved one is left alone (so Undo after a partial Apply writes only what Apply wrote), a live value equal to the proposed one is written back, and anything else refuses the whole Undo. It ends with a readback against the saved values.
- **Readback** prints PASS when the live value is the applied one. Without `-Only` it reads the rows of the newest complete folder; with `-Only` it checks exactly the named settings, each against its row in the newest complete folder that holds it, and names that folder per setting. A setting with no such folder (or, without `-Only`, the default set when there is no folder) is compared with its proposed value, read live; an opt in whose off value cannot be read is FAIL. After an Undo it therefore reads FAIL, as expected; the Undo output itself shows PASS against the saved values. For each folder used whose Apply is newer than the last boot, it adds that the PC has not restarted since.

### Sources

- **The keyword.** `*IdleRestriction`: 0 (default) "No restriction", 1 "Only idle when user isn't present"; [standardized INF keywords for power management](https://learn.microsoft.com/windows-hardware/drivers/network/standardized-inf-keywords-for-power-management). The resume latency guideline and the framework's D0 while the interface is in use: [configuring NetAdapterCx power management](https://learn.microsoft.com/windows-hardware/drivers/netcx/configuring-power-management), [porting NDIS miniports to NetAdapterCx](https://learn.microsoft.com/windows-hardware/drivers/netcx/porting-ndis-miniport-drivers-to-netadaptercx#querying-and-setting-power-management-capabilities).
- **Reading.** [Get-NetAdapter](https://learn.microsoft.com/powershell/module/netadapter/get-netadapter) and [MSFT_NetAdapter](https://learn.microsoft.com/windows/win32/fwp/wmi/netadaptercimprov/msft-netadapter) (Status, ConnectorPresent, NdisPhysicalMedium, DriverFileName), [Get-NetAdapterAdvancedProperty](https://learn.microsoft.com/powershell/module/netadapter/get-netadapteradvancedproperty) and [MSFT_NetAdapterAdvancedPropertySettingData](https://learn.microsoft.com/windows/win32/fwp/wmi/netadaptercimprov/msft-netadapteradvancedpropertysettingdata) (RegistryDataType, ValidRegistryValues), [MSFT_NetAdapterPowerManagementSettingData](https://learn.microsoft.com/windows/win32/fwp/wmi/netadaptercimprov/msft-netadapterpowermanagementsettingdata) (AllowComputerToTurnOffDevice, read only), [Get-PnpDeviceProperty](https://learn.microsoft.com/powershell/module/pnpdevice/get-pnpdeviceproperty) with [DEVPKEY_Device_Driver](https://learn.microsoft.com/windows-hardware/drivers/install/devpkey-device-driver), the network class GUID from [system defined device setup classes](https://learn.microsoft.com/windows-hardware/drivers/install/system-defined-device-setup-classes-available-to-vendors), [Win32_OperatingSystem](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-operatingsystem) for the last boot.
- **Writing and restarting.** [Set-NetAdapterAdvancedProperty](https://learn.microsoft.com/powershell/module/netadapter/set-netadapteradvancedproperty) with `-NoRestart`; "Many advanced properties require restarting the network adapter before the new settings take effect" ([New-NetAdapterAdvancedProperty](https://learn.microsoft.com/powershell/module/netadapter/new-netadapteradvancedproperty), [Restart-NetAdapter](https://learn.microsoft.com/powershell/module/netadapter/restart-netadapter)). The script restarts nothing; the operator disables and enables the adapter in Device Manager or restarts the PC.
- **Saving.** `reg export <key> <file> /y` returns 0 on success and 1 on failure: [reg export](https://learn.microsoft.com/windows-server/administration/windows-commands/reg-export).

## `kbd-crash-dump.ps1`: keyboard initiated crash dump

Not an undo order step: it is the change that lets the captain end a hard freeze with a stop code and a memory dump instead of a power off. What it changes: `CrashOnCtrlScroll` REG_DWORD 1 under the USB (`kbdhid`) and PS/2 (`i8042prt`) keyboard `Parameters` keys, or with `-AlternateKeys` the documented `Dump1Keys` and `Dump2Key` under their `crashdump` keys, so a hard freeze can be ended with stop error 0xE2 and a memory dump. Takes effect after a restart; the script never restarts anything.. The operator page with the key sequence, what to expect, what to do after the reboot and what it cannot do is [docs/changes/kbd-crash-dump.md](../../docs/changes/kbd-crash-dump.md).

```
kbd-crash-dump.ps1 [-Plan] | -Apply | -Undo [-EvidenceFolder <folder>] | -Readback
                   [-AlternateKeys [-Dump1Keys <bitmap>]] [-EvidenceRoot <dir>]
```

Exit codes: 0 done (Plan: ready; Readback: every value PASS), 1 refused or a read only check failed, with nothing changed, 2 a write or the readback failed after a change began (run `-Undo`). Plan reports a non elevated console as a failed precondition, Readback runs unelevated, and Apply and Undo refuse without elevation. The default evidence root is `<Desktop>\wf-changes\kbd-crash-dump`.

### What it reads and decides

- Change rows: the two `CrashOnCtrlScroll` values (or the four alternate values). Guard rows, read and never written: the alternate values in the default mode, `CrashOnCtrlScroll` in the alternate mode, because Microsoft documents the alternate keys only with `CrashOnCtrlScroll` 0 or removed ([keyboard crash](https://learn.microsoft.com/windows-hardware/drivers/debugger/forcing-a-system-crash-from-the-keyboard)). Context rows, printed and saved: `CrashDumpEnabled`, `LogEvent`, `AutoReboot` and `DumpFile` under `CrashControl` ([recovery options](https://learn.microsoft.com/troubleshoot/windows-client/performance/configure-system-failure-and-recovery-options)).
- Preconditions: elevated; a 64-bit PowerShell on 64-bit Windows; both service keys exist (the script never creates a service key, only the `Parameters` or `crashdump` subkey under an existing one); every value read; each change value absent (or REG_DWORD 0 for `CrashOnCtrlScroll`), so an applied or half applied change is never saved as a before-state; the guards hold; `CrashDumpEnabled` a nonzero REG_DWORD, because a dump is written only when dump files are enabled; `-Dump1Keys` a combination of Microsoft's six documented first keys, which Microsoft allows: "You can assign `Dump1Keys` a value that enables one or more keys as the first key used in the keyboard shortcut sequence. For example, assign `Dump1Keys` a value of 0x11 to define both the rightmost and leftmost SHIFT keys as the first key in the keyboard shortcut sequence." (https://learn.microsoft.com/windows-hardware/drivers/debugger/forcing-a-system-crash-from-the-keyboard, "Dump1Keys").
- Saved per apply, under `<Desktop>\wf-changes\kbd-crash-dump\<yyyyMMddTHHmmssZ>-apply` (or `-EvidenceRoot`): `before-values.csv` (role, mode, key, name, whether the key and the value existed, kind, data, target), one `.reg` per change key that exists (a key that does not exist yet is exported by nothing: the CSV records it as `KeyExisted` False and `SHA256SUMS.txt` covers the CSV; the parent service key is never exported, since it holds subkeys this change does not touch and the privacy rule keeps device identifiers out of saved evidence), `SHA256SUMS.txt`, and `log.txt` with every printed line. `-Undo` writes the same set as `<time>-undo` before it restores; when every value already reads as saved and no key the apply created remains, it reports that there is nothing to undo, saves no folder and changes nothing. Just before its first write each run adds `writes-begun.txt` to its folder (and refuses, nothing changed, if it cannot); a folder without it is from a refused run, and `-Readback` never counts it as a change.
- Writes go through `Microsoft.Win32.RegistryKey` in the 64-bit view: the parent is opened for writing and must exist, `CreateSubKey` opens or creates the leaf, `SetValue` writes a REG_DWORD, `DeleteValue` removes one, and a key the apply created is removed with `DeleteSubKey` only when it holds no values and no subkeys again ([RegistryKey](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey), [DeleteSubKey](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey.deletesubkey)). The only process it starts is `reg.exe export <key> <file> /y` from the system directory, whose exit code is 0 on success and 1 on failure ([reg export](https://learn.microsoft.com/windows-server/administration/windows-commands/reg-export)).
- `-Readback` also compares the last boot time (`Win32_OperatingSystem.LastBootUpTime`, [Win32_OperatingSystem](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-operatingsystem)) with the newest apply or undo folder that holds `writes-begun.txt`, and says whether the restart Microsoft requires has happened.
- Unlike step 1a, this change may have to create a key: Microsoft says to create the value in the `Parameters` or `crashdump` key, which need not exist. The script creates only that subkey, only under an existing service key, records that it did, and on undo removes it only if it is empty again. `CreateSubKey` and `DeleteSubKey` appear only in its two write adapters (`Set-KcdRegistryDword`, `Remove-KcdRegistryKey`); `tests/test_changes_area.py` allows them for this script alone and `tests/test_change_kbd_crash_dump.py` confines them to those adapters.

### Tests

- `tests/KbdCrashDump.Synthetic.ps1` replaces the adapters with an invented registry, reg export, identity, clock and boot time; `tests/KbdCrashDump.Tests.ps1` runs the real script against it: every verb, every precondition, export failures (exit code and a missing file), an evidence folder that cannot be created, a value that moves during the save, a failed write followed by an undo that restores the exact before-state, a readback mismatch, a tampered or foreign CSV, a value changed by something else before an undo, a key the apply created and the undo removes or keeps, and the alternate keys.
- `tests/test_change_kbd_crash_dump.py` keeps the guards that hold even for code no test reaches (registry writes only in the write adapters, reg.exe only with `export`, each with a planted negative case), checks the operator page's required sections and the K list, and runs the unmodified script as a process off Windows, where every adapter fails and it must refuse without writing anything. The area rules are checked by `tests/test_changes_area.py`, and `tests/test_changes_pwsh.py` runs the analyzer and the whole Pester suite.

## `session-bracket-task.ps1`: the session bracket logon task

Not an undo order step: it registers, reads back and removes the per user logon task that starts the read only `session-bracket` collector's baseline (`collectors/windows/README.md`, "The session-bracket sources"), so a play session never depends on anyone announcing it first. It runs from a normal Windows PowerShell window, never elevated. The operator page with the sequence, the after read, what happens when a game starts at logon and what to record is [docs/changes/session-bracket-task.md](../../docs/changes/session-bracket-task.md).

```
session-bracket-task.ps1 [-Plan] | -Apply | -Undo | -Readback
```

Exit codes: 0 done (every readback value PASS), 1 a change or a readback failed (run `-Readback`, then `-Undo`), 2 refused before anything changed. Each run prints PASS or FAIL per value; it never prompts.

The task, in the root folder of the Task Scheduler library:

| Field | Value |
|---|---|
| Name | `win-forensics-session-bracket-baseline` |
| Trigger | At logon of the account that ran `-Apply`, nobody else |
| Principal | That account, logon type Interactive (no password stored), run level Limited |
| Action | `<System32>\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -WindowStyle Hidden -ExecutionPolicy RemoteSigned -File "<repository>\collectors\windows\session-bracket.ps1" -Phase baseline -ToEvidenceFolder` |
| Settings | Stop after 10 minutes; a second start while one runs is ignored |
| Description | Names the undo command |

Why it can carry no more than the account's standard token: Microsoft documents that a user who is not an administrator may register a task for their own account with the interactive logon type and no password, that from a process that is not elevated only the low run level (LUA, Limited) can be registered, and that members of Users can read, change, delete and run only the tasks they created ([Security Contexts for Tasks](https://learn.microsoft.com/windows/win32/taskschd/security-contexts-for-running-tasks)). The same page says the run level is ignored for the built in Administrator account and when UAC is turned off, so the task would then run elevated; the preconditions refuse both.

Preconditions, each printed by `-Plan` and checked again by `-Apply`:

| Check | Why |
|---|---|
| `no_game_running` | None of the games or launchers runs, as `Get-Process` reports `ProcessName` (names only); a list that cannot be read is refused. `-Undo` checks it too. The area's rule: nothing runs beside the game or its launcher. |
| `not_elevated` | `WindowsPrincipal.IsInRole(Administrator)` is false until the process is elevated under UAC ([IsInRole](https://learn.microsoft.com/dotnet/api/system.security.principal.windowsprincipal.isinrole)); an elevated shell is refused so nothing elevated is registered. |
| `not_builtin_administrator` | The built in Administrator has RID 500 (same page); its tasks ignore the run level. |
| `uac_on` | `EnableLUA` under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System` is 1 ([UAC settings](https://learn.microsoft.com/windows/security/application-security/application-control/user-account-control/settings-and-configuration)); 0, absent or unreadable is refused. |
| `task_absent` | `-Apply` registers a new task only; an existing one is read with `-Readback` and removed with `-Undo`. A task list that cannot be read is refused. |
| `collector_present`, `helper_present`, `powershell_present` | The files the task runs exist. |
| `path_quotable` | The collector path holds no double quote, so it passes quoted to `-File`. |
| `collector_not_blocked`, `helper_not_blocked` | No `Zone.Identifier` stream: `RemoteSigned` refuses a script downloaded from the internet until `Unblock-File` removes the stream ([about_Execution_Policies](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_execution_policies), [Unblock-File](https://learn.microsoft.com/powershell/module/microsoft.powershell.utility/unblock-file)). A stream that cannot be listed is refused. |
| `execution_policy_machinepolicy`, `execution_policy_userpolicy` | Group Policy scopes override `-ExecutionPolicy` on the command line (same page); `Restricted` or `AllSigned` there would stop the unsigned collector, so they are refused. |
| `desktop_resolved` | The evidence folder is `Environment.SpecialFolder.DesktopDirectory` ([SpecialFolder](https://learn.microsoft.com/dotnet/api/system.environment.specialfolder)), never a hard coded profile path. |

What `-Apply` saves, in `<Desktop>\latency-evidence\session-bracket-task-<UTC>\`, each file with its `.sha256`: `before.csv` (the task absent), `collector-hashes.csv` (the SHA-256 of the collector and `_common.ps1` it registers), `apply-started.txt`, then `after.csv` and `task-after.xml` (the `Export-ScheduledTask` XML with the account written `<user>`, its SID `<sid>`, the profile `<profile>`). `-Undo` saves `undo-before-<UTC>.csv` before it removes anything, removes the task only when its definition is the expected one or the one saved in `after.csv` (so a partial `-Apply` can be undone), and never touches a task with this name that changed since. `-Readback` also prints the last run time and result (`0` the collector exited 0, `1` its bundle failed, `0x41303` not yet run, `0x41301` running: [Task Scheduler error and success constants](https://learn.microsoft.com/windows/win32/taskschd/task-scheduler-error-and-success-constants)) and whether the collector or the helper changed since `-Apply`.

The cmdlets: [Register-ScheduledTask](https://learn.microsoft.com/powershell/module/scheduledtasks/register-scheduledtask), [New-ScheduledTaskPrincipal](https://learn.microsoft.com/powershell/module/scheduledtasks/new-scheduledtaskprincipal), [New-ScheduledTaskTrigger](https://learn.microsoft.com/powershell/module/scheduledtasks/new-scheduledtasktrigger), [New-ScheduledTaskSettingsSet](https://learn.microsoft.com/powershell/module/scheduledtasks/new-scheduledtasksettingsset), [Unregister-ScheduledTask](https://learn.microsoft.com/powershell/module/scheduledtasks/unregister-scheduledtask), [Export-ScheduledTask](https://learn.microsoft.com/powershell/module/scheduledtasks/export-scheduledtask), [Get-ScheduledTaskInfo](https://learn.microsoft.com/powershell/module/scheduledtasks/get-scheduledtaskinfo).
