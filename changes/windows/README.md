# Windows change scripts

This directory holds the project's only code that changes a Windows machine. Everything in `collectors/` reads; a script here writes, when the captain runs it by hand at the PC on his own word for that specific change. The captain authorized building change tooling on 2026-11-19, on a plan that applies a change only on his own Yes at the PC.

## Rules for every change script

- **Separate area.** One self-contained script per change, here and nowhere else. A change script does not dot source the collector helper, and nothing in `collectors/` (the collectors, the helper, the scenario runner) or `remote-access/` (the dispatcher, the setup, the Mac scripts) may reference this directory or call a change script. `tests/test_change_kbd_crash_dump.py` checks that, and the collectors' static guard keeps its forbidden command list unchanged. The front door's setup installs only `collectors/windows/*.ps1`, so no change script ever reaches the dispatcher's account.
- **Verbs.** `-Plan` is the default and read only: the current state, exactly what would change, every precondition with OK or FAIL, and a refusal with the reasons when one fails. `-Apply` prechecks, saves, applies and reads back. `-Undo` restores the saved before-state. `-Readback` is read only and compares the live state with the expected state. Only `-Apply` and `-Undo` change anything, each only when named; more than one verb is refused. No parameter is mandatory and nothing prompts.
- **Save before change, refuse without it.** Before `-Apply` writes anything it saves every affected key to a new timestamped evidence folder (a values CSV, a `reg export` of each key, and `SHA256SUMS.txt` over them) and refuses if any part of that fails. It then reads the state again and refuses if it moved. `-Undo` checks the CSV against its saved SHA-256, accepts only the documented keys and values, refuses if anything other than the change has touched them since, restores a value that was absent by deleting it, and touches nothing else. Every apply and undo ends with a readback that prints PASS or FAIL per value. Exit codes: 0 all PASS (or, for `-Plan`, ready), 1 refused or a read only check failed, nothing changed, 2 a write or the readback failed after a change began.
- **Preconditions are guards.** A value that is not in the state the change was written for stops the script before anything changes, the way the reviewed WER change's precheck stopped on an unexpected value. An unreadable value is a failed precondition, never an absent one.
- **Elevation by hand only.** A script that needs Administrator says so and refuses without it; the operator opens Windows PowerShell with Run as administrator. No scheduled task, no service, no stored elevation.
- **No game handles, injection, overlays, installs or downloads**, and nothing that runs while a game runs unless that is the point of the change and is documented.
- **The same rules as the collectors** otherwise: Windows PowerShell 5.1, plain ASCII, no em or en dashes in documents, a Microsoft Learn citation for every Windows fact (anything uncited is marked unverified), privacy (no user names, profile paths, command lines, or network or hardware addresses in output; the profile path prints as `<profile>`), Win-opt is tooling history only, and no new CI before phase 2.
- **Testing.** Each script's Windows adapters sit in one guarded block at its bottom, and its Pester suite under `tests/` replaces them with a synthetic registry, so every apply, undo and readback path, including the failure paths, runs here. Nothing is tested on a real registry.

## The scripts

| Script | What it changes | Operator page |
|---|---|---|
| `kbd-crash-dump.ps1` | `CrashOnCtrlScroll` REG_DWORD 1 under the USB (`kbdhid`) and PS/2 (`i8042prt`) keyboard `Parameters` keys, or with `-AlternateKeys` the documented `Dump1Keys` and `Dump2Key` under their `crashdump` keys, so a hard freeze can be ended with stop error 0xE2 and a memory dump. Takes effect after a restart; the script never restarts anything. | [docs/kbd-crash-dump.md](../../docs/kbd-crash-dump.md) |

### kbd-crash-dump: what it reads and decides

- Change rows: the two `CrashOnCtrlScroll` values (or the four alternate values). Guard rows, read and never written: the alternate values in the default mode, `CrashOnCtrlScroll` in the alternate mode, because Microsoft documents the alternate keys only with `CrashOnCtrlScroll` 0 or removed ([keyboard crash](https://learn.microsoft.com/windows-hardware/drivers/debugger/forcing-a-system-crash-from-the-keyboard)). Context rows, printed and saved: `CrashDumpEnabled`, `LogEvent`, `AutoReboot` and `DumpFile` under `CrashControl` ([recovery options](https://learn.microsoft.com/troubleshoot/windows-client/performance/configure-system-failure-and-recovery-options)).
- Preconditions: elevated; a 64-bit PowerShell on 64-bit Windows; both service keys exist (the script never creates a service key, only the `Parameters` or `crashdump` subkey under an existing one); every value read; each change value absent (or REG_DWORD 0 for `CrashOnCtrlScroll`), so an applied or half applied change is never saved as a before-state; the guards hold; `CrashDumpEnabled` a nonzero REG_DWORD, because a dump is written only when dump files are enabled; `-Dump1Keys` a combination of Microsoft's six documented first keys, which Microsoft allows: "You can assign `Dump1Keys` a value that enables one or more keys as the first key used in the keyboard shortcut sequence. For example, assign `Dump1Keys` a value of 0x11 to define both the rightmost and leftmost SHIFT keys as the first key in the keyboard shortcut sequence." (https://learn.microsoft.com/windows-hardware/drivers/debugger/forcing-a-system-crash-from-the-keyboard, "Dump1Keys").
- Saved per apply, under `<Desktop>\wf-changes\kbd-crash-dump\<yyyyMMddTHHmmssZ>-apply` (or `-EvidenceRoot`): `before-values.csv` (role, mode, key, name, whether the key and the value existed, kind, data, target), one `.reg` per change key (the parent service key when the subkey does not exist yet, which records its absence), `SHA256SUMS.txt`, and `log.txt` with every printed line. `-Undo` writes the same set as `<time>-undo` before it restores. Just before its first write each run adds `writes-begun.txt` to its folder (and refuses, nothing changed, if it cannot); a folder without it is from a refused run, and `-Readback` never counts it as a change.
- Writes go through `Microsoft.Win32.RegistryKey` in the 64-bit view: the parent is opened for writing and must exist, `CreateSubKey` opens or creates the leaf, `SetValue` writes a REG_DWORD, `DeleteValue` removes one, and a key the apply created is removed with `DeleteSubKey` only when it holds no values and no subkeys again ([RegistryKey](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey), [DeleteSubKey](https://learn.microsoft.com/dotnet/api/microsoft.win32.registrykey.deletesubkey)). The only process it starts is `reg.exe export <key> <file> /y` from the system directory, whose exit code is 0 on success and 1 on failure ([reg export](https://learn.microsoft.com/windows-server/administration/windows-commands/reg-export)).
- `-Readback` also compares the last boot time (`Win32_OperatingSystem.LastBootUpTime`, [Win32_OperatingSystem](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-operatingsystem)) with the newest apply or undo folder that holds `writes-begun.txt`, and says whether the restart Microsoft requires has happened.

## Facts to verify on the PC

The script passes PSScriptAnalyzer's Windows PowerShell 5.1 compatibility rules and its logic runs against a synthetic registry, but each item below needs evidence from the PC. A row moves to "reported" only with the date and the PC session's report, never as a settled rule.

| # | Unverified | How to check at the PC | If it fails |
|---|---|---|---|
| K1 | The script runs under Windows PowerShell 5.1, elevated, as written: the guarded adapters load, `RegistryKey.OpenBaseKey(LocalMachine, Registry64)` opens HKLM, and `[Console]::Out` prints to the window. | `-Plan` prints the state and ends with `READY` or `REFUSED` with reasons, exit 0 or 1. | The error text names the adapter; nothing has changed, since `-Plan` only reads. |
| K2 | Both service keys `kbdhid` and `i8042prt` exist on this Windows 11 install, and whether their `Parameters` subkeys exist before the change. Microsoft says to "create a value" in those keys and does not say whether the keys ship with Windows. | `-Plan` lists each service key as OK and shows each `Parameters` value as `absent` or `absent (the key does not exist)`. | A missing service key refuses the change; report it, and do not create it by hand. |
| K3 | `reg export` writes a `.reg` file for each key, run elevated, into the desktop folder, and exits 0. | After `-Apply`, the apply folder holds the `.reg` files and `SHA256SUMS.txt` lists them. | `-Apply` refuses with the exit code; nothing changed. |
| K4 | The values take effect after one restart, as Microsoft documents, and stay in place across later boots (nothing on this PC rewrites them at startup). | `-Readback` after the restart: `PASS` on every value and `Restart done`. | A value back at its old state after a boot means something rewrites it; stop and report, do not re-apply in a loop. |
| K5 | The keyboard the captain uses during play is driven through `kbdhid` (a USB HID keyboard, including through a wireless receiver) and not only through a vendor driver, so the sequence reaches the documented handler. Learn documents USB keyboards through `kbdhid` and PS/2 through `i8042prt`, nothing about receivers, Bluetooth or vendor filter drivers. | Only a stop error proves it: after a keyboard crash, the System log holds `WER-SystemErrorReporting` 1001 with bug check 0x000000e2. | No stop code after the sequence: report it; the alternate keys do not help a keyboard the driver never sees. |
| K6 | The sequence works during this PC's hard freezes. Learn documents that it does not work when the machine stops responding at a high IRQL and is silent about graphics hangs. | A freeze ended with the sequence leaves 0xE2 in 1001 and in Event 41's `BugcheckCode` (226 in decimal). | A freeze where the keys did nothing, reported as such, is evidence that the hang blocks the keyboard path. |
| K7 | A dump is written and fits: `CrashDumpEnabled` is nonzero, but whether the page file holds the dump on this PC is unproven. | 1001 says "A dump was saved in" and that file exists with a stable size. | A 0xE2 with no dump: keep the records of that boot and change nothing; the page file is the lead. |
| K8 | With `-AlternateKeys`, the default `Dump2Key` 0x3d is the spacebar on this PC's keyboard layout, as in Microsoft's example ("the spacebar twice"); Microsoft describes `Dump2Key` as an index in the scan code table "for the keyboard layout of the target computer". | Only a stop error proves it, as for K5. | Undo and keep the default sequence on a keyboard with SCROLL LOCK. |
| K9 | `Win32_OperatingSystem.LastBootUpTime` read through `Get-CimInstance` converts to the correct UTC instant, so `-Readback`'s restart line is right. | After the restart, `-Readback` says `Restart done` with a boot time a few minutes before the run. | The line is advisory only; the values themselves are read directly. |
| K10 | The profile path redaction catches every printed path: the evidence root under the desktop prints as `<profile>\Desktop\...`. | Read the `-Plan` output for the account's folder name. | Report it before sharing any output. |
| K11 | The default evidence root, `[Environment]::GetFolderPath('Desktop')` in the elevated window, is the desktop of the account that opened it, so the captain finds the folders where the operator page says. With other credentials typed at the elevation prompt it would be that account's desktop (inference). | After `-Apply`, the `Saved:` line names `<profile>\Desktop\wf-changes\kbd-crash-dump\...` and the folder is on his desktop. | Pass `-EvidenceRoot <folder>` to every verb, including `-Undo` and `-Readback`. |

## Testing

```
scripts/fetch_pwsh.sh                                  one time: PowerShell 7, Pester and PSScriptAnalyzer into tools/
pytest tests/test_change_kbd_crash_dump.py             static checks, the Pester suite, and the real adapters off Windows
tools/pwsh/pwsh -NoProfile -File changes/windows/tests/Invoke-Checks.ps1 -ModulePath tools/psmodules
```

- `tests/KbdCrashDump.Synthetic.ps1` replaces the adapters with an invented registry, reg export, identity, clock and boot time; `tests/KbdCrashDump.Tests.ps1` runs the real script against it: every verb, every precondition, export failures (exit code and a missing file), an evidence folder that cannot be created, a value that moves during the save, a failed write followed by an undo that restores the exact before-state, a readback mismatch, a tampered or foreign CSV, a value changed by something else before an undo, a key the apply created and the undo removes or keeps, and the alternate keys.
- `tests/test_change_kbd_crash_dump.py` checks the isolation rule above, the ASCII rule, that the script holds no forbidden command (prompts, restarts, services, scheduled tasks, downloads, interop) and starts no process but `reg.exe export`, that it names only the documented keys and values, runs the Pester suite when `pwsh` is present, and runs the unmodified script as a process off Windows, where every adapter fails and it must refuse without writing anything.
