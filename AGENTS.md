# Project agent memory

win-forensics: capture, decode, and correlate Windows performance evidence. Read `README.md` first; it names the four contracts under `docs/contracts/` and the build order the repository follows (phase 0a is done, and the read only history collectors for the gaming PC, three live captures, `dpcisr-trace`, `presentmon-frames` and `diskio-trace`, and the clock calibration session, `clock-calibration`, are in `collectors/windows/`; the other live capture collectors, decoders for the other tables, analyzers, and the correlator come in later phases and must be built against the contracts, not around them).

## Working rules that are not obvious from the code

- Measurement status and evidence never share a field. A collector that did not run produces no evidence row, not even an absence row; see `docs/contracts/measurement-status.md` section 3 before writing any analyzer or validator logic.
- Every decoded row and every observed evidence row carries the structured provenance object from `schemas/decoded/provenance.schema.json`. Decoders self validate their rows with `scripts/wf_schema.py` before writing; keep that pattern.
- Schemas are hand maintained JSON under `schemas/`, registered by `$id` (see `wf_schema.load_schemas`). Bump `x-schema-version` and the matching `const` in the table's provenance pin together; `tests/test_schemas.py` checks the pin.
- The example bundle under `fixtures/example-bundle/` is regenerated, not edited: run the two decoder commands in `README.md` with `--decoded-at 2026-09-03T00:00:00Z` after changing a decoder, or `tests/test_decoders.py` fails on the stale comparison. `manifest.json`, `verdict.json`, and `evidence.jsonl` there are hand written examples; the tests cross check them against the decoded tables.
- Win-opt (the captain's earlier toolkit, registered read only) is tooling history. Its recorded files are format fixtures only; its findings, numbers, driver names, and causes never appear in prose, schemas, scripts, or tests (`tests/test_docs.py` enforces a denylist). Thresholds cite Microsoft or tool documentation.
- Documents are plain prose with no em or en dashes (also enforced by `tests/test_docs.py`).
- Nothing captured from a real machine is committed; `.gitignore` excludes bundles, captures, and trace, dump, and log extensions. Only `fixtures/` holds synthetic bundles and format fixtures.

## Collectors that run on the PC

`collectors/windows/README.md` is the authority: the interface shared with the SSH dispatcher, what each collector reads with its Microsoft citation, how status is decided, what needs elevation, and the list of facts nobody has verified on Windows yet. Who may run what on the captain's PC: development agents (any session building or reviewing this repository, on the Mac or elsewhere) never run anything against it. Collectors run on the PC only when the captain has directed it (he did on 2026-11-18, to help diagnose and fix the latency issue), and then only the read only, passive collectors from a pinned commit of this repository, using a checkout or that commit's GitHub source ZIP, with the full commit ID and any source ZIP's SHA-256 recorded in run notes that identify the resulting bundles, started by the captain or by the agent session on that PC acting on that direction. Nothing that changes the machine (settings, drivers, registry, interrupt affinity, power, services, scheduled tasks, timers) runs without the captain's explicit word for that specific change, with its undo recorded first. Rules that are easy to break:

- The scripts target Windows PowerShell 5.1, and the tests here only ever run them under PowerShell 7 with the Windows adapters replaced (`collectors/windows/tests/SyntheticBackend.ps1`); the one run on the PC so far (2026-11-18, reported by the PC session) is recorded on the README's verification list (item 35). A change to an adapter at the bottom of `_common.ps1` is untested by construction; add the fact it relies on, with its citation, to the README's verification list.
- Keep every `.ps1` plain ASCII (5.1 reads a file without a byte order mark in the ANSI code page), never use `ConvertTo-Json` in the helper (its default depth is 2, and Windows PowerShell writes a wrapped array as an object with `value` and `Count`, which cannot be tested here; use `ConvertTo-WfJson`), and never use `$script:` variables there (the helper is dot sourced into other files).
- A collector prints one JSON line on stdout and nothing else, stays read only, and records an unreadable source as a status with a reason, never as an empty export. `tests/test_collectors_static.py` holds the forbidden command list, the allowed `Remove-Item` targets, and the rule that the only process the helper builds itself is `wevtutil epl`; the netsh allowlist (`wlan show` listings only) is checked on what runs record, by the synthetic process recorder in `Collectors.Tests.ps1` and on the manifests in `tests/test_collector_bundles.py`.
- The helper has eleven source types (eventlog, cim, command, file, directory, registry, topology, pnp, unavailable, script, and custom); `collectors/windows/README.md` ("The config-snapshot sources", "How status is decided") defines each. A `script` source is a scriptblock the collector implements itself; a `custom` source is a function the collector script defines; `clock-calibration` is the one collector that uses it and keeps its session control (start, bounded duration, stop, the marks file lifecycle) in its own file, not in `_common.ps1`; see `docs/clock-calibration.md`. Its marks file is written by a second process (the collector's own `-Mark` mode), so the collector reads it back by exact shape and never trusts a line it did not write. Two rules to keep: `unavailable` records a question with no documented read only path as `not_collected` with its reason and no primary (a collector that uses it is `partial` by design, never papered over), and a refused or failed read is unknown, never absent. Native calls live in exactly two audited `Add-Type` blocks in `_common.ps1` (`New-WfDeviceKeyNative` for the device hardware keys through `SetupDiOpenDevRegKey` with `KEY_READ`, `Get-WfLogicalProcessorInformation` for the topology); `tests/test_collectors_static.py` pins their imports, masks and literals and bans interop everywhere else, with negative cases, so a new native read needs its own audited block, its own guard entry and a README verification item, never a widening of these. Everything that could carry free text goes through a `Protect-Wf*` function before it is written (netsh text, event records, copied files and the helper command line through `Protect-WfCopiedText`, Bluetooth peer rows) or stays out; the README's "What a bundle contains" lists the rules. Helper functions must not be called from scriptblock closures (`GetNewClosure`), which cannot see them under Pester, and an ordered map must not pass through a `[hashtable]` parameter (it loses its order).
- Event query time bounds are `@SystemTime` comparisons with ISO 8601 UTC literals at millisecond precision, built only by `Build-WfEventQueryXml`. The documented `timediff(@SystemTime, <FILETIME>)` form failed on the gaming PC at the first read (README verification item 35), and the synthetic backend models that failure, so the Pester suite fails if the form comes back. A fact observed on the PC goes on the README's verification list with its date and "reported, not reproduced" status, never as a settled rule.
- `presentmon-frames.ps1` is the second `script` source and the pattern for a live capture that runs an operator supplied binary: the recording control (pinned binary check, wpr start, window, status, stop and cancel, the offline PresentMon read) stays in the collector, the helper only dispatches, and any process it starts goes through the helper's one runner (`Invoke-WfProcess`). PresentMon never runs live there (its realtime mode opens a handle to every presenting process, settled from its source at the pinned tag); it only reads the recording with `--etl_file`. Every wpr call ends in `-instancename wf-presentmon-frames` (the collector never probes, stops or cancels another recording), any loss from any counter is `capture_failed`, zero frames is never a quiet window, and the recording is deleted on the PC (a merged WPR trace can carry network adapter addresses); the bundle carries the CSV and `recording.json`. The pinned release, hash, provider list and citations live in the collector and `collectors/windows/README.md`; what the collector passes to wpr and PresentMon (only the offline options, the four wpr verbs, the instance name on every call, never a live option) is checked on the recorded runs in `tests/test_collector_bundles.py` and on every process the Pester suite's runs start. The one `.etl` git keeps is `fixtures/presentmon/gold-test_case_0.first-buffer.etl` (an explicit `.gitignore` exception): the first buffer of a PresentMon regression recording, the format fixture the log file header reader and the synthetic recording are checked against.
- `netsh` and `powercfg` output is localized: the decoders (`scripts/decode_rf_survey.py`, `scripts/decode_config_snapshot.py`) name fields by English label and otherwise by the shape of the value (a GUID, a hex index, the order powercfg prints AC before DC); `docs/rf-survey.md` is the authority for what the RF survey can and cannot prove.
- `dpcisr-trace` is the kernel trace live capture. Its session control (start, wait, status, stop, cancel, confirm, all under its own `-instancename`) stays inside that script as `script` sources; do not move it into `_common.ps1` until the later runner unifies live sessions. The kernel trace never leaves the machine (it carries hardware and network addresses in its configuration events): it lives under the output directory's `private` folder, is read there, and the definition's `Cleanup` removes it on every exit path. The profile requests Interrupt, DPC and Loader only; process, thread and scheduling keywords carry command lines and user ids and need the owner's decision first. Loss figures are read from the tool texts as whole numbers or null, never zero, and the trace is `observed` only when the final figures (tracerpt summary) are zero; the README section "The dpcisr-trace sources" states the privacy statement, the status rules and the three per CPU paths. Tools that are not inbox (xperf) run only from an operator supplied path whose hash and version match `Get-WfPinnedToolBuilds`, hashed again after the run; no build is pinned yet. In PowerShell, `(Test-WfX -Status $s -or $y)` passes `-or $y` to the function as arguments: always parenthesise the call before a logical operator; and `@(f)` where `f` returns `, $array` nests the array, so assign such returns without `@()`.
- The JSON writer in the helper enumerates a map through its enumerator, never `.Keys`: PowerShell resolves `$map.Keys` to an entry named `keys` when one exists. Never pipe or wrap `Get-WfList` in `@()` (it returns a wrapped array; assign it first), and keep `keys`, `values` and `count` out of entry names you address with dot syntax.
- `diskio-trace` is the third kernel live capture and follows the `dpcisr-trace` rules (own instance, session control local in `Start-/Test-/Wait-/Stop-/Confirm-DiskIoSession*`, private folder removed on every exit path). It also deletes the `tracerpt` XML dump after aggregating it on the PC; only `aggregate.jsonl`, the pseudonym rules and the hashes leave. The reader takes `ProcessId` and `ImageFileName` from Process events and never reads `CommandLine` or `UserSID` (the synthetic dump carries both and the bundle tests check neither leaves); a directory keeps one readable level below a fixed root, `<profile>` for the user folder, salted `dir-` pseudonyms deeper. It runs alone until README item 68 (two kernel instances at once) passes; zero disk events is `capture_failed`, never a quiet window.
- After changing a collector or the helper, regenerate `fixtures/collector-bundles/` with `collectors/windows/tests/New-FixtureBundles.ps1`; the content is invented in `SyntheticScenarios.ps1`. `scripts/fetch_pwsh.sh` puts PowerShell 7, Pester and PSScriptAnalyzer under `tools/` (ignored), and `tests/test_collectors_pwsh.py` skips without them, so run it before claiming the collectors pass.

## Change scripts

`changes/windows/README.md` is the authority. The only code that changes the PC lives in `changes/windows/`, one self-contained script per change, and runs only by hand at the PC, elevated, on the captain's explicit word for that change (he authorized building the tooling on 2026-11-19). No agent runs one against the PC. Rules that are easy to break:

- Nothing in `collectors/` (including the helper and the scenario runner) or `remote-access/` may reference `changes/` or a change script by name; `tests/test_change_kbd_crash_dump.py` scans for it. Collectors stay read only with their forbidden command list unchanged, and a change script never dot sources `_common.ps1`.
- Verbs: `-Plan` is the default and only reads; `-Apply` prechecks, saves (values CSV, `reg export` per affected key, `SHA256SUMS.txt`) and refuses if any of that fails, re-reads, writes, and reads back PASS or FAIL per value; `-Undo` restores exactly the saved before-state (absent means delete) after checking the CSV hash and that only documented keys are named; `-Readback` only reads. Nothing prompts, nothing restarts, no persistent elevation. A precondition on an unexpected value is a guard: it stops the script, it is never relaxed to let a change through.
- The real Windows adapters sit in one guarded block at the bottom of each script (skipped when the test backend already defines them); the Pester suite under `changes/windows/tests/` covers every apply, undo and readback path including failures. Facts only the PC can show go on that README's "Facts to verify on the PC" list with their own id prefix (`K` for `kbd-crash-dump`). Check runner: `changes/windows/tests/Invoke-Checks.ps1`; run pwsh with stdin closed (`< /dev/null`), or it can stall.

## Process Monitor facts to rely on

Settled on the GitHub hosted Windows runner with committed fixtures; read `docs/contracts/procmon-facts.md` before touching anything Process Monitor related. Short form: only `/Runtime` bounds a run and its expiry exits with code 1; stack capture is unconditional and has no `.pmc` setting; the CSV column set is exactly the loaded configuration's column selection in its order, `TID` and `Duration` appear only when selected, `Sequence` is `n/a` in exports, stacks are XML only; configuration is sticky in the registry, so always pass `/LoadConfig`. The committed `.pmc` files come from `scripts/make_procmon_pmc.py` (needs the `procmon-parser` dev extra).

## SSH front door

`remote-access/README.md` is the authority for the path from the captain's Mac to the PC: the setup script's steps with their citations, the dispatcher's verbs, exit codes and transfer framing, where it departs from the plan, and the facts nobody has verified on Windows. No agent, development or on the PC, runs any of it against the PC: the setup changes the machine (sshd, the firewall, an account), so it stays the captain's own action at the PC, by the checklist. Rules that are easy to break:

- `dispatch.ps1` takes no parameters, reads no variable but `SSH_ORIGINAL_COMMAND`, and compares the client's string against an exact allowlist; it never evaluates it or hands it to a shell. `remote-access/tests/Dispatch.Tests.ps1` checks this by running it as sshd would, with injected requests, arguments, and environment variables.
- The wire protocol has four readers that must change together: `dispatch.ps1`, `mac/wf-fetch.sh`, `mac/wf-acceptance.sh`, and the stand-in `ssh` in `tests/test_remote_access.py`. The outbox directory name travels as `bundle_dir`; the `bundle_id` in a bundle's manifest is the authoritative id and can differ.
- The setup script's result is PASS, INCOMPLETE (a verification could not run; exit 2; no Mac handoff), or FAIL (exit 1). Firewall and sshd failures fail closed: sshd stopped and set to manual start. Keep that shape; a warning never stands in for a check that did not run.
- Every setup step id (`S1`...) needs a row in `CHECKLIST.md` under "If a step fails", and every acceptance check (`A1`...) an explanation there; a test enforces both. A new assumption about Windows goes on the README's "Not verified off Windows" list with a step that proves it on the PC.
- The Windows scripts target Windows PowerShell 5.1 and have only run under PowerShell 7 here: keep them ASCII, write files sshd reads without a byte order mark (`Write-WfTextFile`), collect function output with `@(...)` before `ConvertTo-Json`, and format dates with the invariant culture. `pytest tests/test_remote_access.py` skips the Pester suite and the analyzer when no `pwsh` is found (`$WF_PWSH`, `PATH`, `tools/pwsh`), so make sure they ran before claiming the scripts pass.
- The captain facing flow is three actions (`mac/wf-start.sh`, double click `windows/SETUP-PC.cmd`, `mac/wf-finish.sh`) that only orchestrate the scripts above; keep new behaviour in the underlying script and the entry points thin. The launcher travels with the kit and cannot vouch for it, so the transport decides the path: the double click is allowed only from a drive Windows reports as Removable, and `wf-finish.sh` trusts `pc-host-key.pub` only from a folder that, resolved with `pwd -P`, sits on a `/Volumes` mount point `diskutil info` reports as External and removable or ejectable (never a network share or the boot disk; the tests stand in `diskutil` on PATH); anything else goes through Windows' own `Get-FileHash` with the full SHA-256 typed from the Mac screen and `--fingerprint` typed from the PC screen. Never weaken those two refusals into warnings, and never write the kit code or the digest into anything that travels with the kit (a test checks every file and zip member). The kit code (left-most 32 hex characters of the zip's SHA-256, 8 groups of 4) has two implementations that must agree, `wf_kit_code` in `mac/wf-common.sh` and `Get-WfKitCode` in `windows/Start-FrontDoorSetup.ps1`, checked against one oracle in `tests/test_remote_access.py`. `SETUP-PC.cmd` is the one CRLF file; the launcher loads `WfCommon.ps1` and `WfSetupLib.ps1` only from its private staging folder after the code matched, and the Pester suite must not preload them. Checklist ids: actions 1 to 3 with the router step between, L1 to L8 for the script by script appendix, S1 to S13 for the setup steps, A1 to A10 for the acceptance checks; tests enforce rows for each.
