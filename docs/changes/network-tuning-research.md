# Network tuning research for the gaming PC

This is the evidence behind `changes/windows/network-tuning.ps1`. The captain asked on 2026-11-19 to "optimize the internet settings", with a look at the registry and at what tools like SpeedGuide's TCP Optimizer change. The rule for this work: reproduce, transparently, only a setting such a tool changes that has a real, sourced case for UDP game latency or connection stability on Windows 11, and leave out anything obsolete, placebo or TCP only unless a source shows it matters here. Overwatch sends its game traffic over UDP; Battle.net and the game's login and store use TCP, which no lag report points at.

Every Windows fact below is cited to Microsoft Learn or to the vendor's own page. A claim with no such source is marked **unverified**. Forum posts and tweak guides are not evidence; SpeedGuide's pages are used only for what TCP Optimizer changes, never for whether a change helps. No tweak tool was downloaded or run for this work; Stutter Guard's source was read on GitHub at a pinned commit.

## Short answer

- **One setting goes into the script:** the adapter's `*IdleRestriction` back to 1 ("Only idle when user isn't present"), the value it had before the Realtek driver install of 19 November. It is a documented Microsoft keyword, the driver exposes it with both values, and it governs when the adapter may power down while the PC is in use. Expect a small effect at most: Microsoft documents that NetAdapterCx keeps the device powered while the interface is in use, so the case is the quiet moments, not steady play.
- **Nothing in the TCP/IP stack goes in.** Every stack setting TCP Optimizer changes is either TCP only (game traffic is UDP), read only on a Windows client, deprecated, or a documented default left as it is.
- **The properties the install reset** (Green Ethernet, Power Saving Mode, Gigabit Lite, LTR/OBFF) and Flow Control are **measure first**: Realtek publishes no description of them, so there is no cited case either way. Measure first means a guarded experiment, not a change by hand: each is an opt in entry in the script (`green-ethernet`, `power-saving-mode`, `gigabit-lite`, `ltr-obff`, `flow-control`), outside the default set, run only when named alone with `-Only`, with the same saved before-state, Undo and Readback. Each proposes the driver's own off value (the valid value it shows as "Disabled"), read live; the script refuses when the driver shows no such value, which today is the case for the hidden `LTROBFF`.
- **"Allow the computer to turn off this device"** stays out of the script: it is owned by the driver framework and has no documented way to set it from a script. The operator page gives the Device Manager steps for it as a separate experiment by hand.
- **Values already on the PC that tweak guides set** (the Nagle trio on five interfaces, NetworkThrottlingIndex 10, SystemResponsiveness 10, NoLazyMode, Psched NonBestEffortLimit 0, a Fortnite DSCP rule) are **present and left alone**: none has a cited harm for UDP game traffic, and restoring a placebo value earns no place in the script.

## Stutter Guard

Read on GitHub at commit `8c783a478f4b511c273b3235bf745b5d64550f49` (`src/DpcTweaker.Core/Tweaks/Network.cs`, `Interrupts.cs`, `DevicePower.cs`, `BootTasks.cs`, `Power.cs`, `UI/InterruptsPanel.cs`), nothing run. It never touches the TCP/IP stack: no `Tcpip` parameters, no netsh, no Nagle values, no `NetworkThrottlingIndex` or `SystemResponsiveness`, no QoS, no DNS, IPv6 or MTU; its own Network screen lists those as "left alone". It does touch the adapter:

- **Advanced properties** in the adapter's driver key, by default on desktops: `*EEE`, `AdvancedEEE`, Green Ethernet, Gigabit Lite, `AutoDisableGigabit`, `PowerSavingMode`, `*SelectiveSuspend`, `*DeviceSleepOnDisconnect`, `*FlowControl` (marked anecdotal), `*InterruptModeration`, and the hidden Realtek `ASPM` and `CLKREQ`; then it restarts the adapter. On this PC its journal shows only `*InterruptModeration`, `ASPM` and `CLKREQ`, each recording 0 as the value before its change, so their 0 came from elsewhere (possibly the FoxOS image; **unverified**).
- **RSS keywords** aligned to the NIC interrupt cores, **interrupt affinity** (CPU 10 for this NIC, later 12 to 15 by another tool) and **MSI mode**: step 4a's, not this script's.
- **Device power:** sets `PnPCapabilities` 24 in every physical adapter's driver key and a WMI power flag, and registers a boot task that does it again at every boot. On this PC `PnPCapabilities` is 24 both before and after the install, yet "allow turn off" is Enabled on the new driver, so `PnPCapabilities` does not appear to govern that box for this NetAdapterCx driver (an observation, **unverified**). The task belongs to step 4b.

## Overlaps with other steps

- **Step 4a (NIC interrupt affinity) owns:** the NIC's `Affinity Policy` key (now present with no values; whether the install cleared it is unknown), `MessageSignaledInterruptProperties` with `MessageNumberLimit` 1, and any RSS processor keywords.
