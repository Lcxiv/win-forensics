## Fact (a): can a maximum backing file size be set from the command line?

No. There is no switch that caps the size of a sequential backing file. What exists:

- The documented switch list. Microsoft Learn's Process Monitor page carries no command line reference; the "Troubleshoot Apps failing to start using Process Monitor" article says "other options are available, including filtering and setting the maximum file size" and shows the `Process Monitor Usage` dialog as a screenshot. That dialog lists `/OpenLog`, `/BackingFile`, `/PagingFile`, `/NoConnect`, `/NoFilter`, `/AcceptEula`, `/LoadConfig`, `/Profiling`, `/Minimized`, `/WaitForIdle`, `/Terminate`, `/Quiet`, `/Run32`, `/Runtime`, `/HookRegistry`, `/SaveAs`, `/SaveAs1`, `/SaveAs2`, `/SaveApplyFilter`, `/EnableBootLogging`, `/ConvertBootLog`, `/RingBuffer`, `/RingBufferSize <size>` (ring buffer size in MB), `/RingBufferLen <len>` (ring buffer length in minutes), and `/Altitude`. The UTF-16 strings of the 4.1 binary carry the same list and no other slash switch. The only size related switch is `/RingBufferSize`, which belongs to flight recorder mode, and the "maximum file size" the article refers to is that ring buffer.
- `/Runtime` bounds a run in seconds. The binary's own validation message reads "Runtime parameter must be between 1 and 3600 seconds." On the runner every capture with `/Runtime 10` ended by itself between 10.15 s and 10.26 s after launch with exit code 1 (`runs.json`, `exited_on_own` true for all four captures). Exit code 1 after a `/Runtime` expiry is therefore the normal outcome, not a failure.
- `/RingBuffer /RingBufferSize 1` did not bound the backing file in the configuration a collector would use. Run C with those switches plus `/BackingFile` and `/Runtime 10` wrote a 124,016,279 byte backing file and exported 300,429 events, more than run D without them (104,361,761 bytes, 252,985 events). The registry after the last run shows `FlightRecorder`, `RingBufferSize`, and `RingBufferMin` all 0, and the binary carries the message "Ring buffer will commence the next time you start a new trace", so the flight recorder appears to be a persisted mode rather than a per invocation cap; this run did not test a second launch after enabling it.
- History Depth is the event count bound. The GUI option persists as the `HistoryDepth` registry value and `.pmc` record ("The history depth limits the total number of events kept during a run" in the binary's strings). After the runs the value was 18 on this runner (`registry-after-run.json`); the committed `.pmc` files carry 200, the value an unmodified export from an earlier version carried. Its unit is not documented by Microsoft and was not tested here.

Consequences for the collector (later phase): always pass `/Runtime` (at most 3600); size the free disk preflight from the observed rate on the runner, about 10 MB of backing file per second for 26,000 events per second on an idle 4 CPU machine plus the load generator, and expect a gaming PC to be higher; treat exit code 1 after `/Runtime` as success and verify by artifact; do not rely on `/RingBufferSize` until a run that enables the flight recorder and then launches again shows it bounding the file.

## Fact (b): does the stack trace capture setting persist in an exported .pmc?

There is no stack trace capture setting to persist. Stacks are captured for every operation whether or not a configuration is loaded, and the `.pmc` carries only symbol resolution settings.

- Documentation: the Process Monitor page lists "capture of thread stacks for each operation" as a built in capability, with no option attached.
- The options that exist: the 4.1 binary's Options menu strings are Always on Top, Highlight Colors, Theme, Configure Symbols, Select Columns, History Depth, Profiling Events, Enable Boot Logging, Show Resolved Network Addresses, Hex File Offsets and Lengths, and Hex Process and Thread IDs; the Filter menu adds Drop Filtered Events. None concerns stack capture.
- The persisted settings: after the runs, `HKCU\Software\Sysinternals\Process Monitor` held 26 values (`registry-after-run.json`): `EulaAccepted`, `MainWindow`, `Columns`, `ColumnCount`, `ColumnMap`, `DbgHelpPath`, `Logfile`, `HighlightFG`, `HighlightBG`, `Theme`, `LogFont`, `BoookmarkFont`, `AdvancedMode`, `Autoscroll`, `HistoryDepth`, `Profiling`, `DestructiveFilter`, `AlwaysOnTop`, `ResolveAddresses`, `SourcePath`, `SymbolPath`, `FilterRules`, `HighlightRules`, `FlightRecorder`, `RingBufferSize`, `RingBufferMin`. An exported `.pmc` is a serialization of these values (the committed files carry the twenty that an earlier export held, and 4.1 loaded them). The only stack related values are `ResolveAddresses`, `SymbolPath`, `DbgHelpPath`, and `SourcePath`, which govern symbol resolution for display and for `/SaveAs2`, not capture.
- The runner evidence: capture A loaded `wf-default-columns.pmc`, which has no stack related record and `ResolveAddresses` 0. Its XML export with `/SaveAs1` holds 45,814 `event` elements, 45,814 `stack` elements, and 2,075,177 `frame` elements (`facts.json`, `xml_exports`; head in `A_default_filtered_stacks.head.xml`). procmon-parser read `A.pml` directly and found stack frames on 4,768 of the first 5,000 events with a maximum depth of 86 (`facts.json`, `pml_files`); the remainder carried an empty frame list.

Consequences: the collector does not need to persist anything for stacks; it needs `_NT_SYMBOL_PATH` or the `SymbolPath` record only if it will resolve them, and it exports stacks with `/SaveAs1` (addresses) or `/SaveAs2` (symbols) to XML, never to CSV.

## Fact (c): the exact column set of a /SaveAs CSV export

The CSV export carries exactly the columns selected in the loaded configuration, in the configuration's order. With the default seven (`A_default_filtered.head.csv`, `A_default_unfiltered.head.csv`):

```
"Time of Day","Process Name","PID","Operation","Path","Result","Detail"
```

With every column selected (`B_allcolumns_filtered.head.csv`; `C_ringbuffer_unfiltered.head.csv` and `D_plain_unfiltered.head.csv` show the same set, see the note on persistence below):

```
"Sequence","Time of Day","Date & Time","Relative Time","Duration","Completion Time","Process Name","PID","TID","Parent PID","Operation","Path","Result","Detail","Event Class","Category","Image Path","Command Line","Company","Description","Version","User","Session","Authentication ID","Integrity","Architecture","Virtualized"
```

So, for the three questions the plan asked:

- Thread id: present as `TID` only when the configuration selects it.
- Duration: present only when selected; seconds with seven decimals (for example `0.0000041`); over the first 2,000 rows of export B it equals `Completion Time` minus `Time of Day` to the last digit.
- Sequence: present as a column when selected, but every value in a `/OpenLog` export is the text `n/a` (51,248 of 51,248 rows in export B).
- Stacks: never in a CSV export, with any column set. XML with `/SaveAs1` or `/SaveAs2` is the only export that carries them.

Formats observed on the en-US runner, all verified across every row of export B:

| Column | Format | Example |
|---|---|---|
| `Time of Day` | `h:mm:ss.fffffff AM` or `PM`, seven fractional digits (100 ns), no date | `9:38:09.6183153 PM` |
| `Date & Time` | `M/d/yyyy h:mm:ss AM` or `PM`, 1 s resolution | `9/3/2026 9:38:09 PM` |
| `Relative Time` | `hh:mm:ss.fffffff` from the first event of the log | `00:00:00.0043033` |
| `Completion Time` | same as `Time of Day` | `9:38:09.6183194 PM` |
| `Duration` | seconds, seven decimals | `0.0000041` |
| `PID`, `TID`, `Parent PID`, `Session` | decimal integers | `3976` |
| `Event Class` | text (`File System`, `Registry`, `Process`, `Network`, `Profiling`, and the 4.1 binary also lists `IPC`) | `File System` |
| `Category` | text, may be empty | `Read Metadata` |
| `Integrity`, `Architecture`, `Virtualized` | text | `High`, `64-bit`, `False` |

Consequences for the `procmon_events` table (see [decoded-tables.md](decoded-tables.md) section 5.11): the seven default columns are required, every other column is optional and present only when the committed `.pmc` selects it, `sequence` decodes `n/a` to null, `time_of_day` is kept verbatim and `time_utc` is derived from it with the date from `Date & Time` when that column is present or from the sidecar otherwise, and stacks come from a separate XML decode.

## Other facts the run settled

- `/LoadConfig` works for both capture and `/OpenLog` export, and `/SaveApplyFilter` applies the loaded filter: the filtered export of A holds 45,814 rows, all under the load path prefix, out of 260,225 events in the log; without `/SaveApplyFilter` the export holds all 260,225.
- Configuration is sticky. Runs C and D loaded no configuration yet exported 27 columns, because run B's column selection had persisted in the registry; the registry after the runs shows `ColumnCount` 27 and `Logfile` pointing at run D's backing file. A collector must pass `/LoadConfig` on every capture and every export and must record the configuration hash, because the machine's registry state is not under its control.
- Non destructive filtering keeps every event in the backing file (`DestructiveFilter` 0): 260,225 events in `A.pml` against 45,814 matching the filter.
- procmon-parser 0.3.13 parsed `A.pml` (260,225 events) but failed on `B.pml`, `C.pml`, and `D.pml` with `6 is not a valid EventClass`; event class 6 is the `IPC` class the 4.1 binary names. A `.pml` decoder in a later phase needs that enum extended or a different reader.
- `Process Monitor` itself produced 175,588 of the 260,225 unfiltered events in run A (registry queries under `HKLM\System\CurrentControlSet\Control\WMI\Security`), which is why the committed filter excludes `Procmon64.exe` and `Procmon.exe` and why the collector's expectation is stated on filtered rows.

## Re-running

Trigger the workflow by hand (`workflow_dispatch`) or by pushing a change to it, the harness scripts, or the `.pmc` files. Download the `procmon-facts` artifact, then copy `out/fixtures/*` over `fixtures/procmon/` and re-read this document against `facts.json`. The full CSV and XML exports stay in the artifact (30 MB compressed) and are never committed; the backing files are excluded from the artifact.

## Not settled here

1. Whether `/RingBufferSize` bounds the backing file once flight recorder mode is already enabled from a previous run. Needs a run that launches twice.
2. The unit and default of `HistoryDepth` (18 on this runner after the runs; 200 in the committed configurations). Needs a run that sets a small value and counts events.
3. Whether an export from the 4.1 GUI adds `Theme`, `FlightRecorder`, `RingBufferSize`, `RingBufferMin`, or `MainWindow` records to the `.pmc`. The twenty record layout loaded fine, which is what the collector needs.
