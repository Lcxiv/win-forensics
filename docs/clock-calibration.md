# Clock calibration and operator marks

Status: version 1.0.0. Serves [docs/contracts/timestamps.md](contracts/timestamps.md) sections 3 and 4; the collector is `collectors/windows/clock-calibration.ps1`, the Mac side fit is `scripts/decode_clock.py`, and the tables are sections 5.17 to 5.19 of [docs/contracts/decoded-tables.md](contracts/decoded-tables.md).

## 1. What this piece is for

Every instrument in a bundle stamps time with its own clock: the kernel trace and PresentMon with the performance counter, counters and event logs with the system clock. The timestamp contract makes the performance counter (QPC) the master clock and asks for calibration pairs, readings of both clocks taken together, so that a system time stamp can be placed on the master clock with a known error bound. Nothing produced those pairs until now. This piece records them for a bounded session, fits the contract's model on the Mac, and refuses any join that the calibration cannot support.

It also gives the person at the PC a way to say "I felt it here" without touching the game: a mark command run in a second console that stamps the moment with the performance counter and appends it to the session's marks file. A mark sits on the master clock on its own, because it carries the same counter the kernel trace stamps events with.

## 2. What the collector records

`clock-calibration.ps1 -OutputDirectory <dir> [-DurationSeconds 120]` runs one bounded session and writes a bundle with two sources.

`clock_calibration` takes a pair in one thread, in the order the contract fixes: a performance counter reading, the system time as a Windows file time, and a second counter reading. It does so at the start, every 5 s strictly inside the session, and at the stop. Each pair is one line of `raw/clock_calibration/samples.jsonl` (the primary artifact) and one element of `calibration.pairs` in the manifest; the two must agree, and the decoder checks that they do. `session.json` records the parameters, the frequency, the APIs used with their citations, the method and the instant after which the session cannot still be running; `result.json` records the pairs taken, any slot missed, how many pairs were taken at a clock edge (section 3), the largest clock step seen and any failure.

`operator_marks` is the marks file. The session creates `raw/operator_marks/marks.open.jsonl` empty right after the start pair and renames it to `marks.jsonl` right after the stop pair, or right after the session fails, so a mark can only land between the two. Each line is a mark: label, counter bracket, file time, process id of the mark command.

The manifest's `calibration` section carries the clock source's own status, the frequency, the expected and missing pair counts, the pairs, and `time_adjustment` with both members null (section 4). `scenario.marks` lists the marks with their label, UTC time and counter value, and `scenario.requested_duration_s` is the session length.

## 3. How the clocks are read from Windows PowerShell 5.1

Nothing is installed and nothing is compiled. The collector uses what the .NET Framework exposes to Windows PowerShell 5.1:

| Reading | Call | What Microsoft documents |
|---|---|---|
| Performance counter | `[System.Diagnostics.Stopwatch]::GetTimestamp()` | "For managed code, the System.Diagnostics.Stopwatch class uses QPC as its precise time basis" and its `Frequency` field and `GetTimestamp` method "can be used in place of the unmanaged Windows APIs QueryPerformanceFrequency and QueryPerformanceCounter" ([Acquiring high-resolution time stamps](https://learn.microsoft.com/windows/win32/sysinfo/acquiring-high-resolution-time-stamps), [Stopwatch](https://learn.microsoft.com/dotnet/api/system.diagnostics.stopwatch)) |
| Counter frequency | `[System.Diagnostics.Stopwatch]::Frequency` | Same pages; the frequency "is fixed at system boot and is consistent across all processors" ([QueryPerformanceFrequency](https://learn.microsoft.com/windows/win32/api/profileapi/nf-profileapi-queryperformancefrequency)) |
| Is it the high resolution counter | `[System.Diagnostics.Stopwatch]::IsHighResolution` | True when the timer "is based on a high-resolution performance counter" ([IsHighResolution](https://learn.microsoft.com/dotnet/api/system.diagnostics.stopwatch.ishighresolution)); the collector refuses the session when it is false, because its counter values would then not be the counter ETW uses |
| System time | `[DateTime]::UtcNow.ToFileTimeUtc()` | A Windows file time, "the number of 100-nanosecond intervals that have elapsed since 12:00 midnight, January 1, 1601 A.D. (C.E.) Coordinated Universal Time" ([ToFileTimeUtc](https://learn.microsoft.com/dotnet/api/system.datetime.tofiletimeutc)); the resolution of `UtcNow` "depends on the system timer, which depends on the underlying operating system. It tends to be between 0.5 and 15 milliseconds" ([DateTime.UtcNow](https://learn.microsoft.com/dotnet/api/system.datetime.utcnow)) |
| Boot time, time zone | `Win32_OperatingSystem.LastBootUpTime`, `[System.TimeZoneInfo]::Local` | Already read by the shared helper for every bundle |

The system clock advances in steps. A reading taken at a random instant can therefore lag the true time by up to one step, and the step's size is not a constant: Microsoft documents that a process's timer resolution request "no longer affects global timer resolution" since Windows 10 version 2004, and that since Windows 11 a process that is "fully occluded, minimized, or otherwise invisible or inaudible to the end user" is not guaranteed a higher resolution than the default ([timeBeginPeriod](https://learn.microsoft.com/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)). So the step the collector's own process sees may differ from the game's, and may change when the person switches to the second console to type a mark. The collector does not estimate it. Instead it takes every pair at a clock edge: it reads the clock in a loop bounded by 100 ms of the counter until the value changes, and keeps the counter read before the last unchanged reading as `qpc_before` and the one after the changed reading as `qpc_after`. The instant the clock took its new value lies inside that bracket, so the pair's uncertainty is the bracket (half its width plus one tick), whatever the step size; the size of the change is recorded with the pair (`edge` true, `step_100ns`) as data. When the clock does not change within the budget, the last plain reading is kept with `edge` false and the fit adds an increment term for it (section 5). The loop is a busy wait of at most one clock step per pair, twenty five times in a two minute session; it reads two clocks and nothing else.

The counter the mark command reads in its own process is the same counter: Microsoft states that "the performance counter results are consistent across all processors in multi-core and multi-processor systems, even when measured on different threads or processes", with a one tick ordering ambiguity between threads, and the WNODE_HEADER page states that an ETW event's QPC time stamp "is equivalent to the value returned from the QueryPerformanceCounter API". Both citations are in the contract.

## 4. The deviation from the contract's named APIs, and why

The contract names `GetSystemTimePreciseAsFileTime` for the system time reading and `GetSystemTimeAdjustment` for the adjustment record. Both are Win32 functions with no .NET Framework wrapper; calling them from Windows PowerShell 5.1 means compiling a P/Invoke declaration with `Add-Type`, which `tests/test_collectors_static.py` forbids in every collector (it runs text as code, and the compiler writes temporary files outside the output directory, which a collector never does). The decision, recorded in the PR that added this piece, is to keep that rule, so:

- The system time is the coarse `[DateTime]::UtcNow`, read at its edges as section 3 describes, so the pairs are as exact as their counter brackets. The clock's step is recorded with every pair; a pair without an edge carries the larger of the largest step seen in the session and the 15.625 ms period of the 64 Hz PC real time clock (the "PC RTC" row of the clock table in [Acquiring high-resolution time stamps](https://learn.microsoft.com/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)). The larger of the two is taken because the step can change during a session, as section 3 cites from [timeBeginPeriod](https://learn.microsoft.com/windows/win32/api/timeapi/nf-timeapi-timebeginperiod), so a smaller step seen at another pair does not bound the one at this pair.
- Both members of `time_adjustment` are null in the manifest, with the reason in `enabled.options.time_adjustment`. The adjustment record was diagnostic only: a system time step shows up in the fit as a segment whose rate is far from nominal, and the fit flags it (section 5).

The contract's text has been amended where it named these APIs so that the contract and the collector agree ([timestamps.md](contracts/timestamps.md) sections 2 and 3). The same sections, and [measurement-status.md](contracts/measurement-status.md) section 2, carry the clock calibration exception decided with the same PR: interval slots strictly inside the session (a slot on the stop instant is the stop pair, so a 120 s session expects 25 pairs, not the general formula's 26, whose last two pairs would be microseconds apart and flag a clock step on every run); a calibration with two or more pairs is `observed` with every pair not taken, the stop pair included, counted in `missing_pairs` and the expectation reported unmet; fewer than two pairs are `capture_failed`; and the widened bound of a clock step segment is the larger of its file time span and its elapsed counter span, with the file times a backward step made the clock show twice refused in the other segments.

## 5. The fit on the Mac

`python scripts/decode_clock.py --bundle <bundle>` writes three tables and prints the model. A run replaces this decoder's earlier outputs: a table it does not write on this run is removed, so a failed rerun never leaves an observed sidecar behind.

- `clock_pairs`: one row per pair, verbatim values plus the pair's half width: `ceil((bracket / 2 + 1 tick) * 10^7 / frequency)` in 100 ns units, the contract's bracket uncertainty, and whether the pair was taken at a clock edge with the step the clock made there.
- `clock_segments`: one row per pair of consecutive pairs, the contract's piecewise model for `system_time` sources. The rate is the counter span over the file time span; `rate_deviation_ppm` compares it with the nominal `frequency / 10^7`. The bound is the larger half width of the two pairs, plus the increment term (zero for two edge pairs, else the larger of the largest step seen and the 15.625 ms default, since the step can change during a session), plus the largest interior residual (zero between consecutive pairs). A deviation more than 1000 ppm above what the two pairs' own uncertainty can explain (`quantisation_limit_ppm`, two times the increment term plus the larger half width, over the span) marks the segment `clock_step`, so a pair with a wide counter bracket is not reported as a step of the system clock while its half width still widens the bound: `step_kind` says whether the system clock gained (`forward`) or lost (`backward`) time against the counter, and the bound also carries the larger of the file time span and the elapsed counter span, so a backward step, which shortens the file time span, never shrinks a bound. For a backward step the row also gives the range of file times the clock may have shown twice, from the segment's first file time minus the lost time to that file time plus the counter span, with the first pair's own uncertainty (its half width, plus its increment term when it is not an edge pair) added on both ends. A source adds its own resolution (1 ms for a PDH CSV, 100 ns for an event log record) to get its `e_S`. The master epoch is the first pair's `qpc_before`.
- `operator_marks`: one row per mark with its counter midpoint and half width; the table's domain is `etw_qpc`.

The same module is the library a later correlator calls: `load_model(bundle)` returns the model or the reason there is none; `model.align(filetime, source_resolution)` returns master time with its bound, or says the stamp is outside every pair (never extrapolated), or that it is a file time a backward step made the clock show twice, which the segment it falls in would otherwise place with a bound that does not cover the step; `model.align_qpc(qpc)` and `model.align_mark(before, after)` place counter values; `check_join(id, left, right, tolerance, left_alignment, right_alignment)` applies section 5 of the contract and returns the record the verdict's `joins` list wants. A join is refused when either side is unaligned or `e_left + e_right` exceeds the tolerance; the tolerance is never widened and the bound is never rounded down.

Two things the sidecar says that a reader should check before trusting a segment: `quantisation_limit_ppm` is how far off nominal the two pairs' own uncertainty can push a segment's rate (two times the increment term plus the larger half width, over the span); the clock step rule allows for it, so when it is above 1000 ppm a clock step smaller than that allowance goes unflagged there, and the only honest answer is the wider bound those terms already give. And `expected_pairs` shows how many slots were missed and whether the stop pair exists; a missed slot makes the segment around it twice as long and its bound no wider (section 4.5 of the contract), and a missing stop pair leaves every file time after the last pair unaligned.

A calibration whose source is not `observed` (fewer than two pairs, a managed timer that is not the high resolution counter) is never fitted; the clock tables are `not_collected` and every alignment through it is refused with that reason. Operator marks do not depend on the calibration and are decoded whenever their source is readable.

## 6. Dropping a mark at the PC

While the session runs, in a second console on the PC:

```
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <install directory>\clock-calibration.ps1 -OutputDirectory <the session directory> -Mark "felt a stutter"
```

`-ExecutionPolicy Bypass` sets the policy for that one process only ([about_PowerShell_exe](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1)); without it a Windows client, whose default execution policy is Restricted, refuses to run any script ([about_Execution_Policies](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_execution_policies)). A session started by hand needs the same switch:

```
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <install directory>\clock-calibration.ps1 -OutputDirectory <a new directory> -DurationSeconds 120
```

The mark command prints one JSON line with the counter value and UTC time it recorded and exits 0, or prints the reason and exits 1: no session is accepting marks in that directory, the session has finished, the session passed its deadline without finishing (it was stopped, and a mark into it would never reach a bundle), the label is empty, longer than 80 characters or holds a control character, or the marks file would exceed its cap. It reads the two clocks, appends one line to the live marks file as its only writer (two marks typed at once cannot overwrite each other; the second waits up to half a second) and exits; it opens, inspects, signals or changes no other process, and in particular never the game or its anti-cheat (the captain plays under Easy Anti-Cheat; the mark is a file append in a separate console). The time between the felt moment and the keypress is the person's reaction time, which nobody measures; a mark says "around here", with the counter bracket as its only instrument uncertainty.

Run by hand at the PC, the session directory is wherever the person pointed `-OutputDirectory`. Through the SSH front door the dispatcher creates the directory under its outbox as the collector account; whether the person's own account may append to a file there is on the verification list in `collectors/windows/README.md`, and until it is settled the by hand run is the way to use marks.

## 7. Limits

- The collector proves nothing about the ETW session clock. A kernel trace captured by another collector must use the QPC clock type (the default) for its stamps to live on this master clock; that collector's documentation says how it verifies that.
- The pairs are exact to their brackets, but a `system_time` source's own stamps are not: an event log record or a counter sample carries the coarse system time at the instant it was taken, which may lag the true instant by one clock step of the process that stamped it. That is the source's own resolution, which the correlator adds to `e_S`; the calibration cannot remove it.
- Drift is measured per segment, not modelled across the session; the contract's model is piecewise and this piece follows it. The sidecar reports the largest deviation so a reader can see a steady drift.
- A backward step of the system clock larger than one interval cannot be fitted and makes the calibration unalignable; one smaller than the interval makes the file times the clock showed twice unaligned and widens the step segment's bound to the time that passed.
- Nothing here has run on Windows. The facts the collector relies on are on the verification list in `collectors/windows/README.md`.
