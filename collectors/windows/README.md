# Windows collectors

Named, read only PowerShell collectors, one per question. Each writes one bundle that follows [docs/contracts/bundle.md](../../docs/contracts/bundle.md) and records measurement status the way [docs/contracts/measurement-status.md](../../docs/contracts/measurement-status.md) requires: a source the account could not read becomes a status with a reason, never an empty result that could be read as "nothing happened".

They run on the Windows PC as a dedicated standard account that is a member of Event Log Readers, started over SSH by a forced command dispatcher. The dispatcher, the setup script, and the transport belong to the front door work and live outside this directory. The history collectors need no Administrator rights and ask for none. Three collectors are different. `dpcisr-trace` and `diskio-trace` record a live kernel trace, which Microsoft documents as an Administrator operation; each refuses to start when the account is not elevated, reports that as its status, and builds no elevation of its own. Their traces never leave the machine (see their sections; `diskio-trace` ships only an aggregate made on the PC). `presentmon-frames` records an ETW trace of PresentMon's providers through Windows Performance Recorder, which Microsoft grants to elevated administrators and to members of Performance Log Users; it never elevates, and its section says what is not yet known about running the recorder as such a member. Its recording never leaves the machine either. The other questions that need elevation are listed under "Needs elevation".

Version 1.2.0 (`Get-WfCollectorsVersion` in `_common.ps1`; each collector also carries its own version, recorded in the manifest as the scenario version). 1.1.0 added three source types to the helper for the RF survey: a fixed `netsh` query (`command`), one known file summarised read only (`file`), and present Plug and Play devices with their parent chain (`pnp`), plus the pseudonyms that keep network names and hardware addresses out of a bundle. 1.2.0 adds the configuration snapshot: the `command` source also runs `powercfg` listings, the `file` source can copy the owner's own text files with a protection pass, and four source types are new: `directory` (the files of one known folder, hashed and versioned, never copied), `registry` (documented values under documented keys, read only, with their type and bytes), `topology` (the logical processor map through the documented API), and `unavailable` (a question with no documented read only path, recorded as a status with its reason). 1.2.0 also adds the live capture: the `script` source type (a source the collector implements itself, used by the live captures so their session control stays local to each script), a definition's `Cleanup` scriptblock (run after the last source and on the way out of a failure), the adapters for the inbox `wpr.exe` and `tracerpt.exe`, for the hash and version of an operator supplied tool, for a monotonic clock and for the wait of a live capture, a definition's own calibration section and requested duration, `buffers_lost` next to `events_lost` in every manifest entry (manifest schema 1.1.0), and, for `presentmon-frames`, Performance Log Users membership in the account record and `Get-WfBinaryInfo` (the adapter that reads an operator supplied executable's size, SHA-256 and version strings before a collector runs it, again right before the run). It also adds the `custom` source type (a function the collector script itself defines, which may fill the manifest's calibration section and scenario marks) and the clock adapters, for `clock-calibration`, the collector that calibrates the system clock against the performance counter during a live session.

## Interface

A collector is a standalone script for Windows PowerShell 5.1:

```
powershell.exe -NoProfile -NonInteractive -File <install directory>\<name>.ps1 -OutputDirectory <path>
```

- `<name>` matches `^[a-z][a-z0-9-]{1,40}$`. The shared helper `_common.ps1` must be installed next to the collectors; its name starts with an underscore so it can never match that pattern and can never be dispatched. Every file a collector needs at run time is a `.ps1` file directly in this directory. The `tests` subdirectory is not needed on the PC.
- `-OutputDirectory` is the one parameter the dispatcher passes. The collector writes the bundle into it (creating it when it does not exist) and writes nowhere else itself. It refuses a directory that already holds a `manifest.json` or a `raw` directory, because `raw/` is immutable after capture. One stated qualification to "nowhere else": `config-snapshot` loads two native declarations with `Add-Type`, which Microsoft documents as compiling the source and generating an in-memory assembly ([Add-Type](https://learn.microsoft.com/powershell/module/microsoft.powershell.utility/add-type?view=powershell-5.1)); whether the Windows PowerShell 5.1 compiler behind it starts a compiler process or writes temporary files to the account's temp folder while it does so is not documented on Learn and is unverified (verify 57). Nothing of that would be part of the bundle, and no other collector does it.
- Native calls are confined to two audited blocks in `_common.ps1`, each a literal ASCII declaration compiled once per process and bound to the system directory: `New-WfDeviceKeyNative` (seven imports from `setupapi.dll` and `advapi32.dll`: `SetupDiCreateDeviceInfoList`, `SetupDiOpenDeviceInfoW`, `SetupDiOpenDevRegKey`, `SetupDiDestroyDeviceInfoList`, `RegOpenKeyExW`, `RegEnumValueW`, `RegCloseKey`) for the device hardware keys, and `Get-WfLogicalProcessorInformation` (`GetLogicalProcessorInformationEx` from `kernel32.dll`) for the processor topology. `tests/test_collectors_static.py` pins the exact imports, the access mask (`KEY_READ`, 0x20019), the flags and the relative subkey literals, bans `Add-Type` and `DllImport` everywhere else, and has negative cases for every widening (an extra import, a write mask, a setter, interpolated source, `Add-Type` elsewhere). Neither block opens a process, a thread or a device for anything but reading its registry key.
- It never prompts. `-OutputDirectory` is deliberately not declared `Mandatory`, because a missing mandatory parameter makes an interactive session prompt; a missing value is reported as a failure instead.
- The last and only line on stdout is the summary: `{"collector":"<name>","status":"ok|partial|failed","bundle":"<OutputDirectory>","artifacts":<count>}`. It is plain ASCII (other characters are written as JSON escapes), so console code pages cannot damage it. `bundle` is the `-OutputDirectory` value exactly as given and `artifacts` is the number of files listed in the manifest. The same line is stored in `logs/summary.json`, also when the run fails after the directory was laid out (then `logs/collector.log` says what happened and no manifest exists). A directory the collector refuses, or cannot create, gets nothing.
- Diagnostics go to stderr and to `logs/collector.log`.
- The exit code is the script's own `exit`, which `powershell.exe -File` returns as the process exit code ([about_PowerShell_exe](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1)). A dispatcher that uses `-Command` instead would flatten every failure to 1 and must add `exit $LASTEXITCODE` itself.

| Summary status | Exit code | Meaning |
|---|---|---|
| `ok` | 0 | The bundle is complete and every source is `observed` or `observed_zero`. |
| `partial` | 0 | The bundle is complete as a container (manifest written, every artifact checksummed). At least one source is `observed` or `observed_zero` and at least one is not; the manifest says which and why, and `capture.incomplete` is true. |
| `failed` | 1 | No source is `observed` or `observed_zero`, or the bundle could not be written. When a manifest could be written it is still there and still valid, and it records the reason per source. |

Optional parameters, for a person running a collector by hand (the dispatcher passes none, so the defaults are what runs):

| Parameter | Default | Meaning |
|---|---|---|
| `-WindowDays` | 30 | How far back to read, 1 to 365. Not on `driver-inventory` or `config-snapshot`, which are snapshots, nor on `presentmon-frames`, a live capture bounded by `-DurationSeconds`. On `rf-survey` it bounds the WLAN AutoConfig channel only. |
| `-MaxEvents` | 5000 (20000 for `driver-inventory`) | Cap on records per source, 1 to 100000. On `rf-survey` it also caps the devices of a `pnp` source. Not on `presentmon-frames`. |
| `-MaxArtifactBytes` | 67108864 (64 MiB) | Cap on the size of one export, 1 MiB to 1 GiB. It is enforced against the bytes actually written, never estimated. On `presentmon-frames` three quarters of it, in whole megabytes, is the recording's `MaximumFileSize` (ETW stops a sequential session at that size, so the cap holds during the recording, not only after it), the merged file is checked against it, and the CSV PresentMon prints is captured under it by the process runner. |
| `-TimeoutSeconds` | 300 (80 for `rf-survey`, 50 for `config-snapshot`, 120 for `dpcisr-trace` and `diskio-trace`) | Deadline for reading one source, 1 to 3600. Every read runs under it: the event log query, the oldest record probe, the WMI query with its operation timeout and a deadline check on every row it returns, `wevtutil`, `netsh`, `powercfg`, the registry and folder reads, and the device property reads. A read that does not finish in time is `capture_failed`. `rf-survey` has ten sources and the dispatcher stops a collector after 900 seconds, so its default is 80 (10 times 80 is 800); `config-snapshot` has nineteen, of which seventeen read something (two are `unavailable`), so its default is 50. On `dpcisr-trace` it bounds each long tool process (`wpr -start`, `wpr -stop`, `tracerpt`, `xperf`); status, profile enumeration and cancel calls have a fixed 30 second deadline. A `wpr -stop` that does not finish in time is stopped and the session cancelled. Not on `presentmon-frames`, whose deadlines follow from `-DurationSeconds`. Not on `clock-calibration`, whose deadline is its duration plus 60 s. |
| `-WlanReportPath` | empty | `rf-survey` only: where the WLAN report is, when `netsh wlan show wlanreport` printed a location other than the conventional one under ProgramData. |
| `-Snapshot` | `start` | `config-snapshot` only: `start` or `stop`, which half of a before and after pair this run is. It is recorded with the process list and labels the `process_inventory` rows; any other value is a `failed` summary and no bundle. |
| `-DurationSeconds` | 60 (120 for `clock-calibration`) | On `clock-calibration`: the session length, 10 to 840 (the dispatcher stops a collector after 900 s). On `dpcisr-trace`: how long the trace session records, 5 to 300, measured on a monotonic clock from the moment `wpr -start` returned to the moment `wpr -stop` is issued (the status read after the start counts toward it; nothing runs between the deadline and the stop). The stop is issued when it elapses, when the recording reaches the trace cap, or when anything fails. Worst case run time, recorded in `session.json` and in the manifest's `requested.options` as `worst_case_seconds`: the duration, plus four long timeouts (`wpr -start`, `wpr -stop`, `tracerpt` and `xperf` can each run to just under `-TimeoutSeconds` in one run), plus five short ones outside the recording (the default instance status and the profile enumeration before the start, the status after the stop, the cancel and the final status, 30 seconds each), plus, for a duration below 30, the up to 25 seconds by which the status read after the start can outlast it. With the defaults that is 60 plus 480 plus 150, 690 seconds, inside the dispatcher's 900 second budget. The collector refuses to start, before any `wpr` call and before the bundle directory exists (a `failed` summary line, exit code 1), when the worst case exceeds that budget: `-DurationSeconds 300` with the default timeout is 930 and is refused, so a recording longer than 270 seconds needs a lower `-TimeoutSeconds`. On `presentmon-frames`: how long the ETW recording runs, 5 to 240. The other phases have fixed deadlines (start 60 s, each status read 30 s, stop and merge 180 s, the offline read 240 s, a cancel 60 s), and the helper's bound on a whole run is `-DurationSeconds` plus 810 seconds (four status reads, three cancels, the start, the stop and the read): 870 at the default, inside the dispatcher's 900; "The dispatcher verb" below says what a longer window means. On `diskio-trace`: the same as on `dpcisr-trace`, 5 to 300; the collector refuses to start when the worst case run time ("The diskio-trace sources", Run time) exceeds 900 s. |
| `-MaxTraceBytes` | 2147483648 (2 GiB) | `dpcisr-trace` and `diskio-trace`: cap on the trace, 16 MiB to 16 GiB. The recording is stopped early when the temporary recording reaches it (the shorter window is a complete record, status `capture_failed`); a saved trace above it is not read. |
| `-MaxDumpBytes` | 4294967296 (4 GiB) | `diskio-trace` only: cap on the XML dump tracerpt writes from the trace on the PC, 16 MiB to 16 GiB. A dump above it is not read (the aggregate is `capture_failed`); the dump is deleted either way. |
| `-XperfPath` | empty | `dpcisr-trace` only: full path of an `xperf.exe` from the Windows Performance Toolkit. It runs only when the file's SHA-256 and version match a build pinned in `_common.ps1` (`Get-WfPinnedToolBuilds`); otherwise the report source is `not_collected` and says so. No build is pinned yet (see "The dpcisr-trace sources"). |
| `-Mark` | empty | `clock-calibration` only, and not a collector run: appends one counter stamped mark with this label to the marks file of the session running in `-OutputDirectory`, prints one JSON line and exits (see "Dropping a mark" below). |
| `-ProcessName` | empty | `presentmon-frames` only: process names PresentMon keeps when it reads the recording, each passed as one `--process_name` (letters, digits, `.`, `_` and `-`, not starting with `-`, at most 8 names). The recording itself is always of every process. Empty keeps every presenting process; see "Process names" below for why that is the default. |
| `-PresentMonPath` | empty | `presentmon-frames` only: where the pinned PresentMon console binary is. Empty means `<install root>\tools\PresentMon-2.6.0-x64.exe`, two directories above the collector (`C:\ProgramData\win-forensics\tools` on the PC). |

A value outside its range produces a `failed` summary and no bundle.

This collector records the kernel's DPC and interrupt events for a bounded window and, on the machine, turns them into the per CPU, per module tables the project already had (`dpcisr_module_cpu` and `dpcisr_interval`). Which threads ran on that CPU is a later question with its own privacy decision (below); this profile records nothing about processes or threads.

No stacks are requested: nothing here needs them and stack walking multiplies the volume. No process, thread or scheduling keyword is requested (next paragraph).

Privacy. Two things a kernel trace can hold must not reach a bundle, and this collector handles each by construction, not by recognising known values:

- Process names, command lines and user ids. The kernel Process events that the `ProcessThread` keyword enables carry every process's `CommandLine` ("Full command line of the process") and `UserSID`, and their DCStart and DCEnd forms "enumerate the process that are currently running" when the session starts and ends ([Process_TypeGroup1](https://learn.microsoft.com/windows/win32/etw/process-typegroup1)). A game launcher's command line can carry account identifiers; an image path carries the user's profile name. The profile therefore requests no `ProcessThread`, `CSwitch` or `ReadyThread`. The status read after the start fails the capture when a requested keyword is missing; a keyword WPR enabled on its own would show in `status.txt`, and whether the saved trace holds any Process event without `ProcessThread` is verification item 32. Recording which threads ran on the pinned CPU is a later piece that needs the owner's decision on what may leave the PC.
- Hardware and network addresses. A kernel session writes system configuration events on its own: "the kernel session automatically generates hardware configuration events; you do not enable these events when starting the NT Kernel Logger session" ([SystemConfig class](https://learn.microsoft.com/windows/win32/etw/systemconfig)), and the NIC configuration event carries `PhysicalAddr` ("Hardware address for the adapter"), `IpAddresses` and `DnsServerAddresses` ([SystemConfig_NIC](https://learn.microsoft.com/windows/win32/etw/systemconfig-nic)). The flag that turns that rundown off, `EVENT_TRACE_FLAG_NO_SYSCONFIG` ("Do not do a system configuration rundown", [EVENT_TRACE_PROPERTIES](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-event_trace_properties)), is an ETW enable flag with no keyword in a WPR profile, and WPR's own `-merge -mergeonly` option is described as merging "without adding machine-specific information or image ID events", which says the normal save adds such information too ([Merge](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-command-line-options#merge)); `-supresspii` is documented only as "Suppresses personally identifiable(PII) information", without saying what. So the documentation does not let this collector show that a saved trace is free of addresses, and the trace does not leave the machine: it is written under `<OutputDirectory>\private`, read there by `tracerpt` and (when pinned) `xperf`, and the whole private folder is removed by the definition's `Cleanup`, which runs after the last source and on the way out of a failure (the dispatcher publishes a directory only when the collector exits 0, so a killed collector leaves nothing to fetch either). The bundle keeps the trace's size and SHA-256 and the three texts made from it, and each of those (`status.txt`, `tracerpt-summary.txt`, `dpcisr.txt`) passes through the helper's hardware address pseudonyms (six hexadecimal pairs become `mac-<12 hex>`) before it is written, with the replacement count in the manifest. Verification item 30 checks the whole of this on the PC.

Loss. ETW discards an event when every buffer of the session is full and counts it ("ETW increments the EventsLost property of the logging session so that consumers can see the data loss", [Sessions](https://learn.microsoft.com/windows-hardware/test/wpt/sessions)); buffers that could not be written to the log are counted separately as `LogBuffersLost` ("the number of buffers that could not be written to the log file", [EVENT_TRACE_PROPERTIES](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-event_trace_properties)), and the saved trace's header keeps both `EventsLost` and `BuffersLost` ([TRACE_LOGFILE_HEADER](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-trace_logfile_header)). A live `wpr -status` is a snapshot of a running session, so it decides nothing about the saved trace: the collector reads it once, right after the start, for the enabled keywords and the buffer size, and fails the capture if its `Events Lost` line is missing or not a number or if it lists lost buffers ("If buffers have been lost, those buffers are listed", [Status](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-command-line-options#status)). The final figures come from `tracerpt <trace> -summary` after the stop: the collector reads the lines whose label is `Events Lost` or `Buffers Lost`, with or without a `Total` prefix, or `Log Buffers Lost`, the name Microsoft's tracelog display gives the `LogBuffersLost` member of EVENT_TRACE_PROPERTIES ("The number of buffers whose content could not be written to a log", [Tracelog Properties Display](https://learn.microsoft.com/windows-hardware/drivers/devtest/tracelog-properties-display)), with a colon or spaces before the value and no other spelling, requires exactly one whole number for each, writes them as the source's `events_lost` and `buffers_lost`, and reports `capture_failed` when either is missing, not a number, stated twice with different values, or above zero. Null never becomes zero, in the collector or in `scripts/decode_tracestats.py`, which decodes both texts into the `tracestats` table and fails when the table's final figures and the manifest's disagree. Microsoft documents that tracerpt writes a summary report and nothing about its text, so until verification item 31 has run on the PC every capture is expected to end `capture_failed` with the reason naming the figure it could not read, and the summary text in the bundle is what fixes the reader.

Status rules for the trace, in the order they are tested: first, a session that was started (a refused or timed out start counts, because it may have left a session behind) and whose own instance does not read as idle after the cancel is `capture_failed`, with the earlier failure named in the reason, because a session may still be recording; then the preflight refusals are `not_collected` (no `wpr`, no `tracerpt`, not elevated, default instance not idle, profile not enumerated, or start refused); then `capture_failed` for settings not verified from the status after the start (the session is cancelled and nothing saved), a stop that failed or timed out (cancelled, nothing saved), a missing or empty trace, a trace above the cap (not read), a summary that could not be produced or read, a loss figure that is null, any loss above zero, and a recording stopped early at the cap. Whatever the status, a session that was started is cancelled unless its own instance reads as idle, and the final state (`idle`, `active` or `unknown`) is in the manifest; `unknown` (a status command that failed, printed nothing, timed out or used words the reader does not know) never counts as idle. The report inherits every one of these: it is `observed` only from an `observed` trace.

Where the per CPU table comes from. Three ways from the trace to `dpcisr_module_cpu` were weighed; the trace stays on the machine, so all three run on the PC.

1. `xperf -a dpcisr`, implemented: its text report is the format the project already decodes, with every CPU number and module name kept. xperf is not inbox, so it is an operator supplied, hash pinned tool, and which Windows Performance Toolkit release goes on the PC is an open decision (verification item 29); until a build is pinned the report source reports `not_collected`.
2. `tracerpt -report`, inbox: produces a "Windows Event Trace Session Report" whose documented sections give "the percentage of processor time spent servicing DPC routines for each driver" and the same for ISRs ([Example 15: Measuring DPC/ISR Time](https://learn.microsoft.com/windows-hardware/drivers/devtest/example-15--measuring-dpc-isr-time)), but Microsoft documents neither a per CPU breakdown nor the report's format, and the per CPU split is the point.
3. `tracerpt -o <file> -of XML` (or `CSV`), inbox, with `-rts` for the raw timestamp: a dump of every event in the documented rendered event schema, whose `System/Execution` element carries `ProcessorID`, "The identification number for the processor that processed the event" ([Execution element](https://learn.microsoft.com/windows/win32/wes/eventschema-execution-systempropertiestype-element)), and whose payloads for the DPC, ISR and Image_Load events are documented MOF classes ("DPC and ISR events have an entry time stamp which is used to compute the duration of the routines", [DPC class](https://learn.microsoft.com/windows/win32/etw/dpc)). An aggregation on the Mac could build the per CPU tables from that dump with no software added to the PC. Not implemented here: whether this Windows build renders the kernel MOF payloads in the dump, the dump's size for a 60 second trace, and how `InitialTime` is rendered are verification item 33, and the dump would carry the system configuration events and every image path, so the collector would have to keep only the DPC, ISR and Image events by their documented type before anything left the machine. The earlier note in this file that the per event processor number is not documented was wrong: it is, in `ETW_BUFFER_CONTEXT` and in the rendered event's `Execution` element; what remains undocumented is the on disk layout of the `.etl` file, which only matters for a parser that reads the file directly.

Anti-cheat. The owner plays under Easy Anti-Cheat. ETW observes from the kernel, outside every process: nothing in this collector opens a handle to, injects into, overlays, suspends, or changes the priority or affinity of any process, and the only thing it starts is the trace session, which it stops. Whether Easy Anti-Cheat treats a running ETW kernel session as a signal is not stated in its documentation as far as this project has found; that is recorded here as unknown, not asserted either way.

### The diskio-trace sources

The question: what reads from and writes to disk while the PC is in use, and does it line up with a hitch? This collector records the kernel's disk, hard fault, file name and process and thread events for a bounded window, reads the saved trace on the PC, and keeps only an aggregate: one row per one second bin, process, directory, disk and operation, with operations, bytes, the `IrpFlags` values seen and the response time distribution. The trace and its dump never leave the machine. Everything disk related is in `diskio-trace.ps1`, with the session control in five local functions (`Start-DiskIoSession`, `Test-DiskIoSessionSettings`, `Wait-DiskIoSessionWindow`, `Stop-DiskIoSession`, `Confirm-DiskIoSessionStopped`) that a later runner can adopt; nothing of it is in `_common.ps1`.

`FileIO` and `FileIOInit` (the logical request on the application's own thread) are not requested until a pilot measures their volume. Without them a write that the system flushes later reaches the disk on a system thread and is charged to that thread's process (System), never to a guessed one; the row's `IrpFlags` values let the decoder show the paging share (`IRP_PAGING_IO`, 0x2, a value from the Windows Driver Kit header `wdm.h`: Microsoft Learn lists the flag on the DiskIo page without its value, so it is verification item 72). A disk request whose issuing thread the trace never names keeps a null process.

Rows. `aggregate.jsonl` has one JSON object per line, sorted, with `bin_start_s` (whole seconds from the header's start), `process_id`, `process_image`, `volume`, `directory`, `path_class`, `extension`, `disk_number`, `operation` (`read`, `write` or `hard_fault`), `operations`, `transferred_bytes`, `irp_flags_operations` and `irp_flags_bytes` (each `IrpFlags` value in hex with its operations and bytes; null for hard faults), and the sum, maximum, median and 95th percentile (nearest rank) of the response time in microseconds (`HighResResponseTime` times 1000000 over `PerfFreq`; null for hard faults, which carry no response time). `scripts/decode_diskio.py` turns it into the `diskio_activity` table ([decoded-tables.md](../../docs/contracts/decoded-tables.md) section 5.20), adding `paging_operations` and `paging_bytes`.

Privacy. A file path names the owner's profile folder, documents, saves and accounts ("Recordings can contain personally identifiable or security-related information. This includes paths to files that the recording accesses", [WPR How-to Topics](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-how-to-topics)); the Process events also carry each process's `CommandLine` and `UserSID` ([Process_TypeGroup1](https://learn.microsoft.com/windows/win32/etw/process-typegroup1)); and the kernel session writes the system configuration events with the adapters' hardware and IP addresses on its own ([SystemConfig](https://learn.microsoft.com/windows/win32/etw/systemconfig), [SystemConfig_NIC](https://learn.microsoft.com/windows/win32/etw/systemconfig-nic)). This collector handles each by construction:

- The trace and the dump live under `<OutputDirectory>\private`, are read there, and are deleted by the aggregate source as soon as it has read them (and by the definition's `Cleanup` on every other exit path, as in `dpcisr-trace`). The bundle keeps their sizes and SHA-256, the trace header and the event counts, which show that they existed and were removed. The collector fails closed on a removal it cannot confirm: when `<bundle>\private` is still there after the delete, `recording_and_dump_removed` is false, no `aggregate.jsonl` is written, both sources are `capture_failed` with a reason and a manifest note telling the owner to delete `<bundle>\private` by hand and not to take the directory off the PC, the summary line says `failed` and the exit code is 1; the decoder refuses such a bundle as well.
- The reader takes from a Process event only `ProcessId` and `ImageFileName`; `CommandLine` and `UserSID` are never read (the synthetic dump's Process events carry both, and the Pester suite and `tests/test_diskio_trace.py` check that neither reaches any bundle file), and the SystemConfig events are counted as "other" and never read.
- A directory keeps its fixed root and one level below it in clear and nothing deeper. The fixed roots are `\Windows`, `\Program Files`, `\Program Files (x86)`, `\ProgramData`, the NTFS `\$Extend` directory, and under `\Users\<profile>` only `AppData\Local`, `AppData\LocalLow`, `AppData\Roaming`, `Desktop`, `Documents` and `Downloads`. The user folder itself is always written `<profile>`; every other component becomes `dir-<first 12 hex of SHA-256(salt, the lower cased path up to it)>`, and a directory outside the fixed roots is a pseudonym from the top. The reserved NTFS names in the volume root (`$Mft`, `$MftMirr`, `$LogFile`, `$Volume`, `$AttrDef`, `$Bitmap`, `$Boot`, `$BadClus`, `$Secure`, `$UpCase`) are files and count under `\` like any root file; below `\$Extend` a level stays readable only when it is one of the names NTFS reserves there (`$Config`, `$Delete`, `$ObjId`, `$Quota`, `$Repair`, `$Reparse`, `$RmMetadata`, `$Tops`, `$Txf`, `$TxfLog`; [NTFS Reserved File Names](https://learn.microsoft.com/openspecs/windows_protocols/ms-fscc/b04c3bd0-79dc-4e58-b8ed-74f19fc2ea0a)). No other name that starts with `$` is a root: `$Recycle.Bin`, whose folders are named by account id, and everything below it are pseudonyms. A name that starts with a drive letter, which Microsoft documents the kernel does not write, has no fixed root and is a pseudonym from the top. A file's name never leaves the PC. The trace cannot tell a folder from a file, so the text after a name's last dot may be the tail of a folder name (a profile folder named with a dot, for one): the extension is kept, lower cased, only when it is one of `bin`, `cache`, `cfg`, `dat`, `db`, `dll`, `etl`, `evtx`, `exe`, `ini`, `jpg`, `json`, `log`, `mp4`, `pak`, `pdf`, `png`, `sav`, `sys`, `tmp`, `txt`, `xml`, `zip`, and any other is recorded as `other`. A file in the volume root counts under `\`. The volume is kept when it is a device name such as `HarddiskVolume3`, else a pseudonym.
- An image name is kept when it is 1 to 64 letters, digits, spaces and `._()+-`, else `image-<12 hex>`. Process names of this machine are therefore in the bundle; the owner reviews them (verification item 77).
- The salt is random per run, lives only in the collector's memory and never leaves the PC: the same directory maps to the same pseudonym inside one bundle and to nothing outside it.
- Files under the collector's own output directory are counted with `path_class` `collector` and no directory, and a disk request whose `FileObject` the trace never names is `unnamed`.

Loss, status and time. The loss rules are those of `dpcisr-trace`: any event or buffer lost, live, in the summary or in the saved header, is `capture_failed`, and null never becomes zero. Zero disk requests over a recording window is never read as quiet: a dump this reader cannot read would look the same, so it is `capture_failed`. The bins are whole seconds from the header's `StartTime` on the trace's own clock, and the header must name the performance counter (clock type 1) for the source to be `observed`; WPR's clock choice is not documented (verification item 69). The decoded table is in the `etw_qpc_relative` domain of [timestamps.md](../../docs/contracts/timestamps.md), the domain `presentmon-frames` already uses; an event is placed by its rendered `SystemTime`, whose precision in the tracerpt dump is verification item 74.

Concurrency. This collector runs alone. "There is only one NT Kernel Logger session. If the session is already in use, the StartTrace function returns ERROR_ALREADY_EXISTS" ([Configuring and Starting the NT Kernel Logger Session](https://learn.microsoft.com/windows/win32/etw/configuring-and-starting-the-nt-kernel-logger-session)), and whether WPR gives a second named instance its own system logger is not documented (verification item 68). Microsoft documents no read only command that lists the kernel sessions in progress (the [logman query](https://learn.microsoft.com/windows-server/administration/windows-commands/logman-query) page describes `-ets` only as "Sends commands to Event Trace Sessions directly without saving or scheduling"), so the collector does not check for another kernel session: the preflight records `concurrent_kernel_session_check` as `not_checked`, and a start that collides is refused by WPR and reported as `not_collected` with WPR's text. It runs next to `dpcisr-trace` only after item 68 passes.

Elevation. "Only users with administrative privileges and services running as LocalSystem can control an NT Kernel Logger session" ([StartTraceA](https://learn.microsoft.com/windows/win32/api/evntrace/nf-evntrace-starttracea)). The collector checks the account before any `wpr` call and reports `not_collected` when it is not elevated, which is what the front door's standard account gets today; it builds no scheduled task, service or other persistent elevation (see "Needs elevation").

Run time. The collector refuses to start (a `failed` summary and no bundle) when its worst case exceeds the dispatcher's 900 seconds: `-DurationSeconds`, plus what remains of a 30 second minimum, plus four `-TimeoutSeconds` (start, stop, the tracerpt read of the trace, reading the dump), plus five 30 second status, profile and cancel calls. The defaults give 690 seconds.

Anti-cheat. As for `dpcisr-trace`: ETW observes from the kernel, outside every process; nothing here opens a handle to, injects into, overlays, suspends, or changes the priority or affinity of any process, and the only thing it starts is the trace session, which it stops and confirms stopped. Whether Easy Anti-Cheat treats a running kernel session as a signal is unknown, not asserted either way.

### The clock-calibration sources

| Source | Type | What it records | Expected status |
|---|---|---|---|
| `clock_calibration` | custom | A bounded session: a triple (counter, system time as a file time, counter) read in one thread at the start, every 5 s (the timestamp contract's cadence) strictly inside the session and at the stop, through `Stopwatch.GetTimestamp` (Microsoft: the managed `Stopwatch` "uses QPC as its precise time basis"; its `Frequency` and `GetTimestamp` "can be used in place of the unmanaged Windows APIs QueryPerformanceFrequency and QueryPerformanceCounter") and `[DateTime]::UtcNow.ToFileTimeUtc()`. `Stopwatch.IsHighResolution` must be true, else the session is `unsupported`. | `operator_marks` | custom | The marks file. ### Dropping a mark

While the session runs, in a second console on the PC:

```
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <install directory>\clock-calibration.ps1 -OutputDirectory <the session directory> -Mark "felt a stutter"
```

`-ExecutionPolicy Bypass` sets the policy for that one process ([about_PowerShell_exe](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1): it "sets the default execution policy for the current session" and "does not change the PowerShell execution policy that's set in the registry"); without it a Windows client, whose default policy is Restricted, refuses to run any script ([about_Execution_Policies](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_execution_policies)). A session run by hand needs the same switch; the dispatcher passes `-ExecutionPolicy RemoteSigned` itself.

The command reads the counter, the system time and the counter again in its own process, appends one line to `raw/operator_marks/marks.open.jsonl` of that session, prints one JSON line (`{"collector":"clock-calibration","mark":"<label>","qpc":<counter midpoint>,"at_utc":"...","file":"raw/operator_marks/marks.open.jsonl","error":null}`) and exits 0. It exits 1 with the reason in `error` and on stderr when no session is accepting marks in that directory, when the session has finished (`manifest.json` exists, or the live file has been renamed), when the session's deadline (`accepts_marks_until_utc` in `raw/clock_calibration/session.json`, its start plus its duration plus 60 s) has passed without a manifest, which means the session was stopped and the mark would never reach a bundle, when the label is empty, longer than 80 characters or holds a control character, or when the marks file would exceed `-MaxArtifactBytes`. It opens the live file for append only when it already exists (never creates one) and as the only open handle (`FileShare.None`: Microsoft documents that it "declines sharing of the current file. Any request to open the file (by this process or another process) will fail until the file is closed"; nothing reads the live file before the session renames it), so two marks typed at once cannot overwrite each other; the second waits up to half a second. It opens, inspects or signals no other process, and never touches the game or its anti-cheat. Microsoft documents the counter as consistent "even when measured on different threads or processes", so the mark's counter value is on the same clock as the session's pairs and the kernel trace. The time between the felt moment and the keypress is the person's reaction time; a mark means "around here".

USB port speed is not in the export because Windows does not expose it through a documented property a standard account can read: "the USB driver stack that Windows loads correlates to the type of host controller, not to the connected device's speed" ([USB in Windows FAQ](https://learn.microsoft.com/windows-hardware/drivers/usbcon/usb-faq--introductory-level)). What the tree does show is which controller serves a port: `USBXHCI` and `USBHUB3` are the USB 3 (xHCI) stack, `usbehci` and `usbhub` the USB 2 stack ([USB host side drivers in Windows](https://learn.microsoft.com/windows-hardware/drivers/usbcon/usb-3-0-driver-stack-architecture)), and the analysis says exactly that much.

Event Log Readers is the documented grant: "Members of this group can read event logs from local computers" ([security groups](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups)). An SSH session keeps the privileges of the account that authenticated and adds none ([SSH remoting](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/ssh-remoting-in-powershell)), so the group membership is the whole authorisation. A machine can carry a different descriptor than the documented default (a `CustomSD` value or a policy), which is why each event log source also records the channel's actual security descriptor when the account may read it.

Deliberate omissions inside those questions: event ids 12, 13 and 19 from Microsoft's restart history list are left out of `bugcheck-history` because many providers share them; the `Microsoft-Windows-Kernel-WHEA` channels are not read because Microsoft Learn documents neither their content nor their access; per application crash dumps belong to the later step that sets the Windows Error Reporting dump keys.

### The presentmon-frames source

One source, `presentmon_frames`, of manifest kind `presentmon`, required. It is a live capture in two steps, both passive, with the game process never opened by anything this collector runs that is documented, and one open question named as such:

1. Windows Performance Recorder (`wpr.exe`, which "ships together with the Windows operating system (Windows 8.1 or a later version) and doesn't require additional installation", [Troubleshoot processes and threads by using WPR and WPA](https://learn.microsoft.com/troubleshoot/windows-server/support-tools/support-tools-xperf-wpa-wpr)) records the ETW providers and event ids PresentMon 2.6.0 enables for its default options into a file inside the bundle, from a profile the collector writes, for `-DurationSeconds`, under the collector's own WPR instance name. WPR is an ETW controller: it enables providers and writes the session's buffers to a file. Whether it opens a handle to any presenting process while it does so is not documented by Microsoft, so this README does not claim it either way; verification item 51 is the check.
2. The pinned PresentMon console application reads that file with `--etl_file` and prints its CSV on stdout (`--output_stdout`), which the collector keeps as `raw/presentmon_frames/frames.csv`. In that mode PresentMon opens no process: at tag v2.6.0, `PresentMon/OutputThread.cpp` `QueryProcessName()` calls `OpenProcess` only when `args.mEtlFileName == nullptr` (lines 294 to 319), and `PresentMon/MainThread.cpp` enables `SeDebugPrivilege` only for realtime analysis (lines 255 to 277: "If we are processing an ETL file we don't need elevated privilege, but for realtime analysis we need SeDebugPrivilege in order to open handles to processes started by other accounts"). Process names come from the recorded Microsoft-Windows-Kernel-Process events (`PresentData/PresentMonTraceConsumer.cpp` `HandleProcessEvent`).

The recording itself never leaves the PC: it is read for its header and by PresentMon, then deleted ("Privacy" below says why). Everything PresentMon and WPR related is in `presentmon-frames.ps1` (the helper only dispatches to it and runs the processes), so the facts below can be checked against one file.

#### Why live PresentMon is not used

PresentMon's realtime mode opens a `PROCESS_QUERY_LIMITED_INFORMATION` handle to every presenting process, the game included, and keeps it for the whole capture: `OutputThread.cpp` `QueryProcessName()` (lines 294 to 319 at v2.6.0) calls `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE, processId)` for each newly seen presenting process whatever `--process_name` says, because the name filter needs the name first; the handle is polled with `GetExitCodeProcess` (lines 212 to 231) and closed at the end (lines 639 to 646). `MainThread.cpp` calls `EnableDebugPrivilege()` on every realtime run (lines 266 to 277; `Privilege.cpp` adjusts the process token). The access right is the one Microsoft lists as "Required to retrieve certain information about a process (see GetExitCodeProcess, GetPriorityClass, IsProcessInJob, QueryFullProcessImageName)" ([Process Security and Access Rights](https://learn.microsoft.com/windows/win32/procthread/process-security-and-access-rights)); it is not a memory access right. The accepted intent for this work is no handle to the game at all, so the design records with a controller and gives PresentMon only the file. That no realtime option (`--timed`, `--session_name`, `--process_id`, `--terminate_after_timed`, `--terminate_existing_session`, `--stop_existing_session`, `--restart_as_admin`, `--hotkey`, `--delay`) and no `--output_file` is passed is checked on what runs record: `tests/test_collector_bundles.py` checks the PresentMon command the committed bundles record, and the Pester suite checks every process its runs start.

#### The run, phase by phase

Every program runs through the helper's one process runner, directly and without a shell, with a deadline and a console cap. The WPR verbs and switches are the documented ones ([WPR Command-Line Options](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-command-line-options)): `-start <profile>` "Starts one or more profiles", `-filemode` "Specifies that recording is done in file mode", `-recordtempto <path>` "Specifies the temporary folder path that the recording is saved to", `-status [collectors [-details]]` "Displays the status of an active recording (if any)", `-stop <file> <description>` "Cancels and saves the recording initiated by WPR (if any)" with `-skipPdbGen`, `-cancel` "Cancels the current recording without saving the recorded data", and on every one of them `-instancename wf-presentmon-frames`: "Specifies a name to uniquely identify the tracing instance. This option can be applied to any commands that manipulate the logging session." and "-instancename must be the last parameter." The instance name is why this collector never sees, stops or cancels another WPR recording: an unnamed `wpr -cancel` is never run (`tests/test_collector_bundles.py` checks every wpr run the committed bundles record ends in the instance name, and the Pester suite checks the same on every process its runs start), and a recording started by anything else, under any other name, is neither probed nor touched. Nothing else: the same checks allow only the four verbs, so no WPR option that changes a machine setting or configures a boot trace can pass.

1. Preflight: the pin, `wpr.exe` present in System32, and `wpr -status -instancename wf-presentmon-frames` (30 s) to see that this collector's own instance is idle. The probe runs only after the pin matched. If the probe says a recording of this instance is in progress, it can only be a leftover of an earlier run of this collector that the dispatcher ended (the name is this collector's alone), so it is cancelled (`wpr -cancel -instancename wf-presentmon-frames`, with a manifest note) and probed again. A probe that fails, times out, or still shows the instance in progress is `not_collected` and nothing is started: the collector does not record when it cannot show that its own instance was idle.
2. `wpr -start "<bundle>\raw\presentmon_frames\profile.wprp!WfPresentMonFrames.Verbose" -filemode -recordtempto "<bundle>\raw\presentmon_frames\wpr-temp" -instancename wf-presentmon-frames` (60 s). The temp folder is inside the bundle, because a collector writes nowhere else; it is removed after the stop and again at the end of every path, a failed start included. A folder or recording that cannot be deleted (a session the collector could not stop still holds its file) does not stop the run: the source is `capture_failed` on every path, a start that timed out included, with no frame count claimed, and a manifest note and `recorded_data_left` in `result.json` name each file still in the bundle by path and size. Such a file is never opened: it is not hashed and not listed as an artifact (the artifact list is then the collector's own files only), and it must be deleted by hand before the bundle leaves the PC. Whether Windows refuses the delete or a read of a file a live session holds is not verified (item 56). A refusal that says access denied is `not_collected` with WPR's words; any other failure to start is `not_collected` too (nothing was recorded); a start that was issued but timed out may have left the instance recording, so it is cancelled by name.
3. The window: `-DurationSeconds` pass (`Wait-WfSeconds`). Nothing runs.
4. `wpr -status collectors -details -instancename wf-presentmon-frames` (30 s): the recording must still be in progress, the loss counters are read ("Dropped event", documented as "The number of lost events since the recording was started" in [WPR How-to Topics](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-how-to-topics), and "Events Lost" per collector as the documentation's sample shows), and the provider lines under "Providers" are compared with the request: every strict provider must be listed with every requested keyword bit and a level at least the requested one, or the source is `capture_failed` ("the requested settings were not shown enabled"). The layout of a provider line is not documented; the collector reads `<name or GUID>: <keywords>: <level>` and verification item 43 settles it. Microsoft: "Each session keeps a record of the number of events discarded (see the EventsLost member)" ([EVENT_TRACE_PROPERTIES](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-event_trace_properties)); PresentMon's realtime mode reads the same counter with `EVENT_TRACE_CONTROL_QUERY` before it stops (`PresentMonTraceSession.cpp` `Stop()`).
5. `wpr -stop "<bundle>\raw\presentmon_frames\trace.etl" "win-forensics presentmon-frames" -skipPdbGen -instancename wf-presentmon-frames` (180 s, the merge included), then `wpr -status -instancename wf-presentmon-frames` (30 s) to confirm the instance is idle. The stop is confirmed only when the stop exited 0 and that status exited 0 and reported no recording; otherwise `wpr -cancel -instancename wf-presentmon-frames` (60 s) is sent, the source is `capture_failed`, and when the cancel did not complete either, the reason and a manifest note say the recording may still be active and how to stop it. The collector's own clock is read just before the start was issued and just after the stop returned; those two instants are the source's `raw_time_range`, a bound that contains the recording.
6. The file's own header is read (`Read-WfEtlHeader`) and the file is hashed. The first buffer of an ETW log file starts with a 72 byte buffer header and then the log file header event: a 32 byte system trace header (hook id 0) followed by [TRACE_LOGFILE_HEADER](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-trace_logfile_header), "the raw data format of the trace information data in the header of an ETW log file". Microsoft documents TRACE_LOGFILE_HEADER and the [EventTrace_Header](https://learn.microsoft.com/windows/win32/etw/eventtrace-header) class, not the two headers before it; those are what the reverse engineered descriptions of the format call the WMI buffer header and the system trace header, and what PresentMon's own regression recordings show. The first 4096 bytes of the vendor's `Tests/Gold/test_case_0.etl` at v2.6.0 (whole file SHA-256 `7127ed1325fd9d179604df2a7356dc3c4cb805cb15220175e34b4faf918a31be`; MIT licence) are committed as `fixtures/presentmon/gold-test_case_0.first-buffer.etl` (SHA-256 `d7d2463ec3f97c59db6815fb936a73ecbdaae5b782ec81e597b1946b97a4a8fc`), the only `.etl` in the repository and a format fixture, not a capture: the Pester suite reads it with the collector's own reader and `tests/test_presentmon.py` checks every field at its offset, and the synthetic recording the fixture bundles were made from is laid out to match it. The header gives `EventsLost` and `BuffersLost`, the clock the events were stamped with (`ReservedFlags`: 1 is the performance counter, 2 system time, 3 the CPU cycle counter, per the `ClientContext` table of [WNODE_HEADER](https://learn.microsoft.com/windows/win32/etw/wnode-header)), `PerfFreq`, the Windows version and build, and the session's `StartTime` and `EndTime`. Every field is checked for plausibility; a header that does not read this way is `capture_failed` ("log file header could not be read"), because loss and clock would be unknown. A session whose `EndTime` is more than five seconds before the stop was requested closed early (it reached its file cap or died) and is `capture_failed` too, and so is a header whose `EndTime` is zero, because the session cannot then be shown to have run until the stop. The merge WPR performs on `-stop` may change the header; verification item 45 is a real first buffer from the PC.
7. Any loss, from any source, is `capture_failed`: the largest of the controller's "Dropped event" count, the sum of its "Events Lost" lines and the header's `EventsLost` is the manifest's `events_lost` (each source is also recorded under `events_lost_sources`), a non zero `BuffersLost` fails as well, and so does a status with no counter line at all. PresentMon is not run over a recording with loss, over one above the artifact cap, or over one whose settings were not shown enabled.
8. The binary is hashed again, then `PresentMon-2.6.0-x64.exe --etl_file "<trace.etl>" --output_stdout --qpc_time [--process_name <name>]...` (240 s). Each option is in the console README at v2.6.0: `--etl_file path` "Analyze an ETW trace log file instead of the actively running processes."; `--output_stdout` "Write CSV output to STDOUT." (`CommandLine.cpp` lines 556 to 557 then set console output to none, so stdout carries the CSV and nothing else; `PrintWarning` and `PrintError` write to stderr, `Console.cpp` `PrintColor` line 340; `--no_console_stats` is therefore not needed and not passed); `--qpc_time` "Output the CPU start time as a performance counter value." (the column is then `CPUStartQPC`; with `--etl_file` the values are the recording's own timestamps); `--process_name name` "Only record processes with the specified exe name. This argument can be repeated to capture multiple processes." The process runner captures stdout under `-MaxArtifactBytes` and stops PresentMon at the cap, so the CSV has a live byte budget; the text is written as `frames.csv` in UTF-8 without a byte order mark (the console output code page it was decoded with is in `command.json`, `csv_console_code_page`; verification item 54). PresentMon exits 0 when the file is read (`MainThread.cpp` line 474), 6 when it cannot open it (lines 361 to 383, "error: failed to start trace session: invalid --etl_file." for a corrupt file). It writes the CSV header at the first frame it emits (`CsvOutput.cpp` `UpdateCsvT`, lines 1354 to 1394: `*fp = stdout` and `WriteCsvHeader` inside `if (*fp == nullptr)`), and it discards the result of `ProcessTrace` (`ConsumerThread.cpp` lines 28 to 31: "However, it seems to always return ERROR_SUCCESS"), so an empty output cannot be told from a read that stopped early, and the collector never calls an empty output a quiet window: zero frames is `capture_failed`. Its stderr is read for "warning: N overflowed present events detected" (`MainThread.cpp` lines 455 to 459, printed in every mode when the consumer threw presents away because its completed ring was full), which is `capture_failed` with the count in `enabled.options.presentmon_overflowed_presents`, and any other warning or error line fails the source as well.
9. The recording is deleted ("Privacy"). `recording.json` keeps its size, SHA-256, header, loss counters, the settings comparison and PresentMon's warnings.

What is kept: `frames.csv` (role primary; the CSV PresentMon printed, absent unless the source is observed), `recording.json` and `result.json` (role report), `profile.wprp` and `command.json` (role config), and `console.txt` (role log; every program's stdout and stderr, labelled, verbatim, except the CSV, which is noted by size). The manifest's `command` is the PresentMon command line; the WPR command lines are in `requested.options.wpr_commands`, recorded with bundle relative paths (the processes received the absolute paths in double quotes). `buffers` records the 64 KB by 256 geometry and file mode; `enabled.providers` and `enabled.keywords` are what `wpr -status` listed.

#### How status is decided for this source

| Status | When |
|---|---|
| `not_collected` | The binary is missing or its SHA-256 or size differs from the pin; `wpr.exe` is missing; the collector's own WPR instance could not be shown idle (the probe failed, timed out, or a leftover recording could not be cancelled); or `wpr -start` did not complete (a refusal that says access denied carries WPR's words and the groups Microsoft documents). Nothing was recorded. |
| `observed` | `wpr -status` reported the recording in progress at the end of the window with zero loss and every strict provider enabled with its keywords and level, `wpr -stop` saved a file below the cap whose header reads with zero events and buffers lost and a session that ran until the stop, the instance was confirmed idle, the binary still matched the pin, PresentMon exited 0 reading the file with no warning, and its CSV carries `Application`, `ProcessID`, `CPUStartQPC` and at least one frame row. |
| `capture_failed` | Everything else after a start that completed: the recording was not in progress at the end of the window; events or buffers were lost (from any of the three counters); no loss counter could be read; the header could not be read or carries no end time; the session closed before the stop was requested (its file cap or another cause); the merged file is above the cap; the settings were not shown enabled; the stop was not confirmed (cancelled instead); the binary changed before the read; PresentMon did not start, timed out, printed above the cap, exited with a code other than 0, warned, or threw presents away; the CSV header lacks `CPUStartQPC`; or no frame was emitted, scoped or not. Nothing is kept as a primary in any of these cases, and the recording is deleted in every case. |

There is no `observed_zero` for this source. The pinned binary gives no way to tell "no process presented" from "the read stopped early", and a desktop with a compositor running presents in any case, so an empty output is a failure to show frames, not a quiet window. The status contract's rule that a target process not alive across the window is `capture_failed` is applied to the scoped case for the same reason.

#### Process names

PresentMon's offline read names a process from the recorded Kernel-Process events (`HandleProcessEvent`: ProcessStart, ProcessStop and ProcessRundown of Microsoft-Windows-Kernel-Process, or the kernel's own process events). The profile asks for the rundown of processes already running at the start (`CaptureStateOnStart` on Kernel-Process), which is how a game that was started before the recording gets its name. A process with no such event in the recording is written as `<unknown>` with its process id, the same spelling PresentMon's README documents for its realtime mode, and `--process_name` cannot match it. PresentMon's own session tolerates access denied on this provider (`EnableProvidersListing`, line 814), so the profile does not make it strict either; when the recording holds no Kernel-Process events the frames are still there under `<unknown>`. That is why the default keeps every presenting process: the rows are separated by `ProcessID` and swap chain address whatever the name says. No handle to any process is opened to learn a name.

#### Elevation and the account

Microsoft: "Only users running with elevated administrative privileges, users in the Performance Log Users group, and applications running as LocalSystem, LocalService or NetworkService can control event tracing sessions. To grant a restricted user the ability to control trace sessions, add them to the Performance Log Users group", with the warning that membership "allows a user to control event tracing sessions that can expose potentially sensitive system and application information. Grant membership only when required, limit it to the minimum number of users and the shortest practical time, and remove users promptly when access is no longer needed" ([Controlling Event Tracing Sessions](https://learn.microsoft.com/windows/win32/etw/controlling-event-tracing-sessions)). Performance Log Users is the well known group S-1-5-32-559 ([security identifiers](https://learn.microsoft.com/windows-server/identity/ad-ds/manage/understand-security-identifiers)); the collector records whether the account is a member and whether it is elevated (`WindowsPrincipal.IsInRole`, the same call the account record already makes for Event Log Readers), in the manifest notes and in `result.json`.

Whether `wpr.exe` itself accepts a Performance Log Users member is not stated by Microsoft; its instructions run WPR "from an elevated (run as Administrator) Command Prompt window" ([Record and View TraceLogging Events](https://learn.microsoft.com/windows/win32/tracelogging/tracelogging-record-and-display-tracelogging-events)). Microsoft-Windows-Kernel-Process is a kernel provider that PresentMon's own code expects a non administrator to be refused. So the honest statement is: the collector works as written for an elevated run; for the standard collector account, the owner adds it to Performance Log Users and verification item 41 says whether WPR records for it, and item 42 whether the process names arrive. The collector never elevates and never adds itself to a group. Until the elevated scheduled task exists, a refusal is `not_collected` with WPR's words.

Running PresentMon itself needs no right at all in this design: reading a file is not controlling a session, and `MainThread.cpp` skips `EnableDebugPrivilege()` for `--etl_file`.

#### The anti-cheat position

The captain plays Fortnite under Easy Anti-Cheat and Overwatch under Blizzard's protection. What the vendors document, and no more:

WPR is an ETW controller; what it does beyond controlling the session is not documented, and whether it opens a handle to any presenting process during a recording is verification item 51 (handle auditing or Sysmon's process access event against a harmless presenting process), not a claim of this README. ETW providers in the game's process (DXGI, D3D9) write to session buffers the kernel owns; nothing here attaches to, injects into, overlays, suspends or reprioritises the game, and no setting is changed.
- PresentMon's documentation describes ETW collection ("a library that performs the lowest-level collection and analysis of ETW events", README at v2.6.0). Its realtime mode's process handles (quoted above from its source) are the reason that mode is not used. The 2.6.0 release notes list the removal of the Flash Injector, the one injecting component the project ever shipped; the 2.5.0 notes' "Anticheat Mitigation" item concerns its realtime session and is quoted above without conclusion, with item 52 as the only test that applies to a WPR recording.

#### Disk use

Every output has a bound, and the collector states the peak in `command.json` (`disk_budget`):

| Output | Bound | How |
|---|---|---|
| The session file under `wpr-temp` | three quarters of `-MaxArtifactBytes` in whole megabytes (48 MB at the 64 MiB default) | The profile's `MaximumFileSize` with `FileMode="Sequential"`: the session stops at the cap, which the header's `EndTime` then shows and the collector reports as `capture_failed` |
| The merged `trace.etl` | `-MaxArtifactBytes` | Checked after the stop; a larger file is `capture_failed` and PresentMon is not run. The file is deleted in every case, and the temp folder removed |
| The CSV | `-MaxArtifactBytes` | Captured from stdout by the process runner, which stops PresentMon when a stream passes the cap and keeps nothing above it |
| Each console stream of wpr and of PresentMon's stderr | 1 MiB | The runner's cap for those runs |
| Peak on disk | session file + merged file + CSV + two console streams, about 178 MiB at the defaults | `disk_budget.peak_bytes_bound`; ETW itself "checks for an additional 200MB of disk space" on the system drive when a file is logged there ([EVENT_TRACE_PROPERTIES](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-event_trace_properties)) |

The CSV is held in memory by the runner while PresentMon prints it (up to the cap, twice that as UTF-16 text), which is the price of the live budget. For scale: about 350 bytes per row with this header, so a 240 second recording of one process at 240 frames per second is about 20 MB of CSV. The merged recording's size for this machine at play is verification item 46.

#### The dispatcher verb

The next kit install makes this collector the SSH verb `collect-presentmon-frames` with its defaults (a 60 second recording, every process, the pinned binary at `C:\ProgramData\win-forensics\tools`), because the dispatcher offers every collector in the directory. At the default window the helper's per source deadline is 840 seconds (the window plus 780), inside the dispatcher's 900; a window above 120 seconds can pass 900 only if every phase runs to its deadline, and then the dispatcher ends the collector and the next run finds and cancels the leftover instance (phase 1). Until the binary is in place the verb answers `not_collected` with the download hint, and until the account can control ETW sessions it answers `not_collected` with WPR's words.

#### Privacy

The recording never leaves the PC. `wpr -stop` merges the session file into the saved trace, and a merge adds machine specific information to it: the WPR profile schema's [TraceMergeProperties](https://learn.microsoft.com/windows-hardware/test/wpt/tracemergeproperties) element lists the custom events a merge can add, among them `NetworkInterface`, and the ETW network configuration event [SystemConfig_NIC](https://learn.microsoft.com/windows/win32/etw/systemconfig-nic) carries the adapter's physical address (`PhysicalAddr`), its IP addresses (`IpAddresses`), its DNS servers and its description. Microsoft's own caution applies: "Recordings can contain personally identifiable or security-related information. This includes paths to files that the recording accesses, or registry access and process names. Be cautious when you share recording files." ([WPR How-to Topics](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-how-to-topics)). This project keeps hardware and network addresses out of every bundle by construction, so the collector reads the recording on the PC (its header, then PresentMon) and deletes it, and the bundle carries what was read from it: the CSV, the header fields in `recording.json` (session name, Windows version and build, processor count, counter frequency, start and end, loss counters, the file's size and SHA-256), the settings `wpr -status` listed, and the console text of the runs. Whether any of those carries an address on a real machine is verification item 53; nothing in the documented output of `wpr -status` or in PresentMon's CSV is one. The CSV holds the presents of every process by executable name and swap chain address, which is what the frame analysis needs. No pseudonym rule of the RF survey applies to it and the manifest's privacy note is not written for this collector.

A collector writes capture output only. It never writes `decoded/`, `evidence.jsonl`, `verdict.json`, or `validation.json`.

Every file under `raw/` is listed in the manifest with its byte count and SHA-256. The list is built by reading the directory after the source finishes, not from what the code meant to write, so an unlisted raw file cannot occur.

`events.json` elements carry the columns of `schemas/decoded/eventlog_events.schema.json` under the same names (`record_id`, `log_name`, `provider_name`, `event_id`, `version`, `level`, `level_display`, `task`, `task_display`, `opcode`, `keywords`, `time_created_utc`, `machine_name`, `user_id`, `process_id`, `thread_id`, `message`, `properties`) plus `xml`, the complete event XML from `EventRecord.ToXml()`. `time_created_utc` is the `SystemTime` attribute of that XML, cut to seven fractional digits. `message`, `level_display` and `task_display` depend on publisher metadata and locale and are null when Windows cannot render them. The XML is complete for every element of a successful primary export: a record whose XML cannot be produced stops the source, which becomes `capture_failed` and leaves no `events.json`. `scripts/decode_eventlog.py` turns these files into the `eventlog_events` table with `index:<n>;record:<id>` provenance; it decodes only primary artifacts the manifest lists for an observed event log collector, refuses a path that is missing, unlisted, or outside the bundle, and writes nothing in that case.

`records.json` elements are the requested properties of the WMI instance under their WMI names (only the documented properties the collector names are requested, so the provider hands over nothing else), with dates as ISO 8601 UTC text and string arrays kept as arrays. The driver export is shaped so a later decoder can emit `config_snapshot` rows of category `driver` (one row per device and property, `index:<n>` provenance), and `driver-inventory` also fills `machine.drivers` in the manifest from `Win32_PnPSignedDriver`.

`keys.json` elements in devices mode carry the device's `Win32_PnPEntity` values (`instance_id`, `class`, `name`, `description`, `manufacturer`, `service`, `status`, `problem_code`, `hardware_ids`), `device_key` (the locator: `resolver` SetupDiOpenDevRegKey, `scope`, `key_type`, `access`, `device_opened`), `stage` (the last stage reached: `argument`, `compile`, `create_set`, `open_device`, `open_hardware_key`, `open_subkey`, `enumerate`, `timeout`, `read`), `error_code` and `registry_error` when a stage failed, `hardware_key_state` and `interrupt_management` (`exists` true, false or null, `error_code`, `error`), and `interrupt_keys`, one record per documented relative subkey with `subkey`, `exists`, `error_code`, `error`, `enumeration_complete` and `values`. A value is `name`, `type_code` (the numeric registry type), `kind` (`REG_DWORD`, `REG_QWORD`, `REG_BINARY`, `REG_SZ` and the rest), `data` (a JSON scalar: numbers for the DWORD and QWORD kinds as unsigned, exact text above 2 to the 53rd, hex text for binary, null for a string kind), `bytes_hex` (the bytes the registry holds, little endian for the numeric kinds; null for a string kind), `byte_count`, `present` and `omitted_reason` (set for a string kind, whose text is free text and is kept neither as text nor as hex). In keys mode each element is one fixed key read through the registry provider, with only the named values, each `present` or not, `kind` as the [RegistryValueKind](https://learn.microsoft.com/dotnet/api/microsoft.win32.registryvaluekind) name. `listing.json` is a JSON array of the folder's files, each with `name`, `bytes`, `last_write_time_utc`, `sha256`, `file_version`, `product_version`, `product_name`, `company_name`, `original_filename`; the folder's own facts (`path`, `exists`, `parent_exists`, `file_count`, `truncated`) are in `result.json`. `topology.json` is a JSON array, one element per `SYSTEM_LOGICAL_PROCESSOR_INFORMATION_EX` record in buffer order: `index`, `offset`, `size`, `relationship` and `relationship_name`, then the documented fields of its layout (`flags`, `smt`, `efficiency_class` and `group_masks` for a core or package; `level`, `associativity`, `line_size`, `cache_size`, `cache_type_name` and `group_masks` for a cache; `node_number` and `group_masks` for a NUMA node; `maximum_group_count`, `active_group_count` and `groups` for the group record), each group mask as `group`, `mask_hex` and the `processors` whose bits are set. `scripts/decode_config_snapshot.py` turns a `config-snapshot` bundle into the `config_snapshot`, `powercfg` and `process_inventory` tables.

`channel_state.json` holds the record count, the oldest retained record's number and time, the file size, the log mode, the maximum size, the isolation, and the security descriptor, each null when the account may not read it, plus which of the requested providers are registered on the machine.

`samples.jsonl` lines carry `seq`, `phase` (`start`, `interval`, `stop`), `qpc_before`, `qpc_after`, `filetime_utc_100ns`, `at_utc`, the scheduled `slot_qpc`, `late_ticks`, `edge` (the pair was taken at a change of the system clock), `step_100ns` (the size of that change), `reads` and `note`; the manifest's `calibration.pairs` holds the first five of each, and `scripts/decode_clock.py` refuses a bundle in which the two disagree. `marks.jsonl` lines carry `label`, `qpc_before`, `filetime_utc_100ns`, `qpc_after`, `at_utc` and `process_id`, in that order, which is the exact shape the collector checks when it reads the file back. The decoder turns them into `clock_pairs`, `clock_segments` (the fitted model) and `operator_marks`.

`output.txt` is the text netsh printed, with CRLF turned into LF and nothing else changed except the pseudonyms below. `result.json` also carries `fields`, every line with a colon as line number, indentation, block, label and value, which is the language independent structure `scripts/decode_rf_survey.py` classifies (by English label, else by the shape of the value), and for the profiles query `profiles`, the saved names with their pseudonyms. The report summary (`report-summary.json`) holds size, time, hash and counts and never the text. `devices.json` elements carry the `Win32_PnPEntity` values under snake case names (`instance_id`, `class`, `class_guid`, `name`, `description`, `manufacturer`, `service`, `status`, `problem_code`, `present`, `hardware_ids`, `compatible_ids`) plus the device properties (`parent_instance_id`, `location_paths`, `location_info`, `address`, `container_id`, `bus_reported_description`, `enumerator`), `is_seed` (false for a device added as an ancestor) and `property_error`.

Network names and hardware addresses belong to the neighbours as much as to the owner, and a paired Bluetooth device is someone's phone or earbuds, so no bundle carries any of them in clear: not under `raw/`, not in `logs/`, not in `manifest.json`, and the analysis never writes one into `decoded/`, `evidence.jsonl` or `reports/`. The rules are complete by construction rather than by recognising known names:

- Netsh text: every hardware address (six hexadecimal pairs with colons or hyphens) becomes `mac-<first 12 hex of SHA-256(salt, address)>`, and every network name found by structure becomes `ssid-<first 12 hex of SHA-256(salt, name)>`. In a scan each network's name line is the unindented line with a colon above its address lines; in an interface listing it is the line whose label is `SSID` and, for a display language that translates that label, the labelled line just before the BSSID address line (netsh prints SSID, then BSSID); every learned name is also replaced wherever else it appears (the Profile line).
- Saved profiles are the one readable exception: `netsh wlan show profiles` lists the owner's own networks, so its text stays as printed and `result.json` maps each name to its pseudonym. That mapping is how the owner names his network at analysis time; a saved profile alone never makes a visible network his.
- Event records are reduced to their System section: no message, string properties null, EventData, UserData and RenderingInfo emptied. A name the run never learned can hide in any of those, so none of them is kept.
- The WLAN report is summarised, never copied, for the same reason.
- Bluetooth peer device nodes, and every node the `bluetooth_devices` row above names as belonging to a peer, have their name fields replaced by `name-<12 hex>` and their bare twelve digit addresses by `mac-` pseudonyms, in the instance id, the parent id, the hardware and compatible ids and the location text.

The salt is random per run and never stored: the same value maps to the same pseudonym inside one bundle, which is what the analysis needs (the owner's profile is the scanned network; the adapter's own address is the one in the interface listing), and to nothing outside it, so a dictionary attack on short network names has no salt to work with. The Pester suite writes neighbour names, an unseen name in the report and in an event's message, properties and XML, addresses and peer names into the synthetic machine and asserts that none of them appears in any file of the bundle; `tests/test_rf_survey.py` repeats that scan over the decoded tables, the evidence rows and the report.

The manifest's machine section is filled from `Win32_OperatingSystem`, `Win32_ComputerSystem`, `Win32_ComputerSystemProduct`, `Win32_Processor`, `Win32_VideoController`, `Win32_BIOS` and `Win32_BaseBoard`, null where a value cannot be read. `machine_id` is cut from a SHA-256 of the SMBIOS UUID (or of the host name when the UUID is unreadable), so it is stable and carries no readable identifier. The real host name is written, as the bundle contract decides; redaction is a later step. `tools[]` lists the PowerShell host, `wevtutil.exe`, the collector script and the helper, each with the SHA-256 of the bytes on disk, which is how a bundle states which version of a collector wrote it.

## How status is decided

Each source gets exactly one measurement status, decided by the collector from what it saw.

| Status | When |
|---|---|
| `observed` | The read finished within the deadline and the caps, every record was exported completely, and there is at least one. |
| `observed_zero` | The read finished, zero records matched, and a record at or before the window start is known to be retained (for a channel, its oldest record; for a WMI history, one row found by a separate bounded probe). That condition is the proof of a quiet window: a log that wrapped or was cleared looks exactly like a quiet one. |
| `not_collected` | The source could not be opened: the account lacks read access, or the preflight failed another way. The entry carries the message from Windows. No export file is written. |
| `unsupported` | The channel or class does not exist on this machine. |
| `capture_failed` | The read started and failed; or it did not finish before the deadline; or it stopped at a record that could not be exported completely; or the export reached a cap; or zero records matched and there is no proof of coverage (the channel is empty, the probe did not complete); or zero records matched on a source whose provider Microsoft does not document (`tdr-events`, provider `Display`, until verified); or a snapshot class returned no instances. |

A failed source leaves no primary export behind, with one exception: an export cut at a cap is kept, because it is a complete set as far as it goes, and the status reason says it was capped. Nothing under `raw/` can therefore be read as "zero records" unless the source is `observed_zero`. A read that timed out or stopped at an incomplete record has its partial export removed.

The clock collector applies them to a live session under the clock calibration exception of [timestamps.md](../../docs/contracts/timestamps.md) section 3: two or more pairs through the high resolution counter are `observed`, with every pair not taken (a missed slot, the stop pair after a failed read or a passed deadline) counted in `missing_pairs` and the expectation reported unmet; fewer than two pairs are `capture_failed` with no samples kept; a managed timer that is not the high resolution counter is `unsupported` for both sources; zero marks in a file that stood open from the start pair to the end of the session is `observed_zero`. The three source types of the RF survey apply the same rules to what they read:

| Type | `observed` | `observed_zero` | `not_collected` | `capture_failed` |
|---|---|---|---|---|
| command (netsh) | exit code 0, output present, at least one record by the language independent count (interfaces by GUID, access points by distinct address pseudonyms, profiles by valued lines, driver blocks by unindented header lines) | exit code 0 and zero records, when the definition says zero is a legitimate observation (interfaces, drivers, profiles: a PC without a wireless interface or a saved profile) | `netsh.exe` is not where Windows keeps it | the process could not start, did not finish before the deadline (it is stopped), exited with a code other than 0 (the reason carries its message), printed nothing, printed more than the cap while it was being read (the process is stopped at once and only a 4096 character diagnostic head is kept, so memory is bounded by the cap), or printed zero records when zero is not accepted (networks: the reason starts with `zero records:` and names location consent) |
| file | the file exists, is readable and fits the cap; the summary (size, creation and last write time, hash, counts, never the text) is the primary | never | the file does not exist (with the hint how the owner creates it) or the account may not read it | the file is above the cap, or reading it failed for another reason |

The `script` source of `presentmon-frames` has its own table, in "How status is decided for this source" above; it never reports `observed_zero` and never keeps a primary for a failed capture.

The range a status speaks for is `raw_time_range` in the manifest entry. It starts at the requested window start, or at the oldest retained record when the log does not reach back that far. In that second case `enabled.options.window_start_utc` differs from `requested.options.window_start_utc`, a note in the manifest and on stderr says so, and nothing is claimed before that time. This is an interpretation of the contract worth stating: the status describes what the collector saw over the range it names, and the later validator's adequacy check ("raw time ranges cover the scenario window") is what refuses a bundle whose range is too short for the question asked of it.

The query interval is fixed before the query runs. The collector takes one end time, `window_end_utc`, cut to the millisecond, and writes both ends into the query as xs:dateTime literals: `TimeCreated[@SystemTime >= '<start>' and @SystemTime <= '<end>']` selects exactly the interval from `window_end_utc` minus the window to `window_end_utc`, both ends inclusive. `SystemTime` is declared `dateTime` in the event schema ([TimeCreated element](https://learn.microsoft.com/en-us/windows/win32/wes/eventschema-timecreated-systempropertiestype-element)) and the comparison operators are in the XPath subset the event log accepts ([Consuming events](https://learn.microsoft.com/en-us/windows/win32/wes/consuming-events)); the same page says a result set also receives matching events raised while it is enumerated, which is why the interval has an upper bound. The literal has three fractional digits, the text `Get-WinEvent` writes for its `StartTime` and `EndTime` keys ([GetEventCommand.cs](https://github.com/PowerShell/PowerShell/blob/master/src/Microsoft.PowerShell.Commands.Diagnostics/GetEventCommand.cs), `SystemTimePeriodTemplate`), and the window end is cut to that precision before anything records it, so the manifest and the query name one instant. The form that page documents for a fixed instant, `timediff(@SystemTime, <FILETIME number>)`, is not used: on the gaming PC it was accepted when the query opened and failed at the first read on every channel (verification item 35). `requested.options.window_start_utc` and `window_end_utc` are that interval, and `raw_time_range` ends at `window_end_utc`. For a WMI history the same interval is a WQL filter on the time property with CIM DATETIME literals, and the coverage probe asks for one row before the window start.

Every read is bounded. Event log records are pulled one at a time with `EventLogReader.ReadEvent(TimeSpan)` carrying the time left before the source deadline; the oldest record probe uses the same call once. A pull that returns nothing after the deadline has passed is treated as a timeout, not as end of stream, because the two cannot be told apart. WMI reads run under `Get-CimInstance -OperationTimeoutSec`, which Microsoft documents as the wait for a response rather than a limit on the whole enumeration, so the source deadline is also checked on every row returned and a slow enumeration that passes it is a timeout. Rows are streamed through the caps, so a provider that never stops producing is cut at `-MaxEvents` or `-MaxArtifactBytes`; a producer stopped that way is `capture_failed` with the capped rows kept.

The binary `.evtx` export is secondary. When `wevtutil epl` fails or exceeds the byte cap, the file is removed, the failure is recorded in `enabled.options` and in the notes, and the source's status is unchanged, because `events.json` already holds the complete XML of every record.

## Read only posture

The collectors read event channels, read WMI classes, read documented registry values (opened for reading with `KEY_READ`; a missing key is recorded absent and never created, a refused key is unknown and never absent), read device properties, read the processor topology, read a few known files and folders, read the two clocks, and hash files. They change no setting, clear no log, start no service, open no network connection, request no Wi-Fi scan themselves (what netsh does is verification item 21), request no timer period, connect to and disconnect from nothing, and touch no process other than the ones they start. The clock collector waits with `Start-Sleep` between its slots, reads the two clocks in a bounded busy loop of at most 100 ms of the counter once per pair (to take the pair at the instant the system clock changes), appends to its own samples and marks files inside the output directory, and renames its live marks file once; the mark command appends one line to that file and does nothing else. The programs they start on purpose are `wevtutil.exe` with the `epl` (export) verb, `netsh.exe` with exactly four `wlan show` listings, `powercfg.exe` with exactly five listings (`/list`, `/getactivescheme`, `/aliases`, `/query`, `/qh`; allowlists in `tests/test_collectors_static.py` and `tests/test_collector_bundles.py`, so neither the report generators nor any verb that sets a scheme or a value can pass), the inbox `wpr.exe` with exactly five verbs (`-status`, `-profiles`, `-start`, `-stop`, `-cancel`; no boot trace, no marker, no configuration change) on the one session `dpcisr-trace` or `diskio-trace` owns, named by its own `-instancename` so a stop or cancel can never reach another recording, the inbox `tracerpt.exe` with the one `<trace> -summary <file> -y` action (for `diskio-trace`, the one `<trace> -o <dump> -of XML -summary <file> -y` action, "The diskio-trace sources" above), a hash pinned `xperf.exe` with the one `-i <trace> -a dpcisr` action, and, for `presentmon-frames` only, the same `wpr.exe` with `-start`, `-status`, `-stop` and `-cancel`, every call ending in `-instancename wf-presentmon-frames`, and the pinned PresentMon console binary with `--etl_file`, `--output_stdout`, `--qpc_time` and `--process_name` (never a live option, never `--output_file`; the Pester suite and `tests/test_collector_bundles.py` check the recorded runs), directly and without a shell, through one process runner that stops them at the deadline or at the output cap; they never launch Process Lasso, IRQControl, LatencyTest, Stutter Guard or its timer helper. A trace session is the one thing a collector starts that outlives a process (the kernel sessions `dpcisr-trace` and `diskio-trace` each own and the WPR instance `wf-presentmon-frames` that only `presentmon-frames` starts), and each is stopped on every exit path, cancelled whenever its own instance does not read as idle, and its final state recorded (an unconfirmed end is a failure). In addition, `config-snapshot` compiles its two native declarations with `Add-Type`, documented as generating an in-memory assembly; whether the Windows PowerShell 5.1 compiler behind it starts a compiler process or writes temporary files is not documented on Learn and is unverified (Interface, verification item 57). That is the one piece of code generation in this directory, and its native surface is exactly the eight imports named there, read calls all, with the search path bound to the system directory ([CA5392](https://learn.microsoft.com/dotnet/fundamentals/code-analysis/quality-rules/ca5392)). The only files they delete are their own exports inside the output directory (an `.evtx` that failed or exceeded the cap, a `records.json`, `output.txt`, report copy, protected copy, `devices.json`, `keys.json`, `listing.json`, `topology.json`, failed `dpcisr.txt`, oversized summary, `frames.csv`, `samples.jsonl` or marks file that must not be left behind), the private folder that held a kernel trace (and, for `diskio-trace`, its XML dump) and the `trace.etl` and WPR temporary folder of the frame recording, none of which leaves the machine. `tests/test_collectors_static.py` and `tests/test_collector_bundles.py` enforce these lists. They do not inspect, attach to, or enumerate game processes beyond reading the system process list through the WMI provider with the properties that list carries (verification item 60); nothing here opens a handle to, injects into, overlays, suspends, or changes the priority or affinity of a running game, and the native adapters open no process either, only a device information set, a device's registry key and the topology query; `presentmon-frames` reads its recording offline with a PresentMon that opens no process ("Why live PresentMon is not used" above; what WPR itself opens is verification item 51). Even so, take a config snapshot with the game and its anti-cheat closed: no vendor documents how an anti-cheat treats a WMI provider's work on its behalf, and the collector cannot answer for it. A standard account can be denied any of these keys by an access control list Microsoft does not document; a denial is recorded as unknown and is never retried with elevation, other rights or a changed ACL.

```
tools/pwsh/pwsh -NoProfile -File collectors/windows/tests/New-FixtureBundles.ps1
```

The fixture content is invented in `tests/SyntheticScenarios.ps1`. Nothing captured from a real machine is ever committed.
