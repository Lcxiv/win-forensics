# Windows collectors

Named, read only PowerShell collectors, one per question. Each writes one bundle that follows [docs/contracts/bundle.md](../../docs/contracts/bundle.md) and records measurement status the way [docs/contracts/measurement-status.md](../../docs/contracts/measurement-status.md) requires: a source the account could not read becomes a status with a reason, never an empty result that could be read as "nothing happened".

They run on the Windows PC as a dedicated standard account that is a member of Event Log Readers, started over SSH by a forced command dispatcher. The dispatcher, the setup script, and the transport belong to the front door work and live outside this directory. Nothing here asks for Administrator. The history collectors need nothing more than Event Log Readers; the one live capture, `presentmon-frames`, records an ETW trace, which Microsoft grants to elevated administrators and to members of Performance Log Users, and says what is not yet known about running its controller as such a member (the section below). The questions that need Administrator are listed under "Needs elevation" and wait for the elevated scheduled task.

Version 1.2.0 (`Get-WfCollectorsVersion` in `_common.ps1`; each collector also carries its own version, recorded in the manifest as the scenario version). 1.1.0 added three source types to the helper for the RF survey: a fixed `netsh` query (`command`), one known file copied read only (`file`), and present Plug and Play devices with their parent chain (`pnp`), plus the pseudonyms that keep network names and hardware addresses out of a bundle. 1.2.0 adds the `custom` source type (a source function the collector script itself defines, dispatched by name, so a live capture keeps its session control in its own file), Performance Log Users membership in the account record, `Get-WfBinaryInfo` (the adapter that reads an operator supplied executable's size, SHA-256 and version strings before a collector runs it), `Get-WfWprPath` and `Wait-WfSeconds` (the recording window of a live capture, which the synthetic backend passes on its own clock).

## Interface

A collector is a standalone script for Windows PowerShell 5.1:

```
powershell.exe -NoProfile -NonInteractive -File <install directory>\<name>.ps1 -OutputDirectory <path>
```

- `<name>` matches `^[a-z][a-z0-9-]{1,40}$`. The shared helper `_common.ps1` must be installed next to the collectors; its name starts with an underscore so it can never match that pattern and can never be dispatched. Every file a collector needs at run time is a `.ps1` file directly in this directory. The `tests` subdirectory is not needed on the PC.
- `-OutputDirectory` is the one parameter the dispatcher passes. The collector writes the bundle into it (creating it when it does not exist) and writes nowhere else, not even to the temp folder. It refuses a directory that already holds a `manifest.json` or a `raw` directory, because `raw/` is immutable after capture.
- It never prompts. `-OutputDirectory` is deliberately not declared `Mandatory`, because a missing mandatory parameter makes an interactive session prompt; a missing value is reported as a failure instead.
- The last and only line on stdout is the summary: `{"collector":"<name>","status":"ok|partial|failed","bundle":"<OutputDirectory>","artifacts":<count>}`. It is plain ASCII (other characters are written as JSON escapes), so console code pages cannot damage it. `bundle` is the `-OutputDirectory` value exactly as given and `artifacts` is the number of files listed in the manifest. The same line is stored in `logs/summary.json`, also when the run fails after the directory was laid out (then `logs/collector.log` says what happened and no manifest exists). A directory the collector refuses, or cannot create, gets nothing.
- Diagnostics go to stderr and to `logs/collector.log`.
- The exit code is the script's own `exit`, which `powershell.exe -File` returns as the process exit code ([about_PowerShell_exe](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1)). A dispatcher that uses `-Command` instead would flatten every failure to 1 and must add `exit $LASTEXITCODE` itself.

| Summary status | Exit code | Meaning |
|---|---|---|
| `ok` | 0 | The bundle is complete and every source is `observed` or `observed_zero`. |
| `partial` | 0 | The bundle is complete as a container (manifest written, every artifact checksummed). At least one source is `observed` or `observed_zero` and at least one is not; the manifest says which and why, and `capture.incomplete` is true. |
| `failed` | 1 | No source is `observed` or `observed_zero`, or the bundle could not be written. When a manifest could be written it is still there and still valid, and it records the reason per source. |

Optional parameters, for a person running a collector by hand (the dispatcher passes none, so the defaults are what runs):

| Parameter | Default | Meaning |
|---|---|---|
| `-WindowDays` | 30 | How far back to read, 1 to 365. Not on `driver-inventory`, which is a snapshot, nor on `presentmon-frames`, a live capture bounded by `-DurationSeconds`. On `rf-survey` it bounds the WLAN AutoConfig channel only. |
| `-MaxEvents` | 5000 (20000 for `driver-inventory`) | Cap on records per source, 1 to 100000. On `rf-survey` it also caps the devices of a `pnp` source. Not on `presentmon-frames`. |
| `-MaxArtifactBytes` | 67108864 (64 MiB) | Cap on the size of one export, 1 MiB to 1 GiB. It is enforced against the bytes actually written, never estimated. On `presentmon-frames` it is the recording's `MaximumFileSize` in whole megabytes (ETW stops a sequential session at that size, so the cap holds during the recording, not only after it) and the cap on the CSV PresentMon writes from the recording. |
| `-TimeoutSeconds` | 300 (80 for `rf-survey`) | Deadline for reading one source, 1 to 3600. Every read runs under it: the event log query, the oldest record probe, the WMI query with its operation timeout and a deadline check on every row it returns, `wevtutil`, `netsh`, and the device property reads. A read that does not finish in time is `capture_failed`. `rf-survey` has ten sources and the dispatcher stops a collector after 900 seconds, so its default is 80 (10 times 80 is 800). Not on `presentmon-frames`, whose deadlines follow from `-DurationSeconds`. |
| `-WlanReportPath` | empty | `rf-survey` only: where the WLAN report is, when `netsh wlan show wlanreport` printed a location other than the conventional one under ProgramData. |
| `-DurationSeconds` | 60 | `presentmon-frames` only: how long the ETW recording runs, 5 to 240. The other phases have fixed deadlines (start 60 s, each status read 30 s, stop and merge 180 s, the offline read 240 s, a cancel 60 s), so the longest run is 240 plus 600 seconds, inside the dispatcher's 900. |
| `-ProcessName` | empty | `presentmon-frames` only: process names PresentMon keeps when it reads the recording, each passed as one `--process_name` (letters, digits, `.`, `_` and `-`, not starting with `-`, at most 8 names). The recording itself is always of every process. Empty keeps every presenting process; see "Process names" below for why that is the default. |
| `-PresentMonPath` | empty | `presentmon-frames` only: where the pinned PresentMon console binary is. Empty means `<install root>\tools\PresentMon-2.6.0-x64.exe`, two directories above the collector (`C:\ProgramData\win-forensics\tools` on the PC). |

A value outside its range produces a `failed` summary and no bundle.

### The presentmon-frames source

One source, `presentmon_frames`, of manifest kind `presentmon`, required. It is a live capture in two steps, both passive, with the game process never opened by anything this collector runs that is documented, and one open question named as such:

1. Windows Performance Recorder (`wpr.exe`, which "ships together with the Windows operating system (Windows 8.1 or a later version) and doesn't require additional installation", [Troubleshoot processes and threads by using WPR and WPA](https://learn.microsoft.com/troubleshoot/windows-server/support-tools/support-tools-xperf-wpa-wpr)) records the ETW providers and event ids PresentMon 2.6.0 enables for its default options into a file inside the bundle, from a profile the collector writes, for `-DurationSeconds`, under the collector's own WPR instance name. WPR is an ETW controller: it enables providers and writes the session's buffers to a file. Whether it opens a handle to any presenting process while it does so is not documented by Microsoft, so this README does not claim it either way; verification item 33 is the check.
2. The pinned PresentMon console application reads that file with `--etl_file` and prints its CSV on stdout (`--output_stdout`), which the collector keeps as `raw/presentmon_frames/frames.csv`. In that mode PresentMon opens no process: at tag v2.6.0, `PresentMon/OutputThread.cpp` `QueryProcessName()` calls `OpenProcess` only when `args.mEtlFileName == nullptr` (lines 294 to 319), and `PresentMon/MainThread.cpp` enables `SeDebugPrivilege` only for realtime analysis (lines 255 to 277: "If we are processing an ETL file we don't need elevated privilege, but for realtime analysis we need SeDebugPrivilege in order to open handles to processes started by other accounts"). Process names come from the recorded Microsoft-Windows-Kernel-Process events (`PresentData/PresentMonTraceConsumer.cpp` `HandleProcessEvent`).

The recording itself never leaves the PC: it is read for its header and by PresentMon, then deleted ("Privacy" below says why). Everything PresentMon and WPR related is in `presentmon-frames.ps1` (the helper only dispatches to it and runs the processes), so the facts below can be checked against one file.

#### Why live PresentMon is not used

PresentMon's realtime mode opens a `PROCESS_QUERY_LIMITED_INFORMATION` handle to every presenting process, the game included, and keeps it for the whole capture: `OutputThread.cpp` `QueryProcessName()` (lines 294 to 319 at v2.6.0) calls `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, FALSE, processId)` for each newly seen presenting process whatever `--process_name` says, because the name filter needs the name first; the handle is polled with `GetExitCodeProcess` (lines 212 to 231) and closed at the end (lines 639 to 646). `MainThread.cpp` calls `EnableDebugPrivilege()` on every realtime run (lines 266 to 277; `Privilege.cpp` adjusts the process token). The access right is the one Microsoft lists as "Required to retrieve certain information about a process (see GetExitCodeProcess, GetPriorityClass, IsProcessInJob, QueryFullProcessImageName)" ([Process Security and Access Rights](https://learn.microsoft.com/windows/win32/procthread/process-security-and-access-rights)); it is not a memory access right. The accepted intent for this work is no handle to the game at all, so the design records with a controller and gives PresentMon only the file. `tests/test_collectors_static.py` checks that no realtime option (`--timed`, `--session_name`, `--process_id`, `--terminate_after_timed`, `--terminate_existing_session`, `--stop_existing_session`, `--restart_as_admin`, `--hotkey`, `--delay`) and no `--output_file` appears in the script, and the Pester suite checks every process the runs start.

Before every run the collector reads the file's size and SHA-256 (`Get-WfBinaryInfo`) and compares both with the pin; it also records the version strings Windows reads from the file, which are never trusted in place of the hash. A missing file, a different hash or a different size is `not_collected` with the reason (the download URL and the pin are in it) and nothing is started, not even the WPR status probe. Because the recording takes a minute or more, the file is hashed a second time immediately before PresentMon is started, and a file that changed in between is not run (`capture_failed`, both hashes in `result.json`); a folder the account cannot write makes that swap impossible, the second hash makes it visible. The manifest's `tools[]` carries the binary and `wpr.exe` with the hashes that were measured, `raw/presentmon_frames/command.json` carries the pin, and `result.json` carries both comparisons. The owner checks the download the same way before placing it: `(Get-FileHash .\PresentMon-2.6.0-x64.exe -Algorithm SHA256).Hash -eq 'B2A706BC6AD475749E3B7E3409263AA1E6906D45BDCF993F6DBC0F660188F1AF'` must print `True`.

Why 2.6.0: it is the current release, and its notes list the removal of the experimental "Flash Injector" (a DLL and hooks that drew a flash in the target process on a mouse click, added in 2.3.1), so the pinned release carries no code that injects into a game. The notes of 2.5.0 (a release with no downloadable asset; the notes point to 2.5.1) list an "Anticheat Mitigation" item under ETW session management: the changes "enable PresentMon to gather data from certain titles that otherwise block ETW trace gathering". This README records that sentence as the vendor wrote it and draws no conclusion from it. It concerns PresentMon's own realtime session, which this collector does not use; whether a title that blocks that session also blocks, or is affected by, a WPR session recording the same providers is not documented by the vendor or by Microsoft, and verification item 34 (frames of the game appear in a recording made while it runs) is the only way to know for this machine.

#### What is recorded, and where it comes from

The profile (`raw/presentmon_frames/profile.wprp`, written by `Get-WfPresentMonProfileXml` and hashed as the manifest's `filter_hash`) enables the providers PresentMon 2.6.0 enables for the console application's default options (track display, GPU and input on; video, frame type, hybrid present, app timing, PC latency and D3D12 shader compilation off: `PresentMon/CommandLine.cpp` lines 380 to 416), taken from `PresentData/PresentMonTraceSession.cpp` `EnableProvidersListing()` (lines 795 to 993) and the event declarations under `PresentData/ETW/*.h`. For each provider the keyword is the OR of the enabled events' keywords (PresentMon's "any keyword" mask), the level the highest event level (0 is LogAlways; WPR treats a level of zero as every level), the event ids are the ones PresentMon filters in, and the capture state keywords are the ones PresentMon enables a second time with `EVENT_CONTROL_CODE_CAPTURE_STATE`. Two adjustments PresentMon makes are kept: the DxgKrnl Performance keyword is never used ("Never filter DxgKrnl events using the Performance keyword, as that can have side-effects with negative performance impact on some versions of Windows", lines 52 to 53), and the Dwm-Core Composition keyword is included next to Scheduling for Windows 10, where PresentMon swaps them (lines 34 to 36). PresentMon filters by event id as well (`EnableTraceEx2` with `EVENT_FILTER_TYPE_EVENT_ID`); the profile carries the same ids in an [EventFilters](https://learn.microsoft.com/windows-hardware/test/wpt/eventfilters) element with `FilterIn="true"` per provider ("EventFilters element enables event filtering through EVENT_FILTER_DESCRIPTOR, Type EVENT_FILTER_TYPE_EVENT_ID"), so the recording holds what PresentMon's own session would hold and no more.

#### The run, phase by phase

Every program runs through the helper's one process runner, directly and without a shell, with a deadline and a console cap. The WPR verbs and switches are the documented ones ([WPR Command-Line Options](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-command-line-options)): `-start <profile>` "Starts one or more profiles", `-filemode` "Specifies that recording is done in file mode", `-recordtempto <path>` "Specifies the temporary folder path that the recording is saved to", `-status [collectors [-details]]` "Displays the status of an active recording (if any)", `-stop <file> <description>` "Cancels and saves the recording initiated by WPR (if any)" with `-skipPdbGen`, `-cancel` "Cancels the current recording without saving the recorded data", and on every one of them `-instancename wf-presentmon-frames`: "Specifies a name to uniquely identify the tracing instance. This option can be applied to any commands that manipulate the logging session." and "-instancename must be the last parameter." The instance name is why this collector never sees, stops or cancels another WPR recording: an unnamed `wpr -cancel` never appears in the script (`tests/test_collectors_static.py` checks every argument string ends in the instance name), and a recording started by anything else, under any other name, is neither probed nor touched. Nothing else: the same test lists the WPR options that change a machine setting or configure a boot trace and checks none is in the script.

1. Preflight: the pin, `wpr.exe` present in System32, and `wpr -status -instancename wf-presentmon-frames` (30 s) to see that this collector's own instance is idle. The probe runs only after the pin matched. If the probe says a recording of this instance is in progress, it can only be a leftover of an earlier run of this collector that the dispatcher ended (the name is this collector's alone), so it is cancelled (`wpr -cancel -instancename wf-presentmon-frames`, with a manifest note) and probed again. A probe that fails, times out, or still shows the instance in progress is `not_collected` and nothing is started: the collector does not record when it cannot show that its own instance was idle.
2. `wpr -start "<bundle>\raw\presentmon_frames\profile.wprp!WfPresentMonFrames.Verbose" -filemode -recordtempto "<bundle>\raw\presentmon_frames\wpr-temp" -instancename wf-presentmon-frames` (60 s). The temp folder is inside the bundle, because a collector writes nowhere else; it is removed after the stop and again at the end of every path, a failed start included. A folder or recording that cannot be deleted (a session the collector could not stop still holds its file) does not stop the run: the source is `capture_failed` and a manifest note names what is still in the bundle and must be deleted by hand before the bundle leaves the PC. A refusal that says access denied is `not_collected` with WPR's words; any other failure to start is `not_collected` too (nothing was recorded); a start that was issued but timed out may have left the instance recording, so it is cancelled by name.
3. The window: `-DurationSeconds` pass (`Wait-WfSeconds`). Nothing runs.
4. `wpr -status collectors -details -instancename wf-presentmon-frames` (30 s): the recording must still be in progress, the loss counters are read ("Dropped event", documented as "The number of lost events since the recording was started" in [WPR How-to Topics](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-how-to-topics), and "Events Lost" per collector as the documentation's sample shows), and the provider lines under "Providers" are compared with the request: every strict provider must be listed with every requested keyword bit and a level at least the requested one, or the source is `capture_failed` ("the requested settings were not shown enabled"). The layout of a provider line is not documented; the collector reads `<name or GUID>: <keywords>: <level>` and verification item 25 settles it. Microsoft: "Each session keeps a record of the number of events discarded (see the EventsLost member)" ([EVENT_TRACE_PROPERTIES](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-event_trace_properties)); PresentMon's realtime mode reads the same counter with `EVENT_TRACE_CONTROL_QUERY` before it stops (`PresentMonTraceSession.cpp` `Stop()`).
5. `wpr -stop "<bundle>\raw\presentmon_frames\trace.etl" "win-forensics presentmon-frames" -skipPdbGen -instancename wf-presentmon-frames` (180 s, the merge included), then `wpr -status -instancename wf-presentmon-frames` (30 s) to confirm the instance is idle. The stop is confirmed only when the stop exited 0 and that status exited 0 and reported no recording; otherwise `wpr -cancel -instancename wf-presentmon-frames` (60 s) is sent, the source is `capture_failed`, and when the cancel did not complete either, the reason and a manifest note say the recording may still be active and how to stop it. The collector's own clock is read just before the start was issued and just after the stop returned; those two instants are the source's `raw_time_range`, a bound that contains the recording.
6. The file's own header is read (`Read-WfEtlHeader`) and the file is hashed. The first buffer of an ETW log file starts with a 72 byte buffer header and then the log file header event: a 32 byte system trace header (hook id 0) followed by [TRACE_LOGFILE_HEADER](https://learn.microsoft.com/windows/win32/api/evntrace/ns-evntrace-trace_logfile_header), "the raw data format of the trace information data in the header of an ETW log file". Microsoft documents TRACE_LOGFILE_HEADER and the [EventTrace_Header](https://learn.microsoft.com/windows/win32/etw/eventtrace-header) class, not the two headers before it; those are what the reverse engineered descriptions of the format call the WMI buffer header and the system trace header, and what PresentMon's own regression recordings show. The first 4096 bytes of the vendor's `Tests/Gold/test_case_0.etl` at v2.6.0 (whole file SHA-256 `7127ed1325fd9d179604df2a7356dc3c4cb805cb15220175e34b4faf918a31be`; MIT licence) are committed as `fixtures/presentmon/gold-test_case_0.first-buffer.etl` (SHA-256 `d7d2463ec3f97c59db6815fb936a73ecbdaae5b782ec81e597b1946b97a4a8fc`), the only `.etl` in the repository and a format fixture, not a capture: the Pester suite reads it with the collector's own reader and `tests/test_presentmon.py` checks every field at its offset, and the synthetic recording the fixture bundles were made from is laid out to match it. The header gives `EventsLost` and `BuffersLost`, the clock the events were stamped with (`ReservedFlags`: 1 is the performance counter, 2 system time, 3 the CPU cycle counter, per the `ClientContext` table of [WNODE_HEADER](https://learn.microsoft.com/windows/win32/etw/wnode-header)), `PerfFreq`, the Windows version and build, and the session's `StartTime` and `EndTime`. Every field is checked for plausibility; a header that does not read this way is `capture_failed` ("log file header could not be read"), because loss and clock would be unknown. A session whose `EndTime` is more than five seconds before the stop was requested closed early (it reached its file cap or died) and is `capture_failed` too. The merge WPR performs on `-stop` may change the header; verification item 27 is a real first buffer from the PC.
7. Any loss, from any source, is `capture_failed`: the largest of the controller's "Dropped event" count, the sum of its "Events Lost" lines and the header's `EventsLost` is the manifest's `events_lost` (each source is also recorded under `events_lost_sources`), a non zero `BuffersLost` fails as well, and so does a status with no counter line at all. PresentMon is not run over a recording with loss, over one above the artifact cap, or over one whose settings were not shown enabled.
8. The binary is hashed again, then `PresentMon-2.6.0-x64.exe --etl_file "<trace.etl>" --output_stdout --qpc_time [--process_name <name>]...` (240 s). Each option is in the console README at v2.6.0: `--etl_file path` "Analyze an ETW trace log file instead of the actively running processes."; `--output_stdout` "Write CSV output to STDOUT." (`CommandLine.cpp` lines 556 to 557 then set console output to none, so stdout carries the CSV and nothing else; `PrintWarning` and `PrintError` write to stderr, `Console.cpp` `PrintColor` line 340; `--no_console_stats` is therefore not needed and not passed); `--qpc_time` "Output the CPU start time as a performance counter value." (the column is then `CPUStartQPC`; with `--etl_file` the values are the recording's own timestamps); `--process_name name` "Only record processes with the specified exe name. This argument can be repeated to capture multiple processes." The process runner captures stdout under `-MaxArtifactBytes` and stops PresentMon at the cap, so the CSV has a live byte budget; the text is written as `frames.csv` in UTF-8 without a byte order mark (the console output code page it was decoded with is in `command.json`, `csv_console_code_page`; verification item 36). PresentMon exits 0 when the file is read (`MainThread.cpp` line 474), 6 when it cannot open it (lines 361 to 383, "error: failed to start trace session: invalid --etl_file." for a corrupt file). It writes the CSV header at the first frame it emits (`CsvOutput.cpp` `UpdateCsvT`, lines 1354 to 1394: `*fp = stdout` and `WriteCsvHeader` inside `if (*fp == nullptr)`), and it discards the result of `ProcessTrace` (`ConsumerThread.cpp` lines 28 to 31: "However, it seems to always return ERROR_SUCCESS"), so an empty output cannot be told from a read that stopped early, and the collector never calls an empty output a quiet window: zero frames is `capture_failed`. Its stderr is read for "warning: N overflowed present events detected" (`MainThread.cpp` lines 455 to 459, printed in every mode when the consumer threw presents away because its completed ring was full), which is `capture_failed` with the count in `enabled.options.presentmon_overflowed_presents`, and any other warning or error line fails the source as well.
9. The recording is deleted ("Privacy"). `recording.json` keeps its size, SHA-256, header, loss counters, the settings comparison and PresentMon's warnings.

What is kept: `frames.csv` (role primary; the CSV PresentMon printed, absent unless the source is observed), `recording.json` and `result.json` (role report), `profile.wprp` and `command.json` (role config), and `console.txt` (role log; every program's stdout and stderr, labelled, verbatim, except the CSV, which is noted by size). The manifest's `command` is the PresentMon command line; the WPR command lines are in `requested.options.wpr_commands`, recorded with bundle relative paths (the processes received the absolute paths in double quotes). `buffers` records the 64 KB by 256 geometry and file mode; `enabled.providers` and `enabled.keywords` are what `wpr -status` listed.

#### How status is decided for this source

| Status | When |
|---|---|
| `not_collected` | The binary is missing or its SHA-256 or size differs from the pin; `wpr.exe` is missing; the collector's own WPR instance could not be shown idle (the probe failed, timed out, or a leftover recording could not be cancelled); or `wpr -start` did not complete (a refusal that says access denied carries WPR's words and the groups Microsoft documents). Nothing was recorded. |
| `observed` | `wpr -status` reported the recording in progress at the end of the window with zero loss and every strict provider enabled with its keywords and level, `wpr -stop` saved a file below the cap whose header reads with zero events and buffers lost and a session that ran until the stop, the instance was confirmed idle, the binary still matched the pin, PresentMon exited 0 reading the file with no warning, and its CSV carries `Application`, `ProcessID`, `CPUStartQPC` and at least one frame row. |
| `capture_failed` | Everything else after a start that completed: the recording was not in progress at the end of the window; events or buffers were lost (from any of the three counters); no loss counter could be read; the header could not be read; the session closed before the stop was requested (its file cap or another cause); the merged file is above the cap; the settings were not shown enabled; the stop was not confirmed (cancelled instead); the binary changed before the read; PresentMon did not start, timed out, printed above the cap, exited with a code other than 0, warned, or threw presents away; the CSV header lacks `CPUStartQPC`; or no frame was emitted, scoped or not. Nothing is kept as a primary in any of these cases, and the recording is deleted in every case. |

There is no `observed_zero` for this source. The pinned binary gives no way to tell "no process presented" from "the read stopped early", and a desktop with a compositor running presents in any case, so an empty output is a failure to show frames, not a quiet window. The status contract's rule that a target process not alive across the window is `capture_failed` is applied to the scoped case for the same reason.

#### Process names

PresentMon's offline read names a process from the recorded Kernel-Process events (`HandleProcessEvent`: ProcessStart, ProcessStop and ProcessRundown of Microsoft-Windows-Kernel-Process, or the kernel's own process events). The profile asks for the rundown of processes already running at the start (`CaptureStateOnStart` on Kernel-Process), which is how a game that was started before the recording gets its name. A process with no such event in the recording is written as `<unknown>` with its process id, the same spelling PresentMon's README documents for its realtime mode, and `--process_name` cannot match it. PresentMon's own session tolerates access denied on this provider (`EnableProvidersListing`, line 814), so the profile does not make it strict either; when the recording holds no Kernel-Process events the frames are still there under `<unknown>`. That is why the default keeps every presenting process: the rows are separated by `ProcessID` and swap chain address whatever the name says. No handle to any process is opened to learn a name.

#### Elevation and the account

Microsoft: "Only users running with elevated administrative privileges, users in the Performance Log Users group, and applications running as LocalSystem, LocalService or NetworkService can control event tracing sessions. To grant a restricted user the ability to control trace sessions, add them to the Performance Log Users group", with the warning that membership "allows a user to control event tracing sessions that can expose potentially sensitive system and application information. Grant membership only when required, limit it to the minimum number of users and the shortest practical time, and remove users promptly when access is no longer needed" ([Controlling Event Tracing Sessions](https://learn.microsoft.com/windows/win32/etw/controlling-event-tracing-sessions)). Performance Log Users is the well known group S-1-5-32-559 ([security identifiers](https://learn.microsoft.com/windows-server/identity/ad-ds/manage/understand-security-identifiers)); the collector records whether the account is a member and whether it is elevated (`WindowsPrincipal.IsInRole`, the same call the account record already makes for Event Log Readers), in the manifest notes and in `result.json`.

Whether `wpr.exe` itself accepts a Performance Log Users member is not stated by Microsoft; its instructions run WPR "from an elevated (run as Administrator) Command Prompt window" ([Record and View TraceLogging Events](https://learn.microsoft.com/windows/win32/tracelogging/tracelogging-record-and-display-tracelogging-events)). Microsoft-Windows-Kernel-Process is a kernel provider that PresentMon's own code expects a non administrator to be refused. So the honest statement is: the collector works as written for an elevated run; for the standard collector account, the owner adds it to Performance Log Users and verification item 23 says whether WPR records for it, and item 24 whether the process names arrive. The collector never elevates and never adds itself to a group. Until the elevated scheduled task exists, a refusal is `not_collected` with WPR's words.

Running PresentMon itself needs no right at all in this design: reading a file is not controlling a session, and `MainThread.cpp` skips `EnableDebugPrivilege()` for `--etl_file`.

#### The anti-cheat position

The captain plays Fortnite under Easy Anti-Cheat and Overwatch under Blizzard's protection. What the vendors document, and no more:

- The only processes this collector holds handles to are its own children (wpr and PresentMon, through the helper's runner). WPR is an ETW controller; what it does beyond controlling the session is not documented, and whether it opens a handle to any presenting process during a recording is verification item 33 (handle auditing or Sysmon's process access event against a harmless presenting process), not a claim of this README. ETW providers in the game's process (DXGI, D3D9) write to session buffers the kernel owns; nothing here attaches to, injects into, overlays, suspends or reprioritises the game, and no setting is changed.
- PresentMon's documentation describes ETW collection ("a library that performs the lowest-level collection and analysis of ETW events", README at v2.6.0). Its realtime mode's process handles (quoted above from its source) are the reason that mode is not used. The 2.6.0 release notes list the removal of the Flash Injector, the one injecting component the project ever shipped; the 2.5.0 notes' "Anticheat Mitigation" item concerns its realtime session and is quoted above without conclusion, with item 34 as the only test that applies to a WPR recording.

#### The dispatcher verb

The next kit install makes this collector the SSH verb `collect-presentmon-frames` with its defaults (a 60 second recording, every process, the pinned binary at `C:\ProgramData\win-forensics\tools`), because the dispatcher offers every collector in the directory. At the default window the helper's per source deadline is 750 seconds, inside the dispatcher's 900; a window near the 240 second maximum can pass 900 only if every phase runs to its deadline, and then the dispatcher ends the collector and the next run finds and cancels the leftover instance (phase 1). Until the binary is in place the verb answers `not_collected` with the download hint, and until the account can control ETW sessions it answers `not_collected` with WPR's words.

#### Privacy

The recording never leaves the PC. `wpr -stop` merges the session file into the saved trace, and a merge adds machine specific information to it: the WPR profile schema's [TraceMergeProperties](https://learn.microsoft.com/windows-hardware/test/wpt/tracemergeproperties) element lists the custom events a merge can add, among them `NetworkInterface`, and the ETW network configuration event [SystemConfig_NIC](https://learn.microsoft.com/windows/win32/etw/systemconfig-nic) carries the adapter's physical address (`PhysicalAddr`), its IP addresses (`IpAddresses`), its DNS servers and its description. Microsoft's own caution applies: "Recordings can contain personally identifiable or security-related information. This includes paths to files that the recording accesses, or registry access and process names. Be cautious when you share recording files." ([WPR How-to Topics](https://learn.microsoft.com/windows-hardware/test/wpt/wpr-how-to-topics)). This project keeps hardware and network addresses out of every bundle by construction, so the collector reads the recording on the PC (its header, then PresentMon) and deletes it, and the bundle carries what was read from it: the CSV, the header fields in `recording.json` (session name, Windows version and build, processor count, counter frequency, start and end, loss counters, the file's size and SHA-256), the settings `wpr -status` listed, and the console text of the runs. Whether any of those carries an address on a real machine is verification item 35; nothing in the documented output of `wpr -status` or in PresentMon's CSV is one. The CSV holds the presents of every process by executable name and swap chain address, which is what the frame analysis needs. No pseudonym rule of the RF survey applies to it and the manifest's privacy note is not written for this collector.

USB port speed is not in the export because Windows does not expose it through a documented property a standard account can read: "the USB driver stack that Windows loads correlates to the type of host controller, not to the connected device's speed" ([USB in Windows FAQ](https://learn.microsoft.com/windows-hardware/drivers/usbcon/usb-faq--introductory-level)). What the tree does show is which controller serves a port: `USBXHCI` and `USBHUB3` are the USB 3 (xHCI) stack, `usbehci` and `usbhub` the USB 2 stack ([USB host side drivers in Windows](https://learn.microsoft.com/windows-hardware/drivers/usbcon/usb-3-0-driver-stack-architecture)), and the analysis says exactly that much.

Event Log Readers is the documented grant: "Members of this group can read event logs from local computers" ([security groups](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups)). An SSH session keeps the privileges of the account that authenticated and adds none ([SSH remoting](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/ssh-remoting-in-powershell)), so the group membership is the whole authorisation. A machine can carry a different descriptor than the documented default (a `CustomSD` value or a policy), which is why each event log source also records the channel's actual security descriptor when the account may read it.

Deliberate omissions inside those questions: event ids 12, 13 and 19 from Microsoft's restart history list are left out of `bugcheck-history` because many providers share them; the `Microsoft-Windows-Kernel-WHEA` channels are not read because Microsoft Learn documents neither their content nor their access; per application crash dumps belong to the later step that sets the Windows Error Reporting dump keys.

```
  raw/<source id>/query.json     WMI source: class, namespace, properties, WQL filter, window, caps (role config)
  raw/<source id>/records.json   WMI export, a JSON array (role primary)
  raw/<source id>/command.json   netsh source: executable, exact arguments, limits, encoding, pseudonym rules (role config)
  raw/<source id>/result.json    exit code, timing, byte counts, protected stderr, replacement counts, line structure (role report)
  raw/<source id>/output.txt     the protected standard output, LF line endings (role primary)
  raw/<source id>/source.json    file source: path, cap, pseudonym rules (role config)
  raw/<source id>/result.json    whether the file existed and could be read, size, last write time, replacement counts (role report)
  raw/<source id>/<file name>    the protected copy (role primary)
  raw/<source id>/query.json     pnp source: classes, instance prefixes, property keys, caps (role config)
  raw/<source id>/result.json    devices present, selected, added as ancestors, property read failures (role report)
  raw/<source id>/devices.json   one element per device (role primary)
  raw/<source id>/command.json   presentmon source: the binaries with the pin, every command line, the providers, limits, citations (role config)
  raw/<source id>/profile.wprp   the WPR profile the recording was started with (role config, hashed as filter_hash)
  raw/<source id>/trace.etl      the recording wpr saved, untouched (role primary)
  raw/<source id>/frames.csv     the CSV PresentMon wrote from the recording, untouched; absent when no frame was emitted (role report)
  raw/<source id>/console.txt    what wpr and PresentMon printed on stdout and stderr, labelled, verbatim (role log)
  raw/<source id>/result.json    the pin comparison, every run, the file header, the CSV summary, the stop confirmation (role report)
  logs/collector.log             what the collector did
  logs/summary.json              the stdout line
```

A collector writes capture output only. It never writes `decoded/`, `evidence.jsonl`, `verdict.json`, or `validation.json`.

Every file under `raw/` is listed in the manifest with its byte count and SHA-256. The list is built by reading the directory after the source finishes, not from what the code meant to write, so an unlisted raw file cannot occur.

`events.json` elements carry the columns of `schemas/decoded/eventlog_events.schema.json` under the same names (`record_id`, `log_name`, `provider_name`, `event_id`, `version`, `level`, `level_display`, `task`, `task_display`, `opcode`, `keywords`, `time_created_utc`, `machine_name`, `user_id`, `process_id`, `thread_id`, `message`, `properties`) plus `xml`, the complete event XML from `EventRecord.ToXml()`. `time_created_utc` is the `SystemTime` attribute of that XML, cut to seven fractional digits. `message`, `level_display` and `task_display` depend on publisher metadata and locale and are null when Windows cannot render them. The XML is complete for every element of a successful primary export: a record whose XML cannot be produced stops the source, which becomes `capture_failed` and leaves no `events.json`. `scripts/decode_eventlog.py` turns these files into the `eventlog_events` table with `index:<n>;record:<id>` provenance; it decodes only primary artifacts the manifest lists for an observed event log collector, refuses a path that is missing, unlisted, or outside the bundle, and writes nothing in that case.

`records.json` elements are the requested properties of the WMI instance under their WMI names (only the documented properties the collector names are requested, so the provider hands over nothing else), with dates as ISO 8601 UTC text and string arrays kept as arrays. The driver export is shaped so a later decoder can emit `config_snapshot` rows of category `driver` (one row per device and property, `index:<n>` provenance), and `driver-inventory` also fills `machine.drivers` in the manifest from `Win32_PnPSignedDriver`.

`channel_state.json` holds the record count, the oldest retained record's number and time, the file size, the log mode, the maximum size, the isolation, and the security descriptor, each null when the account may not read it, plus which of the requested providers are registered on the machine.

`output.txt` is the text netsh printed, with CRLF turned into LF and nothing else changed except the pseudonyms below. `result.json` also carries `fields`, every line with a colon as line number, indentation, block, label and value, which is the language independent structure `scripts/decode_rf_survey.py` classifies (by English label, else by the shape of the value), and for the profiles query `profiles`, the saved names with their pseudonyms. The report summary (`report-summary.json`) holds size, time, hash and counts and never the text. `devices.json` elements carry the `Win32_PnPEntity` values under snake case names (`instance_id`, `class`, `class_guid`, `name`, `description`, `manufacturer`, `service`, `status`, `problem_code`, `present`, `hardware_ids`, `compatible_ids`) plus the device properties (`parent_instance_id`, `location_paths`, `location_info`, `address`, `container_id`, `bus_reported_description`, `enumerator`), `is_seed` (false for a device added as an ancestor) and `property_error`.

Network names and hardware addresses belong to the neighbours as much as to the owner, and a paired Bluetooth device is someone's phone or earbuds, so no bundle carries any of them in clear: not under `raw/`, not in `logs/`, not in `manifest.json`, and the analysis never writes one into `decoded/`, `evidence.jsonl` or `reports/`. The rules are complete by construction rather than by recognising known names:

- Netsh text: every hardware address (six hexadecimal pairs with colons or hyphens) becomes `mac-<first 12 hex of SHA-256(salt, address)>`, and every network name found by structure becomes `ssid-<first 12 hex of SHA-256(salt, name)>`. In a scan each network's name line is the unindented line with a colon above its address lines; in an interface listing it is the line whose label is `SSID` and, for a display language that translates that label, the labelled line just before the BSSID address line (netsh prints SSID, then BSSID); every learned name is also replaced wherever else it appears (the Profile line).
- Saved profiles are the one readable exception: `netsh wlan show profiles` lists the owner's own networks, so its text stays as printed and `result.json` maps each name to its pseudonym. That mapping is how the owner names his network at analysis time; a saved profile alone never makes a visible network his.
- Event records are reduced to their System section: no message, string properties null, EventData, UserData and RenderingInfo emptied. A name the run never learned can hide in any of those, so none of them is kept.
- The WLAN report is summarised, never copied, for the same reason.
- Bluetooth peer device nodes, and every node the `bluetooth_devices` row above names as belonging to a peer, have their name fields replaced by `name-<12 hex>` and their bare twelve digit addresses by `mac-` pseudonyms, in the instance id, the parent id, the hardware and compatible ids and the location text.

The salt is random per run and never stored: the same value maps to the same pseudonym inside one bundle, which is what the analysis needs (the owner's profile is the scanned network; the adapter's own address is the one in the interface listing), and to nothing outside it, so a dictionary attack on short network names has no salt to work with. The Pester suite writes neighbour names, an unseen name in the report and in an event's message, properties and XML, addresses and peer names into the synthetic machine and asserts that none of them appears in any file of the bundle; `tests/test_rf_survey.py` repeats that scan over the decoded tables, the evidence rows and the report.

The manifest's machine section is filled from `Win32_OperatingSystem`, `Win32_ComputerSystem`, `Win32_ComputerSystemProduct`, `Win32_Processor`, `Win32_VideoController`, `Win32_BIOS` and `Win32_BaseBoard`, null where a value cannot be read. `machine_id` is cut from a SHA-256 of the SMBIOS UUID (or of the host name when the UUID is unreadable), so it is stable and carries no readable identifier. The real host name is written, as the bundle contract decides; redaction is a later step. `tools[]` lists the PowerShell host, `wevtutil.exe`, the collector script and the helper, each with the SHA-256 of the bytes on disk, which is how a bundle states which version of a collector wrote it.

## How status is decided

Each source gets exactly one measurement status, decided by the collector from what it saw.

| Status | When |
|---|---|
| `observed` | The read finished within the deadline and the caps, every record was exported completely, and there is at least one. |
| `observed_zero` | The read finished, zero records matched, and a record at or before the window start is known to be retained (for a channel, its oldest record; for a WMI history, one row found by a separate bounded probe). That condition is the proof of a quiet window: a log that wrapped or was cleared looks exactly like a quiet one. |
| `not_collected` | The source could not be opened: the account lacks read access, or the preflight failed another way. The entry carries the message from Windows. No export file is written. |
| `unsupported` | The channel or class does not exist on this machine. |
| `capture_failed` | The read started and failed; or it did not finish before the deadline; or it stopped at a record that could not be exported completely; or the export reached a cap; or zero records matched and there is no proof of coverage (the channel is empty, the probe did not complete); or zero records matched on a source whose provider Microsoft does not document (`tdr-events`, provider `Display`, until verified); or a snapshot class returned no instances. |

A failed source leaves no primary export behind, with one exception: an export cut at a cap is kept, because it is a complete set as far as it goes, and the status reason says it was capped. Nothing under `raw/` can therefore be read as "zero records" unless the source is `observed_zero`. A read that timed out or stopped at an incomplete record has its partial export removed.

The three source types of the RF survey apply the same rules to what they read:

| Type | `observed` | `observed_zero` | `not_collected` | `capture_failed` |
|---|---|---|---|---|
| command (netsh) | exit code 0, output present, at least one record by the language independent count (interfaces by GUID, access points by distinct address pseudonyms, profiles by valued lines, driver blocks by unindented header lines) | exit code 0 and zero records, when the definition says zero is a legitimate observation (interfaces, drivers, profiles: a PC without a wireless interface or a saved profile) | `netsh.exe` is not where Windows keeps it | the process could not start, did not finish before the deadline (it is stopped), exited with a code other than 0 (the reason carries its message), printed nothing, printed more than the cap while it was being read (the process is stopped at once and only a 4096 character diagnostic head is kept, so memory is bounded by the cap), or printed zero records when zero is not accepted (networks: the reason starts with `zero records:` and names location consent) |
| file | the file exists, is readable and fits the cap; the summary (size, time, hash, counts, never the text) is the primary | never | the file does not exist (with the hint how the owner creates it) or the account may not read it | the file is above the cap, or reading it failed for another reason |
| pnp | the enumeration completed and at least one device matched the classes; every matched device and its ancestors are in the export | the enumeration completed with devices and none matched, when the definition says the class may be absent (Bluetooth) | the enumeration itself was refused | the enumeration failed or returned no device at all, the property reads did not finish before the deadline, the cap cut the export (kept), or no device matched a class that is never absent (USB) |
| presentmon (custom) | the recording was in progress at the end of the window with zero loss, was saved below its cap, PresentMon exited 0 reading it, and the CSV carries `CPUStartQPC` and at least one frame | the same recording and no CSV (PresentMon writes none without a frame), with no `-ProcessName`; the recording is the proof | the binary or `wpr.exe` is missing, the binary differs from the pin, another WPR recording is active, or `wpr -start` did not complete (nothing recorded) | loss, a recording not in progress at the end, an unreadable loss count, a capped, empty or missing file, a stop that did not complete (cancelled), a PresentMon failure, a CSV above the cap or without `CPUStartQPC`, or zero frames for named processes; a recording with loss or at its cap is kept and says so, every other failure leaves no primary (the full table is in "The presentmon-frames source") |

The range a status speaks for is `raw_time_range` in the manifest entry. It starts at the requested window start, or at the oldest retained record when the log does not reach back that far. In that second case `enabled.options.window_start_utc` differs from `requested.options.window_start_utc`, a note in the manifest and on stderr says so, and nothing is claimed before that time. This is an interpretation of the contract worth stating: the status describes what the collector saw over the range it names, and the later validator's adequacy check ("raw time ranges cover the scenario window") is what refuses a bundle whose range is too short for the question asked of it.

The query interval is fixed before the query runs. The collector takes one end time, `window_end_utc`, and writes it into the query as a FILETIME literal: `timediff(@SystemTime, <end>) >= 0 and timediff(@SystemTime, <end>) <= <window in ms>` selects exactly the interval from `window_end_utc` minus the window to `window_end_utc`. `timediff` with a literal second argument is the documented form ([Consuming events](https://learn.microsoft.com/en-us/windows/win32/wes/consuming-events)); the same page says a result set also receives matching events raised while it is enumerated, which is why the interval has an upper bound. `requested.options.window_start_utc` and `window_end_utc` are that interval, and `raw_time_range` ends at `window_end_utc`. For a WMI history the same interval is a WQL filter on the time property with CIM DATETIME literals, and the coverage probe asks for one row before the window start.

Every read is bounded. Event log records are pulled one at a time with `EventLogReader.ReadEvent(TimeSpan)` carrying the time left before the source deadline; the oldest record probe uses the same call once. A pull that returns nothing after the deadline has passed is treated as a timeout, not as end of stream, because the two cannot be told apart. WMI reads run under `Get-CimInstance -OperationTimeoutSec`, which Microsoft documents as the wait for a response rather than a limit on the whole enumeration, so the source deadline is also checked on every row returned and a slow enumeration that passes it is a timeout. Rows are streamed through the caps, so a provider that never stops producing is cut at `-MaxEvents` or `-MaxArtifactBytes`; a producer stopped that way is `capture_failed` with the capped rows kept.

The binary `.evtx` export is secondary. When `wevtutil epl` fails or exceeds the byte cap, the file is removed, the failure is recorded in `enabled.options` and in the notes, and the source's status is unchanged, because `events.json` already holds the complete XML of every record.

## Read only posture

The collectors read event channels, read WMI classes, read a few registry values, read device properties, read one known file, and hash files. They change no setting, clear no log, start no service, open no network connection, request no Wi-Fi scan themselves (what netsh does is verification item 21), connect to and disconnect from nothing, and touch no process other than the ones they start. The only programs they start are `wevtutil.exe` with the `epl` (export) verb, `netsh.exe` with exactly four `wlan show` listings (an allowlist in `tests/test_collectors_static.py`, so neither spelling of the report generator can pass), and, for `presentmon-frames` only, `wpr.exe` with `-start`, `-status`, `-stop` and `-cancel`, every call ending in `-instancename wf-presentmon-frames`, and the pinned PresentMon console binary with `--etl_file`, `--output_stdout`, `--qpc_time` and `--process_name` (the same test checks the script for every live option, for `--output_file`, for an unnamed wpr call and for every WPR verb that changes a setting; the Pester suite and `tests/test_collector_bundles.py` check the recorded runs), directly and without a shell, through one process runner that stops them at the deadline or at the output cap. The only ETW recording anything here starts, stops or cancels is the WPR instance named `wf-presentmon-frames`, which only `presentmon-frames` ever starts. The only files they delete are their own exports inside the output directory (an `.evtx` that failed or exceeded the cap, a `records.json`, `output.txt`, report copy, `devices.json` or `frames.csv` that must not be left behind, the `trace.etl` that never leaves the PC, and WPR's temporary folder inside the bundle). `tests/test_collectors_static.py` enforces this list. They do not inspect, attach to, or enumerate game processes; `presentmon-frames` records ETW providers with a controller and reads the recording offline with a PresentMon that opens no process ("Why live PresentMon is not used" above; what WPR itself opens is verification item 33).

## Testing

No test here touches a Windows machine.

```
pytest                         schema, layout, checksum and decoder tests over fixtures/collector-bundles
scripts/fetch_pwsh.sh          one time: a pinned PowerShell 7 plus Pester and PSScriptAnalyzer into tools/ (ignored by git)
pytest tests/test_collectors_pwsh.py
```

- `tests/test_collector_bundles.py` validates the committed synthetic bundles against `schemas/manifest.schema.json`, checks every artifact's size and SHA-256, and decodes the event exports into `eventlog_events`.
- `tests/test_rf_survey.py` decodes the five `rf-survey` bundles with `scripts/decode_rf_survey.py` and runs `scripts/analyze_rf_survey.py` over them, with and without an owner selection: a congested airspace whose strongest signal is a neighbour's and whose owner network has two 2.4 GHz access points, a clean airspace, 5 GHz available and absent, a stale profile and an unknown name, a receiver on the USB 3 and on the USB 2 controller, a PC whose wireless service is not running, a connected interface, a German display language, IPv6 only and dual stack routes, a missing signal line and a failing section. The Pester suite covers the pseudonyms (no neighbour name, unseen name, address or peer name in clear anywhere in the bundle), the netsh, file and device sources, the output cap against a real child process, and the failure modes.
- `tests/test_presentmon.py` decodes the six `presentmon-frames` bundles with `scripts/decode_presentmon.py`: a two process recording with NA cells, and the five failures that must not become tables (no frames, no binary, access denied, lost events, overflowed presents); the recording record deciding the time domain and refusing loss, overflow or an unconfirmed window; the start columns the table refuses; unknown columns kept under `raw_columns`; malformed rows; schema violations; the inputs the decoder refuses; and the committed vendor first buffer read field by field at the offsets the collector uses. The Pester suite runs the collector against synthetic wpr and PresentMon programs: the six process starts in order with the instance name on every wpr call and their allowlisted arguments (never a live option), the pin (wrong hash, wrong size, missing file: nothing runs, not even wpr; a file swapped before the read is not run), a leftover of its own instance cancelled and any other probe outcome failing closed, wpr missing, a refused, failed and hanging start, loss from each of the three counters, a hanging stop with and without a confirmed cancel and a stop that left the instance running, a recording that died before the end, a session that closed before the stop, a merged file above the cap, counters or a header that cannot be read, the vendor's first buffer read by the collector and compared with the synthetic layout, settings not shown enabled, an empty PresentMon output scoped and unscoped, overflowed presents, a warning, a failing, hanging or oversized PresentMon, a CSV without `CPUStartQPC`, the console log and recording record, and parameters outside their rules.
- `tests/test_collectors_static.py` checks the interface, the read only posture, the ASCII rule (Windows PowerShell 5.1 reads a script without a byte order mark in the ANSI code page), that this document covers every collector, and that `presentmon-frames` pins one release whose hash, size and URLs agree between the script, this document and the fixtures, passes PresentMon only the offline options and WPR only its four verbs with the instance name on every call, and never names a live PresentMon option, `--output_file`, or a WPR verb that changes a setting.
- `tests/test_collectors_pwsh.py` needs `pwsh` and skips without it. It runs PSScriptAnalyzer with the 5.1 compatibility rules, the Pester suite in `tests/Collectors.Tests.ps1`, a fresh generation of the fixture bundles compared with the committed ones, and the unmodified scripts as processes on a machine with no Windows API, where every source must fail closed.
- The Pester suite replaces the Windows adapters at the bottom of `_common.ps1` with `tests/SyntheticBackend.ps1`. Everything above the adapters (layout, manifest, checksums, status, summary, exit code) is exercised as it will run; the adapters themselves are not.

After changing a collector or the helper, regenerate the fixtures from the repository root:

```
tools/pwsh/pwsh -NoProfile -File collectors/windows/tests/New-FixtureBundles.ps1
```

The fixture content is invented in `tests/SyntheticScenarios.ps1`. Nothing captured from a real machine is ever committed.
